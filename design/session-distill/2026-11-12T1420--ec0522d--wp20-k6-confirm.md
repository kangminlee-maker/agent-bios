# WP-20 K6: the owner confirms one final set, built from S10's approvals and bound to it by field

The sixth package of WP-20 on `wp/20-review` (plan `2026-10-20T2119--cc0498f--implementation-plan.md`, WP-20
done-when 6, 7 and 9 for the confirmation schema; design §10.3, §10.4; release-1 amendment
`2026-11-11T0040--062b76d--…`: S10b is the owner's confirmation of the final set in one pass, with no confirmation
episodes and no S8). It adds `session-distill/runlib/stage_confirm.py`, `schemas/confirmation.schema.json`,
`distill.py confirm`, and S10b's two parts in `records.STAGE_PARTS`. It also carries the two render items folded
into K6.

## What landed

- **S10b has two parts** (`records.STAGE_PARTS`): `build` and `confirm`. The confirm part reads the build part's
  manifest and page as its inputs, so the shared record checks refuse a manifest edited after build
  (`INPUT_INVALID S10b.build`), and refuse an input that moved after build (`INPUT_STALE`), before anything is
  read.
- **build** reads S9's current rows, S10's approvals and committed parses, S7b's review and S2's current inventory.
  It writes `confirm/v<k>/manifest.json`, the page `confirm.ko.v<k>.md` and the owner's copy
  `confirm-decision.ko.v<k>.md`. Each item whose last approval row decides it lands in exactly one place:
  - **F**: approved, changes the library, at the current item_sha, not awaiting R. This is `stage_approvals.f_of`,
    the same function S10 hashed, and `configuration_sha` is S10's.
  - **ledger_only** (§10.4): an approved proposal whose disposition changes nothing installed, each member of an
    approved legacy group under its group, and an adopted S7b alternative whose disposition is ledger-only.
  - **apart, by name**: stale, awaiting R, `needs_proposal` (a 수정, or an adopted alternative that would change the
    library; neither has operations of its own, so S7 proposes them), and `nothing_to_apply` (an approval of a row
    that carries no proposal, such as a returned row; a disputed row cannot be approved at all, which the grammar
    refuses).
- **Refusals at build**:
  - `ALTERNATIVE_STALE`: an adopted alternative that S7b's recorded review no longer offers in the same form (its
    reason text aside).
  - `CONFIRMATION_UNBOUND configuration_sha`: the latest committed parse bound another F.
  - `NOTHING_APPROVED`: no approval is bound. The message counts the apart items by reason.
  - `CONFIRMED_ALREADY`: the run's final set is already confirmed.
- **The order (done-when 6).** F's exact order is answered again over the approved subset alone
  (`sequencing.subset_answer`). Each operation is passed as S7 proposed it, a route's `names` included. The starting
  tree is the paths the current inventory's units hold. A subset with no valid order is shown to the owner with its
  refusal, and that version carries no confirmation block.
- **The page** shows F, the ledger-only set, the apart items with their reasons, the order and the deferred tests. A
  version that can be confirmed has one `owner_lines.confirm_block`, bound to the manifest's set hash. A page line
  that reads as an owner line is refused (`OWNER_SHAPED_TEXT`), and every line of the page is checked, including a
  line break inside a value.
- **confirm** reads the latest version's copy. The block must be bound to the manifest's set hash
  (`CONFIRM_STALE` otherwise). The final set is built again and held to the manifest by field:
  `CONFIRMATION_UNBOUND item_sha <id>`, `configuration_sha`, `manifest_sha` and `results_sha`, then the whole set.
  - `확인: 확정` writes `confirmation.json`: §10.3's binding of the bound approval ids to F's `configuration_sha`, the
    manifest's sha256 as build recorded it, and the results state. It also carries the plan's `confirmation_id`,
    `confirm_version`, `decision_input_sha` and `at`.
  - `확인: 반려` with its 메모 writes `confirm/v<k>/returned.json`. That is not a confirmation, and the owner decides
    again in a new review version.
  - A version is decided once (`VERSION_DECIDED_ALREADY`). An older version than the latest is not decided at all
    (`VERSION_SUPERSEDED`).
- **Release 1's named state.** No S8 ran, so the manifest's `cases` and `results`, and the confirmation's
  `results_sha`, are `untested: s8_deferred`. The schema refuses a null.
- **Contract fidelity (done-when 9)**: the confirmation schema's required set is §10.3's four fields plus the plan's
  four, copied into the module and held by the suite.
- **Declared to the gates**: `runlib/dispatch.py` `SCRIPT_RUNS` names the suite's `distill.py confirm` child;
  `gates/check-endpoints.py` names the schema's dialect pointer; `gates/check-parity.sh` has the suite's leg;
  `gates/control-audit.py` `SUBJECTS` lists the module.

## The two folded render items

- **BLANK_LOOKALIKES is derived** (`runlib/stage_render.py`). It is every Default_Ignorable_Code_Point of a category
  the allowlist writes as itself, plus the braille blank U+2800, which is not default-ignorable but renders as an
  empty cell. Python's `unicodedata` does not carry the property, so `DEFAULT_IGNORABLE` copies its ranges from
  DerivedCoreProperties.txt. Perl's `Unicode::UCD` (Unicode 13.0.0, on the author's machine) lists the same ranges
  but U+180F, which 14.0.0 added as a variation selector. The suite holds the copy to the property's own derivation:
  every format character but the derivation's exclusions (`DI_FORMAT_EXCLUDED`), and every character the database
  names a variation selector. Every code point in the copy must be written in notation, alone or after a letter. The
  derived set equals the set that was listed before.
- **Inside a fence every backslash is shown doubled** (lead decision 2026-11-12). This replaces doubling only a run
  that stands before a replaced character or before its imitation. The renderer's own notation keeps its single
  backslash, so a notation is always the last of an odd run and the file's own `\u....` the end of an even one,
  whatever surrounds it. This is the rule `inline` already follows outside fences. The note under a fence counts the
  doubled backslashes and states the parity rule.

## A control that could not fail by name

`stage_render`'s control "a row S9b marked, rendered without its mark, is refused by name" looked up the marked row with
`next()` and no default. When a rule upstream of it was reverted, the overlay held no such row, and a StopIteration ended
the whole suite before it reported. Six of K2's revert rows showed this as a traceback when they were refreshed. The
row is now looked up with a default, and its absence fails that control by name.

## Observation for lane L

`runlib/drift.py` `order_problems` passes each operation to `sequencing` as its `type` and `target` only, so a
route's `names` and a merge's `units` are dropped. `route_integrity` then reads `route:<target>->None`, and an
approved route would be refused `ROUTE_TO_NOTHING`. This was reported to the lead, not edited here. Lane L fixed
it in `2f369ce` on `wp/21-apply`; S10b is held against that fix at the next merge of that branch.

## Open

- A legacy group's members are listed with the group row's disposition (`none`) and its `legacy_word`. Each member's
  default answer is the ledger's, and S12 applies it from there.
- The order's starting tree is the inventory units' `path` values. If a real inventory records a delivered path in
  another form than a proposal's repo-relative target, a route to an existing guide is refused rather than admitted.
  That fails closed and needs a decision on the path form when S11 lands.
