This record designs the mechanism that produces what
`2026-10-20T1133--02a6ba2--purpose-and-outcomes.md` (below: the purpose record, outcomes
O0–O10) requires. Sources: two independent drafts written from one blind packet
(gpt-6-astra/xhigh, hermetic, receipted; claude-fable-5-1/max), the owner's decisions of

## 2. Owner decisions recorded with this step

- The reconstructed library in the three-alternative comparison is a **separate
  reconstruction of the whole library, once per run**, shared by that run's core items (the
  2026-09-09 sense), with per-item attribution by withholding arms.
- Pre-approval testing uses the **broad scale**: six cases per change, two repetitions, four
  actor strata, five configurations for core changes.
- The rule that the always-loaded global file only shrinks is **enforced by a commit gate**.
- Approval of a subset is **conditional**: the owner decides once; the exact approved set is
  then confirmed by test, and only items whose confirmation fails return to the owner.

## 3. Architecture

One driver, `session-distill/distill.py`, one subcommand per code stage; Workflow scripts for
Claude-side model stages; `codex-run.sh` for OpenAI-side model stages; a test harness under
`benchmarks/` for actor runs. Each run writes under `session-distill/out/<run-id>/`. Runs
share the ledger and the coverage state, nothing else.

```
S0 declare ─► S1 census ─► S2 views + inventory ─► S3 read (+ stitch) ─► S4 form (+ lifecycle)
  ─► S5 retrieve + deterministic checks ─► S6 judge A ║ judge B (+ absence sweeps)
  ─► S7 propose ─► S7b review proposals ─► S8 test ─► S9 render ─► S9b review Korean
  ─► OWNER ─► S10 parse decisions ─► S10b confirm the approved set
  ─► S11 apply + verify delivery ─► S12 close
```

### 3.2 The model-call gate

The driver allocates a `call_id` (run, stage, item, attempt) for every call and passes it in
the packet header and to the runner. Every output passes, in order:

1. **Completion and binding** — exit status zero; no refusal; no truncation (`max_tokens` or
   equivalent is failure); where the contract requires a receipt: the receipt carries this
   `call_id`, the packet and result hashes of the bytes the driver sent and read, the schema
   hash, the seat sent and the seat observed, the profile, the working directory, and the
   context-manifest hash, and each equals what the contract requires. A stale receipt (another
   `call_id`), an inherited profile, or a working directory outside the declared manifest is
   rejected. **(probe 5: the receipt today records the seat sent, not the seat used, and has no
   call id, profile, or context fields.)**
2. **Seat attestation** — the observed model equals the declared seat: `message.model` in
   the Workflow subagent transcript, `claude -p` JSON output, or the receipt. A call whose
   observed model cannot be attested fails. Effort is recorded as requested and marked
   attested only where the runtime reports it.
3. **Schema.**
4. **Cross-record integrity** — every referenced claim, evidence, unit, candidate, and pin id
   resolves.
5. **Set accounting** — every input id of the transformation appears in the output exactly
   once as retained, merged (with explicit membership), rejected (with a reason), or
   quarantined; ids are unique.

A failing output is rejected, retried once with the validation message, then recorded as
failed with every attempt kept. The driver never extracts JSON from prose, repairs values, or
treats a failed call as empty. Rehearsal controls: a truncated output, a nonzero exit, a stale
receipt, a mismatched result hash, an inherited profile, a contaminated working directory, and
an unattested model must each be rejected by name.

### 3.3 Claim records

S3 writes each observation as a **claim record** `{claim_id, fact, interpretation,
uncertainty, evidence_ids, call_id}`. Later stages refer to claims and evidence by id and never
retype them; a stage that revises a claim writes a new claim referencing the old one. The
renderer and the ledger project quotation bytes, fact, interpretation, and uncertainty from the
stores, so these distinctions reach the review and the ledger unchanged.

## 5. Evidence

### 5.1 Census (S1)

Enumeration starts from transcript directories: `~/.claude/projects/*/*.jsonl` and
`~/.codex/sessions/**/*.jsonl`. Classification from the first records: Claude `entrypoint` `cli`
→ claude-cli, `claude-desktop` → claude-desktop, `sdk-*` → excluded (automated); Codex
`session_meta.source` `cli` → codex-cli, `vscode` with originator `Codex Desktop` →
codex-desktop, `exec` → excluded. Child transcripts on both hosts — Claude sidechain or
`agentId` records and subagent transcripts, Codex rollouts with `source: {"subagent": …}` — are
linked to their parent session and read as part of the parent's evidence; they are never
counted as independent owner sessions. Missing or malformed metadata → `unknown_provenance`,
counted and listed. History files are secondary: a history entry without a transcript is
`known_absent`.

Statuses are disjoint; every discovered transcript ends in exactly one: `excluded(reason)`,
`child_of(parent)`, `unknown_provenance`, `unreadable`, `known_absent`, or eligible; eligible
ends as `read_complete`, `read_partial`, `failed`, `deferred`, or `nothing_new`. Code
reconciles S3's results back into these statuses and asserts the counts add up per source. A
missing source directory is unknown coverage, never zero. S1 also reports, per source, how
many eligible sessions have a pin; the claim that desktop sessions carry none (E2: sessions
not launched through activation have no pin) is measured there each run, not assumed.

### 5.2 Transcript versions and ranges

`session-distill/coverage.json` records per transcript a list of versions `{sha,
record_count, prefix_sha}` and, per version, two kinds of range: **read** (records seen in a
view, for any reason) and **processed for window w** (records owned by window w, §5.2 window
membership, whose events were extracted for w). Only processed ranges discharge work: a record
read as context for another window stays unprocessed for its own window, and the run that owns
it reads it again as in-window. Events still `pending` at a run's end are stored in the coverage
state with their ids, and the stitch of a later run (§5.4) joins them to outcome records it
processes, across runs. A later run checks
append-only continuity: the new file's first `record_count` records must hash to the previous
`prefix_sha`. Appended records are new work; a transcript that fails continuity (rewritten or
truncated) becomes a new version read in full, and evidence ids keep pointing at the source
copy of the version they came from. A session is fully covered for window w when its processed
ranges for w cover every record of its latest version that w owns. `read_partial`, `failed`, and `deferred` sessions keep
their unread ranges in a backlog that the next run reads first. Targeted runs read but never
advance the periodic coverage. A window is **accounted** when every eligible session has a
terminal status with its unread ranges in the backlog; the run record reports accounted and
fully read counts separately.

**Window membership.** A record belongs to the window when its timestamp is in `[start,end)`.
An event belongs to the window of its first record. Records outside the window are read only as
context: they may be quoted as context but never count toward this window's recurrence,
occasions, or observations. Backlog ranges from earlier windows are read as late evidence of the
window they belong to and are tagged with it. Every evidence record carries `window_role`:
`in_window`, `context`, or `backlog(<window>)`.

### 5.3 Lineage

Identity is `(host, full session id)`. Two sessions are one lineage when explicit parent,
resume, or fork metadata links them, or when they share at least one identical (timestamp,
human text) turn. Sessions and their links form connected components. A component is an
**affirmed lineage** when exactly one of its sessions carries host metadata marking it as a
fresh root — markers that distinguish fresh, resumed, and forked sessions on each host,
established by probe 8 — and every other member is linked to it; each affirmed lineage counts
once toward recurrence and the promotion bar, however many continuations it has. A component
without such a root, or containing a session whose ancestry is unknown, has unknown
independence and counts toward neither. Fixtures: a fork after one turn, a truncated replay, a replay across windows, a
continuation with no parent metadata and no retained shared turn, and a replay whose timestamps
do not reveal its ancestry, and two independent roots that each have continuations (two
lineages).

### 5.4 Views and expansion (S2, S3)

Each transcript version is copied immutably into the run. The reading view, redacted by
`learn/redact.py` plus local-path masking, keeps human and assistant text whole, each tool call
with its arguments, and each tool result as head, tail, and every error line, with an omission
manifest naming each clipped record, its size, and its omitted span. Views are cut into windows
bounded in tokens (input at most 120k, output capacity reserved), with a five-turn overlap; a
message larger than a window is split into mapped spans.

For every clipped record in its window, S3 returns `expand` or `skip` with a reason (set
accounting over the omission manifest). Expansion is mandatory, by code, for every clipped
record between a pending event (below) and the next human turn, and for every clipped record
that the full-source search below matches. Code supplies each expansion as additional windows
under the same token bound and span mapping.

Two completeness levels are kept apart. A session is **view complete** when every window has a
gate-passing result and every clipped record has an executed expansion or a recorded skip; it is
**source complete** when, in addition, no span was skipped. Coverage reports both. Skipped spans
are listed per session as content not read by judgment.

**Full-source search.** A deterministic search (BM25 with the claim's retrieval terms) over the
full redacted text of every version, including clipped spans, forces expansion of every match.
Search only adds reading; it never closes a claim.

**Coverage basis.** Skipping is a cost control and never evidence that skipped content is
irrelevant. Every claim that depends on what sessions contain carries its coverage basis, set by
code over the claim's **scope** — every session of the window in the sources where the claim
applies, with their linked child transcripts — and checked in this order:

1. **incomplete** — a source in scope is not accounted or its directory is missing; or a session
   in scope is unreadable, known absent, of unknown provenance, `read_partial`, `failed`,
   `deferred`, or has records the window owns that are not yet processed for it;
2. **view** — otherwise, when some session in scope is view complete but not source complete;
3. **source** — otherwise (every session in scope is source complete). Claims of absence
— no occasion for an expected observation, no occasion for a unit in the occasion index — require
basis source; otherwise they are `pending`. A positive claim (observed, an occasion found) may
rest on basis view and is shown with that basis; measures that compare runs count only basis
source and report view-based results beside them (§13.4).

**Stitching.** An event whose cause or outcome lies outside its window is returned with
`outcome: pending` and a description. After all windows of a session are read, code collects
its pending events and the session's later claim records, and one S3 stitch call per session
resolves each pending event with evidence ids or leaves it `unresolved`. Fixture: a cause in the
first window whose outcome appears four windows later.

### 5.5 Evidence locators

An evidence record is `{evidence_id, source_copy, version_sha, line, json_pointer, char_span,
redaction_version, redacted_text}`. Quotes are checked against the deterministic redacted
projection of that content block; the review shows the quote with an openable path and line
into the immutable source copy.

## 6. Library, delivery, and coverage

### 6.1 Inventory (S2)

Code splits every layer of the effective library into numbered units `{unit_id, layer, path,
heading, n, text, sha, operative|reference}`:

- catalog content: rules, guides, skills, hooks, agents from the checkout, plus adopted
  packages;
- the owner's overlays as `compose/instructions_store.py` resolves its effective items;
- native layers: native global instruction files, project instruction files, settings, memory
  entries, session-level injection;
- incubating ledger principles and active `keep` records.

Reference points: *current* (all layers now); *release* (the complete catalog at the session's
time: from a pin's snapshot `inputs.baseline_ref` to `runtime/baselines/<ref>/inventory.json`,
which holds every item's body and source path — measured 2026-10-20 on baseline `4bfdcf44…`:
104 items; for an unpinned session, *release* is unknown unless an install record with a
timestamp maps the session's time to a baseline); *selection* (the pin's snapshot items).
Historical overlays and native layers are unknown unless recorded. Each reference point carries
a completeness flag; an unsupported structure or an unknown layer makes it incomplete.

### 6.2 Judgments (S5, S6)

**Retrieval (code).** BM25 over units, query = situation + action + exception + named hints;
top 20 per layer plus every unit a candidate names; and the top ledger entries by the same
query.

**Judges (model).** Both judges receive the candidate, its claims and evidence (projected by
code), the retrieved units, and the retrieved ledger entries. Per unit: situation match, action
match, reason, quoting the unit. Per candidate: each admission requirement `met | unmet |
uncertain` with reason; for each matching unit, its following (`followed | not_followed |
unknown`) and its contribution to the outcome (`helped | harmed | neutral | unknown`), each with
evidence ids — kept apart from the event's consequence, which admission judges; the consequence class; the relation to each
retrieved ledger entry (recurrence, revision, contradiction, relation to a retired entry, or
none). Judge B receives only its packet. A judgment is reused across reference points only when
its complete judgment packet is identical: the key is the hash of the packet itself — candidate
version with its claim and evidence versions, unit text, heading path, the enclosing guide's or
router line's trigger, enclosing exceptions, the operative units it references, layer, scope,
prompt and schema versions, and seat. The same key is used for deduplication and for cost
estimates.

**Absence sweeps.** A diagnosis that rests on "no unit covers" at a reference point requires
that reference point to be complete, and an exhaustive sweep of its remaining units in shards,
each shard judging several candidates: once by claude-sonnet-5-5 (producing call) and once by
gpt-6-luna (independent-judgment contract), each returning per unit situation match, action
match, and a one-line reason, bound to the inventory hash. Judge B then reviews, per absence
claim, every unit either sweep marked as a partial match, plus a code-drawn sample of fifty
negatives (seeded by run id) with both reasons. A unit flagged by either sweep or by Judge B
returns to both judges; disagreement makes the candidate disputed. At an incomplete reference
point the absence conclusion is `unknown`.

### 6.3 Delivery evidence

Selection is not delivery. Evidence levels, each with its time, which must precede the event
being diagnosed:

| Surface | Levels |
|---|---|
| Rule on the always surface | selected → exposed (in the compiled `output.json` instruction text, route not in its `unavailable` list) |
| Guide | selected → pointer exposed (router path in the compiled text) → router read (transcript reads `router/relevant.md` and the returned content holds the guide's trigger line) → unit read (the unit's **operative context** — the same set the judgment packet of §6.2 holds — is a set of requirements, each a source file, its version, and a span: the unit's text and heading path, the enclosing trigger and exceptions, and every operative unit it references, which may live in other guides or the router; the requirement set is met when, across every read the session made before the decision, the bytes the tool actually returned, with line-number prefixes removed, cover each span, and each covering span matches its own source's version; a requested offset and limit are never enough, since a response can be truncated; a returned fragment that matches two versions of its source equally binds to the version the pin or release names, else that requirement's version is unknown) |
| Executable invoked directly (hook script, skill script, tool, wrapper) | identity (the effective path the session or launcher resolves points to an artifact whose hash is recorded) → invoked (a transcript tool call, process record, or receipt naming that path and hash) → completed (its exit status) |
| Executable producing consumed artifacts (catalog compiler, installer) | identity of the producing version → consumed (the session's snapshot records the compiler's digest in `inputs.compiler_digest`; for the installer, an **installation receipt** — new, written by the installer at the end of each successful transaction — binds the digest of the installer code that actually executed, the transaction id and result, the installed release digest, and the resulting artifact hashes; and the store, when it builds a session's snapshot (`compose/instructions_store.py`), records in the snapshot's inputs the id of the installation receipt it read the release from, before the snapshot's `content_ref` is derived, and activation keeps that immutable binding, so a session is bound to exactly one installation transaction even when several transactions served the same release; consumption is shown when that receipt is a success receipt and its resulting artifact hashes include the artifacts the snapshot records; the release's own package identity is not evidence of which installer ran) |
| Skill | selected → listed → invoked |
| Hook | selected → registered for the route → fired (execution evidence) |
| Native layer | identity (file hash recorded) → loaded (the host's loading record in the transcript) |

The **delivery state** of a matching unit for a session is one of: `delivered` (at the level the
diagnosis needs, before the decision or action the event concerns); `exposed_not_read` (guide
pointer exposed, but the unit's operative context was not fully returned before that decision or
action); `selected_unavailable` (in the selection, but its route is in the compiled
output's `unavailable` list or its native route did not load); `not_delivered` (the complete
*release* holds it, the *selection* lacks it); `unknown` (any needed evidence missing).

A session without an activation pin (per E2, one not launched through activation, which today
includes the desktop apps) has no selection evidence, so its selection and the completeness of
its *release* are unknown, and `not_delivered` cannot be shown for it. Its units are still
diagnosed from the evidence that exists — a guide unit read before the action (version-bound by
the returned content), a native layer with its loading record, an executable with its identity
and invocation — and only what is actually missing stays `unknown`.

### 6.4 Derivations (code)

- **Unit diagnosis**: situation yes / action yes → covers; situation yes / action no → wrong or
  insufficient; situation no / action yes → trigger problem; neither → no match. Every unit's
  diagnosis, delivery state, following, and consequence are kept per unit and shown.
- **Candidate diagnosis**, per reference point, by precedence over its units: covered (list
  every covering unit) > wrong or insufficient > trigger problem > gap; an incomplete reference
  point turns "gap" into `unknown`. A lifecycle redundancy candidate (§7.1) whose judges find two
  or more units covering the same situation and action is diagnosed `redundant`.
- **Unit outcome**, for each unit with a diagnosis other than no match, from its delivery state,
  following, and contribution. The table is total; a row marked "—" accepts every value:

| Unit diagnosis | Delivery | Following | Contribution | Unit outcome |
|---|---|---|---|---|
| any | unknown | — | — | unknown |
| any | selected_unavailable or not_delivered | — | — | not delivered |
| covers | exposed_not_read | — | — | misfire (trigger) |
| covers | delivered | not_followed | — | misfire |
| covers | delivered | followed | harmed | misfire |
| covers | delivered | followed | helped | confirmed |
| covers | delivered | followed | neutral | neutral (followed, no effect) |
| covers | delivered | followed | unknown | unknown |
| covers | delivered | unknown | — | unknown |
| trigger problem, wrong or insufficient | delivered or exposed_not_read | — | — | misfire |

- **Kind**, over the unit outcomes, in this order, so that a helpful unit never hides a harmful,
  missed, or unresolved one: any misfire → misfire; else any not delivered → not delivered; else
  any unknown → unclassified; else any confirmed → confirmed; else (all neutral) → unclassified.
  Every unit's outcome and uncertainty is shown with the kind. With no matching unit: gap at *release* and *current* → gap; gap at *release*,
  covered at *current* → already resolved (no proposal). A lifecycle candidate with evidence that
  the situation no longer arises → obsolete. A redundancy candidate keeps the kind its units
  yield and carries the diagnosis `redundant`.

- **Admission**: admitted only when both judges mark all eight requirements `met` and every
  deterministic check passes. All `unmet` from both on some requirement → rejected. Anything
  else → disputed.
- **Promotion eligibility**: affirmed independent lineages ≥ 2, or a consequence both judges
  classed irreversible, security-relevant, or verification-corrupting; type G uses its own bar
  (§7.4). Below the bar, the allowed dispositions are incubate, keep, and drop.

### 6.5 Planted controls

Every run: two paraphrases of covered units (must match their unit); two admission failures
(cause by temporal order only; a task-specific requirement); one altered quote; one fabricated
session id; the model-call gate controls of §3.2. Controls enter under ordinary ids and are
reported apart from the natural rejection share. More than twenty natural candidates with no
rejection fails O4.

## 7. Proposals and placement

### 7.1 Lifecycle inputs (S4)

Besides session events, S4 receives: every unresolved incubate decision whose expiry is on or
before the window end — whether it is an incubating entry or a pending intervention on a placed
entry (§12.3) — with the window's occasions for its observation; obsolete-review hints;
redundancy hints; and the G inputs of §7.4. A later decision on the same learning or intervention
names the incubate decision it resolves (`resolves: <decision id>`), so the pending item leaves
the intake only when resolved or expired-and-dropped, and the installed entry's history is kept.

**Legacy incubation.** Entries migrated in `incubating` status carry no observation or expiry
(measured 2026-10-20: 142 entries in `incubating` or `incubating-G`, some with no decision that
maps to incubate, for example S3-03). The first run's intake includes every one of them as a
lifecycle candidate marked `legacy, observation unavailable`; they are judged against the
window's evidence like any candidate, and S7 proposes for each a disposition under the
legacy-maintenance row of §7.2 — incubate with a prospective observation and expiry, or drop —
even when its historical evidence is unavailable and its kind stays unclassified; placing it
still needs its own admission and promotion evidence. No past decision is invented, and the
unavailable evidence stays marked. Until an entry receives an applied decision, it stays in every
run's intake.

- **Occasion index**: at S12 code records, per unit, whether the full-source search (§5.4) with
  the unit's trigger terms matched any in-window record, and the window's coverage basis. A unit
  with no match in three consecutive windows of basis source becomes an obsolete-review hint. A hint is not evidence: obsolete requires the judges to find evidence
  that the situation no longer arises (for example, the tool or version it concerns is gone from
  the current dependencies); low frequency alone retires nothing.
- **Redundancy hints**: code pairs units of the current library whose BM25 similarity exceeds a
  fixed threshold; S4 turns a pair into a redundancy candidate only when both units are operative.
  The judges decide whether both cover the same situation and action (§6.4); a redundant pair may
  be reduced by a faithful merge even when both units work.

### 7.2 Fields

Every row carries four separate fields with closed vocabularies:

- **kind**: misfire, gap, not delivered, confirmed, obsolete, already resolved, unclassified;
- **diagnosis**: covered, wrong or insufficient, trigger problem, gap, redundant, unknown;
- **disposition**: place, correct, re-deliver, keep, reduce, incubate, drop, none;
- **status**: rejected, disputed, admitted, quarantined, proposed, tested, untested,
  approved, confirmed, applied, delivery_verified, delivery_failed, returned.

Allowed dispositions by kind and diagnosis (code rejects any other pair):

| Kind / diagnosis | Allowed |
|---|---|
| gap | place, incubate, drop |
| misfire, trigger problem | re-deliver, correct, incubate, drop (drop needs a reason naming why the miss is acceptable) |
| misfire, wrong or insufficient | correct, incubate, drop (same) |
| misfire, covered (not followed or harmed) | correct, re-deliver, reduce (when harmful), incubate, drop (same) |
| not delivered | re-deliver, incubate, drop |
| confirmed | keep, none |
| any kind, diagnosis redundant | reduce (merge), keep (with reason), none |
| obsolete | reduce, keep (with reason), none |

## 8. Pre-approval testing (S8)

Every item with disposition place, correct, re-deliver, or reduce — core or personal — is
tested before the owner decides it.

### 8.1 Episodes, cells, and isolation

An **episode** is one actor run. A **cell** is the aggregate (configuration, case, stratum) whose
episodes are its repetitions. Each configuration has a **configuration manifest** — catalog
release hash, overlay state hash, native files, settings, memory, injection, fixture hash, and,
when the configuration includes author-side changes, the tree hash of the worktree holding them
and the executor artifacts built from it — and its hash is the `configuration_sha`. From the
manifest the harness builds a template tree with its own HOME, `CLAUDE_CONFIG_DIR` and
`CODEX_HOME`, the agent-bios roots (`AGENT_BIOS_STATE_DIR`, `AGENT_BIOS_INSTRUCTIONS_DIR`, and
the install, launcher, and bin destinations of `compose/instructions_install.py`), the private
release installed into those roots, and the fixture as the working directory with no instruction
files in its ancestry but its own. Credentials are linked read-only. Every episode runs in a
fresh copy-on-write clone of its template, so state changed by one episode never reaches
another; the harness records the instruction surfaces' hashes before and after each episode and
marks the episode invalid if any changed without authorization.

Isolation is established, not inferred from silence, by three checks per episode: a static check
that no file in the template names a path outside the cell (settings, hook commands, imports,
native instruction files); the host's own report of its effective configuration (the session's
initial configuration record listing its configuration directory, working directory, loaded
instruction files, hooks, and plugins), which must name only cell paths; and, where the
operating system allows it for that host, a sandbox profile that denies reads of the owner's
real roots, so that a leak fails loudly instead of passing unseen. **(probe 2)**

Every configuration receives the same native layers captured from the owner at S0, except where
the change under test is a personal change to one of them. Before any actor runs, code scans
every effective instruction surface of every comparison arm and asserts its intervention (§8.6)
is present or absent as the arm requires.

### 8.2 Headless activated actors

The harness runs each episode one-shot through the full activation lifecycle of
`compose/instructions_session.py` — snapshot verification, native route validation
(`validate_claude_plugins`, `validate_codex_hooks`), argument composition, pin preparation and
observation — using `claude -p --output-format json` and `codex exec --json` in place of the
interactive launch. Activation today launches Codex only through an interactive `codex resume`,
and the battery dispatches both CLIs without activation, so this adapter is new. **(probe 1)**

### 8.3 Child actors

For contracts claiming subagent reach, the case's task genuinely needs a delegation, and the
harness fixes the child's task brief: the parent is given the exact brief to hand over, the
harness captures the brief actually sent (the parent's tool input or spawn message), and an
episode whose sent brief is not byte-identical to the fixed brief is invalid — so neither a
literal nor a paraphrased copy of the unit can reach the child through the brief. Child delivery
is claimed only with version-bound route evidence: the child's own record of its effective
context (the instruction files, plugin or agent definition, or instruction hash the host records
for the child session) naming the cell's compiled artifact. Which record each host provides is
established by probe 3; a host that provides none supports no child-reach claim, and its child
stratum is reported as behaviorally tested only. The behavioral test compares the applied
configuration with the item in its B state (§8.6) under the identical brief. **(probe 3)**
Contracts that claim hermetic-reviewer, script, gate, or hook reach also get a route-specific
executor check, run from the exact tree hash in the configuration manifest.

### 8.4 Actors

Four strata on every case: Claude main, Claude subagent, Codex main, Codex subagent. At S0 code
takes each stratum's seat from the window's observed usage (the most-used seat by session count,
ties broken by most recent use); a stratum with no observed usage takes the fallback in
`session-distill/seats.json` and is marked `fallback`. Every seat must be covered by a prompting
guide; a check over `run.json` joins `launch/check-prompting-targets.sh`. The actor explains the
lesson only after its actions are frozen.

### 8.5 Cases and calibration

gpt-6-astra (authoring contract) writes six cases per change from the behavior contract and
evidence, never the proposed wording: two unseen positive analogues (one keyword-stripped), two
non-trigger or exception cases (one with the competing value), two regressions. Each case has a
fixture, a completion mode (action cases run uncapped to completion within the episode budget; the
battery's four-action cap applies only to recognition-only cases), a deterministic postcondition
wherever an artifact can show the action, a HIT criterion, and a `naive_miss`, all written
before any run. The battery's 13 scenarios are the shared regression set; items sharing a unit
or route get interaction cases.

Per case the author also writes calibration responses, one per failure dimension that applies:
a full HIT; a `naive_miss`; recognition without action; correct action with a wrong explanation;
for non-trigger cases an over-trigger. claude-opus-5-5 (independent contract) labels them blind;
a disagreement with the author's label invalidates the case's calibration, and the author reworks
it once. Every required case slot stays in the manifest: a slot whose calibration is still invalid
may receive a valid replacement case only before any actor result is seen; otherwise the slot's
cells are `invalid` and the item is incompletely tested. The action dimension is decided by the
postcondition where one exists and needs no calibration there.

A leakage review (claude-opus-5-5, independent contract) checks every actor-visible request and
fixture for the diagnosis in any wording; code enforces literal stripping only for the
designated keyword-stripped variant.

### 8.6 Configurations and interventions

Item i's **intervention** is its operations; its **B state** is the state of its targets in B
(for place: absent; for correct: the prior wording; for re-deliver: the prior routing; for
reduce: the removed content present).

- **B** — the library at the run's starting commit, with the S0 native layers.
- **A** — B plus every proposed core intervention.
- **R** — a whole-library reconstruction, once per run, by gpt-6-astra (authoring contract),
  from the frozen baseline's purposes, its unit inventory, and the behavior contracts of the
  run's core items, never shown A's wording or any result. The requirement set is frozen when R
  is built (after S7b of the first pass): a later revision of a core item that keeps its behavior
  contract reuses R; a core item admitted later by adjudication, or revised so that its behavior
  contract changes, has no R comparison in this run and waits for the next run's R (§10.2). The
  **evaluation infrastructure** stays fixed in R — the driver, the test harness, the hermetic
  runners, the scorers, and item identities. Everything that is part of the **evaluated
  configuration** can differ in R: item bodies and their arrangement, routing data (router lines,
  selection and domain mappings, hook registrations), executable item members (hook and skill
  scripts), and, when an accepted requirement needs it, an executable patch to shipped machinery
  — a wrapper, the catalog compiler, or the installer — written by the R author for that
  requirement, built into R's own private release, and tested like any executable change.
  So a requirement carried by a route, a script, or a wrapper is carried by R's own choice of
  carrier, and R−i reverts that carrier. R comes with two maps: every baseline operative unit's obligation → the R items that carry it
  (or "dropped" with a reason), and every accepted requirement → its R items, routes, and
  executable carriers.
  claude-opus-5-5 (independent contract) validates both maps in shards; a failing map is
  reworked once, and a still-failing R is invalid, which leaves every core item `untested` for
  the three-alternative comparison and therefore not eligible. **(probe 7)**
- **A−i** — A with item i in its B state. **R−i** — R with requirement i's carriers (text and
  routes) rewritten by the reconstruction author to its B-state obligation; claude-opus-5-5
  confirms that A−i and R−i differ from A and R only in item i. Where that fails for R, attribution of item i inside R is
  `unresolved`: the review shows it, the owner may still approve, and no item-level effect inside
  R is claimed or recorded.

Personal changes use B and B plus the change; the final combination is tested in S10b.
Author-side changes (this repository's own gates and tools, which do not ship) use B and B plus
the change at the same broad scale — six cases, two episodes, four strata — with cases built
around the moment an agent meets the change (for a gate: committing in a fixture repository where
the gate fires, and a clean commit where it must not), supplemented by the artifact validation of
§8.8, including the change's own negative control (it must fail on a planted violation and pass
on the clean tree), and by the route-specific executor check when the contract claims one. An
intervention that changes anything shipped is core, whatever else it touches, and needs R.

### 8.7 Scoring and acceptance

The scoring judge is of the other provider than the actor (gpt-6-astra for Claude actors;
claude-opus-5-5 through the hermetic Claude runner for Codex actors), through the model-call
gate, and scores a case only after classifying all of its calibration responses correctly;
otherwise the case is `unscored`. Scores are per dimension: recognition, completed action (the
postcondition decides where one exists), meaning, boundary, regression.

Acceptance rules, fixed before any run and bound into the manifest with the adaptive slots:

- An **episode** passes when every dimension its case type requires passes: positive —
  recognition, completed action, meaning; non-trigger — boundary and no harm; regression —
  regression.
- A **cell** starts with two episodes: 2/2 pass → pass; 0/2 → fail; 1/2 → two more episodes from
  its pre-bound adaptive slots, then 3/4 or 4/4 → pass, otherwise fail. An unscored,
  budget-stopped, or invalid episode is re-run once; still not scorable → the cell is `invalid`.
- An item is **accepted on A** when, in every stratum its contract claims, both positive cells
  pass, and in every stratum its non-trigger and regression cells pass. It **shows
  improvement** when, in addition, B fails at least one of those positive cells. Failures in B,
  A−i, or R−i are outcomes, not invalid tests. Any invalid cell makes the item `incompletely
  tested`, which is not eligible.
- Item i's contribution inside A is A versus A−i, and inside R is R versus R−i, each conditional
  on the other interventions present. A versus R is reported as a library-level difference,
  never attributed to wording or placement of one item. When R carries a requirement better than
  A, R's text for it becomes a new proposal that goes through S7, S7b, and S8 in its own intended
  configuration. Results describe these fixtures at this sample size, not general effectiveness.

### 8.8 Artifact validation

S8 also builds every proposed artifact set into a scratch worktree and runs
`gates/emit-mirrors.py`, the parity umbrella, the lexicon and package gates, the translation
presence check, and author-side negative controls; these results are bound into the item's
results alongside the actor results.

## 9. Review (S9, S9b)

`review.ko.v<n>.md`, code-rendered from validated payloads; each render is a new immutable
version. S4's set accounting classifies every event as a member of a candidate, a **non-finding**

**rejected finding** (S4 formed a claim about what to do differently but it fails an admission
requirement at formation, for example a task-specific requirement). One population: every
candidate (including lifecycle candidates), every rejected finding, and every quarantined or
failed item. Non-findings are counted by reason in the coverage section and listed with locators
in an appendix. Every row has every O6 field — what
happened (claims with quotes), proposal (or the no-change outcome, for example "제안 없음: 이미
해결됨"), reason, cost (or none), whom it serves, falsifier — plus kind, diagnosis, the related

## 10. Decisions and application (S10, S10b, S11)

### 10.1 Decisions

Per row the owner writes `결정:` followed by one of `승인`, `수정`, `보류`, `기각`, `판정`, with a
note. `수정` returns the item to S7 with the note (naming S7b's alternative adopts it). `판정`
lists, per disputed judgment, the side chosen or the owner's own value. A `reduce` or `merge`
over a `keep` record needs `keep 해제: <record id>` with grounds. Code parses decisions into
`approvals.jsonl` `{approval_id (code-generated), item_id, item_sha, review_version_sha,
configuration_sha, manifest_sha, results_sha, decision, superseded_keeps, note, at}` and
`adjudications.jsonl` `{adjudication_id, candidate_id, resolved: [{judgment_ref, choice}],
rationale}`. An item whose sha changed after rendering must be decided again.

### 10.2 Adjudication

Code recomputes the derivations of §6.4 with the adjudicated values. A candidate that becomes
admitted goes through S7, S7b, and S8 in a second pass of the same run and appears in a new
review version for its decision. A core item admitted this way is tested on B, A, and A−i in
this run; because R is frozen (§8.6), its three-alternative comparison happens in the next run,
and until then it is not eligible for application and stays `incubating` with the reason
"awaiting R". Personal items admitted by adjudication need no R and proceed.

### 10.3 Conditional approval and confirmation (S10b)

`승인` is approval conditional on confirmation of the exact final configuration. Code builds
**F** = B plus every approved core, personal, and author intervention, and runs on F, in all four
strata: each approved item's six cases and interaction cases, the shared regressions, and the
artifact validation of §8.8. B's results are reused from S8, since B's configuration manifest and
the cases are unchanged; if either changed, B runs again. The acceptance rules of §8.7 apply. When every
item is accepted, code writes a confirmation record binding the approval ids to F's
`configuration_sha` and the confirmation manifest and results hashes; this binding is what S11
applies. When an item fails, it returns to the owner in a new review version with the new
results, F is rebuilt without it, and confirmation repeats, at most once per approved item.

### 10.4 Eligibility

**Ledger-only dispositions** — keep, incubate, drop, and none — change no installed instruction,
so they skip the behavior matrices of S8 and are not part of F. Each still passes the structural
rules of §7.3 and S7b, needs an approval row, and is applied by S12 to the ledger alone (a keep
record, a pending intervention or incubating entry with its observation and expiry, a dropped
intervention or retired entry with its reason). The rest of this section concerns dispositions
that change the library.

S11 applies an item only when all hold: admitted (directly or by adjudication and re-test);
disposition allowed by §6.4 and §7.2; no unresolved dispute; accepted on its assigned arms with a
complete matrix (core on A; personal and author-side on B plus the change, author-side also by
artifact validation and executor checks; §8.6); for core items, a valid R with a complete R and R−i comparison, whose item attribution is
either validated or recorded as unresolved with restricted claims; artifact validation passed; an approval row whose hashes match the rendered artifacts; superseded keeps named where
required; and a confirmation record for the F that contains it. An ineligible item is returned
with the failing condition named.

### 10.5 Application

Before applying anything, code recomputes the live configuration manifest (every layer of §6.1,
dependencies, and author-side tree hashes) and compares it with F's manifest minus the approved
interventions; any difference is drift, which stops the affected items for rebuild, retest, and
re-confirmation. F fixes the order of operations; operations sharing a target are chained, each
expecting the previous operation's after-hash as its before-hash, and each operation re-checks
its own target before running.

The side-effect journal is write-ahead: before each effect, a `planned` record (durable operation
id, target, expected before-hash, intended after-hash) is written and fsynced; after the effect,
a `done` record. Commits carry the operation id in their message; installation is idempotent and
always followed by verification. Core: one commit per item on a branch naming item and approval ids — canonical text
under `claude/` and `ko/claude/` (the named development-time exception of D-20260804-67d586),
then `gates/emit-mirrors.py` and the parity umbrella. Personal: the approved patch to the named
external file with an application receipt. Author: the gate change with its negative control.

**Delivery verification.** `bash install.sh install --non-interactive`, `bash install.sh
verify`, then fresh activated sessions through the §8.2 adapter. Every applied unit is checked
at its surface's levels (§6.3): a rule — exposed; a guide — pointer exposed, and in a fixture
where its trigger applies, router read and guide read; a skill — listed and invoked when its
trigger applies; a hook — registered and fired on a probe event; a native layer — identity and
loaded; an executable — the effective path the launcher or session resolves points to the
applied artifact's hash, and the route-specific executor check of §8.3, rerun from that installed
path, shows it invoked and completed, against the item's B-state executable. Operation-specific:
create and edit — the new unit traced from canonical source through the catalog's origin mapping
into the compiled output (or, for an executable, to its installed path), and the replaced text or
version absent; delete and merge — the removed unit absent, the merged unit present; route — the
route entry present and the unit reaching the session by it. Author-side changes do not ship and
have no installed path: they are verified in the checkout, by the §8.3 executor contract run
against the effective checkout executor bound to the approved tree hash — for a gate, the route
from `.githooks/pre-commit` (or the umbrella that calls it) to the changed gate is present, and
the gate's violation and clean controls are rerun there. Controls: a selected-but-unused
unit, an emitted-but-unavailable unit, and a fresh pin paired with an invocation of the old
executable version must fail. Claimed child reach is verified by §8.3's controlled
delegation with the item's operation-specific contrast — the applied configuration against the
item in its B state (a reduction: the removed content present in B and absent after; a
correction or re-delivery: the prior wording or route in B) — and the child's version-bound
context record naming the applied artifact; a failed check sets the item's delivery `failed` and
returns it for revision, never narrowing the claim silently.

### 10.6 Recovery

An item whose operations completed but whose delivery check failed or did not run is recorded
`applied` with delivery `failed` or `unverified`, not lost. If S11 stops partway, a recovery close
reads the journal and reconciles every `planned` record without `done`: the target shows the
intended after-hash → the effect happened, record `done`; the target shows the expected
before-hash → the effect did not happen, leave it not done; anything else → drift, stop the item.
For commits the check is the operation id in the branch log; for installation, re-running install
and verify. The recovery close then records every completed operation in the ledger with its
delivery state and leaves the rest as not done; replaying S11 skips operations already `done`.
The next review lists every `applied` item without verified delivery for the owner to keep,
revert, or revise.

## 11. Follow-up (S3, S12)

An occasion is a located decision or action opportunity inside a session — the span where the
expected observation's occasion criteria hold, found by reading (with the full-source search of
§5.4 forcing expansions) and judged. Its **exposure** to the applied item must be shown before the
decision or action the occasion concerns, not before the session began, so a request followed by
a guide read and then the action is exposed; whether the trigger was recognized in time is judged
separately and reported. Exposure is: create or edit — delivery of the applied unit version at its
surface's level (§6.3); delete or merge — the session's pin shows the removed unit absent (and
the merged unit present); route — the pin shows the route entry and the unit reached by it;
executable, by its role — invoked directly (a hook, script, tool, or wrapper): the invocation at
that occasion names the applied artifact's path and hash; producing an artifact others consume (the
catalog compiler, the installer): the session consumed an artifact produced by the applied version,
shown by the version digest the artifact records (the snapshot's `inputs.compiler_digest` for the
compiler; for the installer, the installation receipt bound to the session's snapshot, §6.3, names
the applied installer digest); deleted: the effective resolution
recorded at that occasion — the launcher binding or the invocation record's resolved path and
artifact hash — shows neither the removed artifact nor an older fallback carrier, and shows any
required replacement; when the occasion recorded no resolution, exposure is `exposure_unknown`;
personal — the layer's identity matches the applied hash and the host's loading record shows it
loaded. An occasion with exposure is **eligible**; one whose exposure cannot be shown is
`exposure_unknown`. S3 judges each eligible occasion observed or not observed with evidence ids,
and every instance is kept. Code derives the item's window resolution:

- **not observed** — at least one eligible occasion not observed (counts shown), whatever else
  is incomplete;
- **observed** — at least one eligible occasion, all eligible occasions observed, no
  `exposure_unknown` occasion, and coverage basis (§5.4) source or view — the basis is recorded
  with the resolution, because a view-based "observed" cannot rule out an unseen occasion that was
  not observed;
- **no occasion** — coverage basis source and no occasion found;
- otherwise **pending** (basis incomplete, basis view for an absence, or `exposure_unknown`
  occasions), carried to the next window. Observed instances are kept whatever the resolution.

Observation records behavior, not causal attribution. `plain-asks.py` is reused only for
expected observations whose counter is "plain-explanation asks": an adapter feeds it the
normalized census (Claude sources; Codex sources are reported unsupported), counts asks per
eligible session after application, compares the rate with the declared pre-application
baseline windows, and resolves by the threshold the expected observation declares.

## 13. Global file, budget, and measures

### 13.1 The global-file rule

A gate leg compares `claude/CLAUDE.md` in the index with `HEAD` and **blocks** when the line
count or byte count grows. It **discloses** every index line absent from `HEAD`, because whether
such a line is a faithful merge is a judgement. S11 accepts a global operation only with an
approval row naming it as delete or merge and, for a merge, S7b's faithful-merge judgment or the
owner's explicit override with a reason. Controls: an added line and an added word block; a
deleted line passes; a deletion plus a shorter unrelated line passes the count check and appears
in the disclosure.

### 13.2 Budget

**Access and usage limits.** Both providers are reached through subscription logins (measured
2026-10-20: Claude through a Max subscription with extra usage enabled on the account; Codex
through a ChatGPT login; no API keys on either). A run's binding constraint is therefore the
providers' usage limits, not money: the budget is declared in tokens per stage and in usage-limit
windows, and the dollar figures of §16 measure volume at placeholder rates, not charges. Default,
recorded at S0 and changeable by the owner there: the run stays within plan limits and does not
draw on extra usage. The harness cannot always tell plan usage from extra usage, so S0 records
the account's extra-usage setting and the default holds only with that setting off; with it on,
S0 records that the owner accepts possible charges. When a provider signals a usage limit, a
circuit breaker stops all dispatch to that provider — no retries against a live limit — records
the outstanding work per item, and resumes it after the window resets; items waiting on that
provider stay `deferred`, and independent items on the other provider continue.

The budget is a declared limit with measured overshoot, not a guaranteed ceiling. A hard ceiling
would need an enforceable maximum charge for every request an agent-backed call can make —
including compaction requests, automatic retries, and children — and the hosts' only firm input
limit is the model's context window, which would make each reservation so large that runs could
not proceed in parallel. The purpose record asks for a declared budget and recorded spend, not a
ceiling, so the design does not claim one.

Every agent-backed dispatch — actor episodes, and also independent judgments, authoring, and
producing calls, since `codex exec` and Workflow subagents may take several turns — is accounted
as an episode. Before dispatch, the harness reserves the episode's **calibrated cost**: the 95th
percentile of measured cost for its class (stage, seat, case type), from the rehearsal and
updated from each run. It starts an episode only when that reservation fits the stage's remaining
budget. During the episode it reads streamed usage and stops the episode at its declared cap,
killing its whole process tree, recording it `budget_stopped` (re-run once per §8.7, then
invalid); a request whose final usage has not arrived is carried as provisional (§13.3). Spend is
recorded in the three states of §13.3; spend past the cap or past the reservation is reported per
episode and per stage as overshoot, measured or estimated. When a stage's remaining budget
cannot fit the next reservation, the remaining work is recorded as not done. A budget amendment
is recorded before spending against it. **(probe 9)**

### 13.3 Usage capture

Every call and episode records `call_id`, stage, seat requested and observed, input, output, and
cache tokens, wall time, and retries — from Workflow subagent transcripts, `claude -p` JSON
output, and the Codex rollout's token counts copied into the receipt before its temporary home is
deleted **(probe 5)**. Cost is computed from a versioned price table.

Usage has three states, kept apart: **measured** (the host or receipt reported it),
**provisional** (a request whose final usage has not arrived, carried at an estimate — the class's
highest observed request cost — and labelled as an estimate), and **unresolved** (no estimate is
possible). Late usage replaces the provisional figure when it arrives. Every stage and the run
report measured totals, provisional totals, and the count of unresolved requests, with a
completeness flag; overshoot is reported as measured or as estimated accordingly, and a total that
contains provisional or unresolved parts is never presented as measured.

### 13.4 Measures

Each is computed by S12 into `run-record.json`, absolute and per fully read session; an unknown or
inapplicable denominator is reported as such, never dropped.

| Measure | Formula |
|---|---|
| coverage, per source | over all discovered transcripts that are not excluded or child-linked (eligible, unknown provenance, unreadable, known absent): source complete, view complete, accounted, unreadable, known absent, each / that total; a source whose directory is missing is reported unknown with no total |
| rejection share | natural candidates rejected / natural candidates; controls reported apart |
| owner overturn rate | per item, its proposal is frozen the first time it is rendered as proposed and tested (in any review version); overturned = finally rejected, or changed materially (disposition, destination, operation targets, or behavior contract differ from the frozen proposal), counted once per item; rate = overturned / such items decided; above one in three, the filter failed; wording-only changes reported apart |
| owner review time | per review version, render time to decision-parse time (an upper bound) |
| reach | applied items with delivery verified / applied items |
| effect | previous windows' resolutions with basis source: observed / (observed + not observed); view-based observed reported beside it, not in the ratio; pending and no occasion counted apart |
| library size | global lines and bytes (non-increasing), library bytes, placed vs incubating, incubating past expiry |
| run cost per stage | sums over usage capture |

## 14. Feasibility probes (before the implementation plan)

Each probe has a pass condition; a failing probe sends its part of this design back for revision
before planning.

1. **Headless activated actor, both hosts.** The adapter runs the full activation lifecycle
   (§8.2). Pass: for valid, invalid, disabled, and unavailable native routes it reaches the same
   outcome the interactive launch reaches; the pin's session id equals the host session id in
   the JSON output; the pin names the compiled artifact the session consumed; a planted rule
   changes behavior on a fixture.
2. **Isolated episode, both hosts.** Pass: authentication works; the static check, the host's
   effective-configuration report, and (where available) the read-denying sandbox profile all
   operate; a native global planted in the cell is loaded by the host's normal mechanism (shown
   by behavior on a fixture, with no explicit file read); two concurrent episodes do not see each
   other's state. Negative controls that must fail by name: a copied setting that points at a
   behavior-changing file in the owner's real roots (caught by the static check, and — with the
   static check disabled — by the effective-configuration report or the sandbox, never passing
   silently); a read of a real-root file whose content is never quoted.
3. **Child route, both hosts.** Pass: the harness captures the brief actually sent and detects any
   byte difference from the fixed brief, including a paraphrase of the unit; the host's record of
   the child's effective context is found and names the cell's compiled artifact, or the probe
   establishes that the host records none; with an identical brief, a planted unit changes the
   child's behavior relative to the unit in its B state.
4. **Runner acceptance, every adapter** (the Workflow channel, the hermetic Claude runner,
   `codex-run.sh`). One common probe per adapter: it binds `call_id`, schema, packet, and result
   identity; it rejects a refusal, a truncated output, a nonzero exit, a stale receipt, a
   mismatched result hash; it attests the observed model; it keeps failed attempts and their
   usage. Context isolation is shown by effective-context evidence, not by output behavior: each
   adapter must expose what the call actually loaded (the host's own record of loaded instruction
   and configuration sources, or the contents of the isolated configuration home and working
   directory the call was confined to, checked against the declared manifest), and a control that
   loads an undeclared instruction which leaves a valid, canary-free answer must still be rejected
   by that evidence. An adapter that cannot expose effective context cannot serve independent
   judgments; the owner then decides where those judgments run.
5. **Codex capture under the real profile.** `codex-run.sh --profile hermetic` runs `codex exec`
   with `--ephemeral`, which may write no rollout. Pass: the call id, profile, working directory,
   context-manifest hash, observed model, and token counts are captured for that exact invocation
   before cleanup. If the observed model cannot be captured at all, the Codex-side contracts
   cannot meet §3.2 step 2, and the owner decides between accepting requested-only attestation
   for Codex calls with a visible mark and moving those judgments to another provider.
6. **Workflow persistence.** Pass: the driver reads a schema-valid result, its `call_id`, and its
   subagent's observed model and usage from the run's `journal.jsonl` and subagent transcripts
   without the main session retyping it; a failed or truncated subagent is distinguishable.
7. **Reconstruction.** Pass: one R of the current library with both maps, including one
   requirement carried by a route, one carried by a hook script or wrapper patch, and one carried
   by a compiler or installer change (a toy change, for example an extra router line the compiler
   emits), validated by the independent reviewer, compiles into a private release; the R−i of
   each of those three requirements validates; the executable carrier's own tests pass in R, and its
   R−i restores the B-state executable; one actor episode runs on each.
8. **Lineage markers, both hosts.** On deliberately created fresh, resumed, and forked sessions
   (and, for Claude, a compacted continuation), find the metadata that distinguishes them. Pass:
   the markers classify every planted session correctly, and a replay whose timestamps hide its
   ancestry is classified not fresh. If no marker distinguishes fresh sessions on a host, that
   host's sessions have unknown independence (§5.3) and cannot count toward recurrence until the
   design is revised.
9. **Episode accounting.** For each host and each kind of agent-backed dispatch, with long
   outputs, large tool results, compaction, children (and their children where the host allows
   it), automatic retries, and late usage reports. Pass: streamed usage is captured for every
   request including children and compaction; a stop at the declared cap kills the whole process
   tree and no request starts after it; a request whose usage arrives late moves from provisional
   to measured, and one whose usage never arrives stays provisional or unresolved and is reported
   so; and overshoot past the cap is recorded per class, measured or estimated, so the rehearsal
   can set calibrated costs.
10. **Installation receipt.** Pass: after an install, the receipt names the digest of the
    installer code that executed; when an old installer installs a package that contains a new
    installer, the receipt names the old installer's digest, so a session served by that
    installation is not exposed to the new installer; a failed transaction writes no success
    receipt; two installations of the same release by different installer versions, each
    followed by a session, bind each session to its own receipt through the snapshot; a session
    started before a later installation keeps its earlier binding; a snapshot whose recorded
    artifacts do not match its receipt's resulting hashes is rejected as unbound.

## 17. Risks

- The test scale needs new harness machinery (probes 1–3, 7, 9) before the first run; if a probe
  fails for one host, that host's strata cannot run and O7 fails for items claiming them.
- If probe 8 finds no fresh-session marker on a host, that host's sessions cannot count toward
  recurrence, and promotion there rests on single high-consequence events until the design is
  revised. If probe 5 cannot capture Codex's observed model, the owner decides how Codex-side
  judgments are attested (§14).
- Whole-library reconstruction can entangle requirements so that R−i does not isolate an item;
  such items carry unresolved attribution.
- Sessions without an activation pin (today the desktop apps, as S1 measures each run) have no
  selection evidence: "not delivered" cannot be shown for them, and units are diagnosed only where
  other version-bound exposure exists (§6.3); the rest stays unclassified.
- A run's volume (about 1,300–2,360 USD at placeholder rates) may need several usage-limit
  windows, stretching elapsed time to days, and with extra usage left on it may incur charges;
  the first measured run decides whether this scale is sustainable per window.
