## What the canary caught, which is the reason it exists

The first live variant run returned `CANARY_GLOBAL` **and** `CANARY_GUIDE: cli-multi-model-workflow=NOT_FOUND`,
with `GUIDES_OR_REFS_READ: /Users/kangmin/.codex/guides/cli-multi-model-workflow.md`. Neither host
exports its home variable into the agent's tool shell, so a router written
`${CODEX_HOME:-$HOME/.codex}/guides/x.md` resolves to the **deployed** guide from inside a variant
home. Every guide-borne ablation would have changed nothing while the arms reported different
`corpus_hash` values. Fixed by rebinding router references to absolute paths into the variant, which
is uniform across arms and therefore cancels; the pre-fix `NOT_FOUND` pair is the negative control.

Two the panel found independently of each other (correctness and reproduction both filed them),
which is the agreement worth weighting:

- **`corpus_hash` was computed after path rebinding and canary injection**, so two builds of the
  *same* corpus hashed differently. C3's "the arms' hashes differ" was therefore true of identical
  arms — a control that could not fail. Split into `experiment_hash` (after edits, before
  instrumentation) and `realized_hash`.
- **The receipts kept only digests, not the response.** Scoring here is semantic — a human reads
  the words — and `run.py` called the directory "raw receipts". Auditable-looking evidence with
  every preimage discarded. Response and raw host output are now persisted beside each receipt and
  rehashed during validation.
- **An all-defect run exited 0** with `C4 ok` and `validation ok`, because validation only judges
  `ok` receipts. Completeness is a third question; `INCOMPLETE` now fails the run.

The sharpest single finding, from correctness alone: **the guide canary was forgeable.** Its value
was `<token>-<slug>-GUIDE` and the global instruction hands the agent that token, so an agent that
read only the global could synthesise a canary for a guide it never opened. The instrument that
caught this session's first real defect was itself open to a false pass. Each guide now carries an
independent nonce stated nowhere else (D-20260826 below).

Also closed: host `returncode`/`is_error` recorded but never gating (an ok status on a failed
host); malformed JSONL lines skipped silently; `claude-opus-50` accepted as `claude-opus-5`;
a second full-strength model in the reported set accepted; the manifest binding no request digest,
so an opener could be rewritten while every cell key stayed identical; a no-op edit set accepted as
an arm; duplicate scenario ids able to answer for each other; and `is_auth_failure` scanning a
successful response's own text. Security found one: variant homes held a copy of the host
credential **inside the repo tree** and were never deleted — now refused by mechanism (a variant
home may not be built inside a git work tree) and cleaned in a `finally`. Following its boundary

`CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR`, so the agent under test no longer inherits the

**Not applied:** the proposal to require a current-arm guide canary on every `ok` receipt. Whether

## Traps this session paid for

- `timeout(1)` does not exist on macOS; a probe using it returned rc=127 on **both** arms. A uniform
  result across an arm and its inverted control is the instrument, not the finding.
- `security find-generic-password -g` prints the secret. It put an OAuth token, a Meta Ads token and
  two Figma client secrets into this session's transcript. The file's existence answered the
  question; the value was never needed. Rotation was advised.
- **One checkout, two sessions, one index — and it costs an hour, not a retry.** A concurrent
  session's gated `git commit` had been running here since 10:26. This session staged ten paths at
  11:07; the peer found and reset them at 11:11; the hook rejected the run at 11:14, ~48 minutes in.
  Two distinct failures, and the second is the expensive one:
  - *Sweeping.* git re-reads the index **after** the pre-commit hook, so staged paths enter a commit
    the gates never saw. `git add` by name protects other people's untracked files from you (the
    `1acdd65` trap); it does not protect your files from someone else's commit.
  - *Aborting.* The hook materialises the index snapshot **at start** but its git-reading legs read
    the **live** index. `check-package.sh --self-test` copies every `git ls-files` path, so a path
    added mid-run is listed but absent from the snapshot tree — FileNotFoundError, surfacing as
    "self-test missed a planted violation", which names nothing about the real cause. This is the
    same index-vs-snapshot mismatch as the `git add -N` trap in AGENTS.md, reached from another
    session instead of from `-N`.

  So *hold* means **no git command that changes the index's PATH SET**: `git add`, `git reset`,
  `git add -N`, `git commit`. Measured in a throwaway repo (600 tracked files, every one touched
  to force a real stat mismatch), which separates two things that get conflated:

  | command | rewrites `.git/index` bytes | moves the path set |
  | --- | --- | --- |
  | `git status` / `git diff` | **yes**, when stat info drifted | no |
  | creating an untracked file | no | no |
  | `git add <path>` | yes | **yes** |

  Only the right-hand column can abort a hook run, so `git status` is hygiene and `index.lock`
  contention — not the abort. Worth recording because the first version of this entry blamed
  `git status` for the abort on mtime evidence alone, and a peer's reasoning corrected it.

  **And the way that correction nearly went wrong is the reusable part.** The first test used a
  two-file repo: `git status` did not rewrite the index at all, which AGREED with the peer's
  model and would have closed the question — falsely, since the rewrite is real and the small
  repo simply never entered git's refresh-write path. A negative result from an under-scaled
  subject looks exactly like a negative result. Scale the subject until you have seen the
  mechanism fire at least once, then test the claim.

  **Distill candidate (window 3), not captured — capture is `learn!`, which only the user runs.**
  Both sessions independently judged the under-scaled-subject failure worth promoting past this
  trap: it is the existing "agreement is when you test the instrument" learning approached from
  the other side. That one says a result matching your expectation is when to check the probe;
  this one says a result matching your expectation *because the probe was too small to fire* is
  indistinguishable from the real thing. Same selection effect, opposite entry point.

  Working-tree edits are safe (`git ls-files` reads the index, not the tree).

  While another session holds a commit open in this checkout:
  - `git rev-parse --short HEAD` — reads `.git/HEAD`, never the index
  - `git --no-optional-locks status --porcelain` (or `GIT_OPTIONAL_LOCKS=0`) when you must look
  - `ps -eo pid,etime,command | rg "git commit"` for liveness
  - `stat -f '%Sm' -t '%H:%M:%S' .git/index` to see whether anything wrote it

  The structural closure is the hook pinning `GIT_INDEX_FILE` to its own snapshot for every
  git-reading leg, which also folds in the existing `git add -N` trap — same cause, reached three
  different ways. Until then the rule survives only by every future session remembering it, which
  is the kind of rule this repo's own guidance says to replace with a mechanism.
- An f-string cannot contain a bare `}` from a dict comprehension — `{d or 'x'}` with a comprehension
  inside is a SyntaxError, not a formatting bug.
