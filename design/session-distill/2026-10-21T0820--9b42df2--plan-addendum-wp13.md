# Session distill implementation plan: addendum for WP-13

This record settles the readings of `2026-10-20T2119--cc0498f--implementation-plan.md`, work
package WP-13 (ledger schema 2, its migration, the transitions and the state file), that its
review raised twice. The plan, design §12.1–§12.4, §10.6 and §7.2 stand; nothing here changes a
field list or a predicate of the design. What it does is name the properties schema 2 carries
**beyond** §12.1's eight keys, say which code reads each one and why it cannot be dropped, and
fix the line between a decision a run made and an element the migration produced.

Without this record those properties were an implementation's own invention, justified by a
comment in the file that invented them. The plan's own rule — one authority per contract — makes
that a defect, not a liberty.

## 1. A decisions[] element has two shapes, and they are kept apart

Design §12.1 gives the element eight keys: `run`, `disposition`, `approval_id`,
`adjudication_id`, `confirmation`, `applied`, `tests`, `expected_observation`. Those eight are
required of **every** element and nothing is added to the required set.

Design §12.2 then migrates schema 1's history fields into elements of the same array, and gives
those elements metadata §12.1 never names: a date, the raw field name, the raw text. An element
is **legacy** when its `run` begins `legacy-` or its `kind` is one of the legacy kinds below;
anything else is a **run's decision**.

A run's decision carries none of §12.2's metadata, and `LEGACY_FIELD_ON_MODERN` in
`session-distill/runlib/ledger.py` refuses it property by property. The reverse also holds:
`kind: revert` marks a run's decision, and `LEGACY_KIND_ON_REVERT` refuses it on a migrated
element.

The separation is **not** written as a conditional in `session-distill/schemas/ledger.schema.json`,
and not for want of trying. The repository's schema policy (`runlib/validate.py`
`SUPPORTED_KEYWORDS`, which `compile_schema` lints every stage schema against) admits no `allOf`,
`if`/`then`/`else`, `not` or `anyOf`: a schema here states shapes, and conditional structure is a
checker's work. So one `decision` definition serves both shapes, each legacy-only property is
**marked in the schema** with the comment `design §12.2, a migrated element only`, and
`ledger.py`'s `contract_problems` derives its own list of legacy-only properties from those marks
and fails when the two disagree. Adding a property to the schema without its mark, or dropping a
mark, is therefore a named failure of the module's self-test, which is what keeps this record and
the schema from drifting apart.

## 2. The properties beyond §12.1, each with its reader and its reason

| Property | On | Read by | Why it exists |
|---|---|---|---|
| `at` | legacy elements only | `ledger.py` (`LEGACY_REQUIRED`), `migrate-ledger.py` (chronology, the expected records) | Design §12.2: every migrated element "carries `at`, the date parsed from its value or `null`". A run's decision takes its instant from its run, so `at` on one is refused. |
| `field` | legacy elements only | `ledger.py` (`LEGACY_REQUIRED`), `migrate-ledger.py` | Design §12.2: the element carries "the raw field name" it was migrated from. |
| `legacy_text` | legacy elements only | `ledger.py` (`LEGACY_REQUIRED`), `migrate-ledger.py`'s value-preservation rule | Design §12.2: "the raw text in `legacy_text`". It is what makes §12.2's own self-test rule — every legacy field value found in the migrated record — decidable. |
| `status_note` | legacy elements only | `migrate-ledger.py` | Design §12.2's own wording for a retirement with no recorded revival. |
| `kind: legacy_application` | legacy elements only | `ledger.py`, `ledger_compat.py` | Design §12.2 names it for the entries with no place decision (measured: G-5, G-8). |
| `kind: legacy_retirement` | legacy elements only | `migrate-ledger.py` | Design §12.2's "historical retirement element"; the name is this record's, the element is the design's. |
| `legacy_placed` | legacy applications only | `migrate-ledger.py`, `ledger_compat.py` | Design §12.2 migrates `placed` onto the **latest place decision**. When that decision's own date differs from the `placed` date (measured), one element would have to hold two dates: `at` keeps the decision's, `legacy_placed` keeps the application's, and no schema 1 value is lost. |
| `kind: legacy_migration` with `legacy_status` | one element per migrated entry, before any run decision | `ledger.py` (`replays`, `revert_target`) | **The baseline.** Design §12.3 derives a revert's target from the entry's own history. A migrated entry's history begins nowhere: schema 1 recorded a status, never the decisions that reached it. Without a recorded start, the first revert of a run decision on any of today's 142 entries is ambiguous and refused. This element records the status the entry held when the migration ran (`legacy_status`, the schema 1 wording in `legacy_text`, `at` the newest window end of the schema 1 ledger), and that is the one start `replays` tries for such an entry. |
| `kind: revert` | a run's decision only | `ledger.py` (`replays`, `revert_target`, `row_violations`) | Design §12.3's event row "application reverted by the owner — the status before that decision; a revert decision appended". The appended decision needs a mark that distinguishes it from a decision that applies a disposition; it is an applied decision with disposition `none`. |
| `reason` | any element | `ledger.py` (`element_problems`, `effect_problems`) | Design §7.2 asks a `drop` for "a reason naming why the miss is acceptable" and a `keep` under `redundant` or `obsolete` for its reason; §12.3's awaiting-R row records a reason. §12.1's eight keys hold none, so it is an optional property, never a required one. |

Every one of these is **optional**. A ledger whose elements carry exactly §12.1's eight keys
validates, and the self-test holds that case first.

## 3. Two readings of the design the code now encodes

Neither adds a field; both decide how existing contracts compose.

**Application and delivery verification are separate.** Design §10.6 records an item whose
operations completed but whose delivery check failed or did not run as `applied` with delivery
`failed` or `unverified`, "not lost", and leaves the owner to "keep, revert, or revise" it — a
revert is only possible for a decision that took effect. Design §12.3's event row says the
delivery outcome leaves the application "unchanged; `decisions[].applied.delivery` records it".
So an applied decision moves the status and licenses its row changes whatever its delivery
outcome; the delivery event records that outcome and moves nothing further; and such a decision
takes part in the revert derivation like any other. Design §12.2 depends on this directly: it
migrates every placed entry with `delivery: unverified` on its place decision, and §11's reach
metric counts "applied items with delivery verified" against applied items, which presumes the
unverified ones are applied.

**An applied decision licenses the fields its disposition changes, not every field.** Design
§12.3 says a decision that does not change what is installed — an incubated or a dropped
intervention on a placed entry, and `none` against any state — leaves the entry alone. So the
licence a decision carries is per disposition: `none` licenses no field of the entry, an
incubated or dropped intervention licenses neither the entry's text nor its destination, and each
other disposition licenses what §7.2 says it does, widened by exactly what the §12.3 cell's own
effects require. `ledger.py` holds this as data (`DISPOSITION_FIELDS`, `EFFECT_FIELDS`) and
refuses the rest (`UPDATES_UNLICENSED`, `ROW_FIELD_UNLICENSED`).
