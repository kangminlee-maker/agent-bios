## Strength 4

### [S4-01] 쉘 파이프라인의 종료 코드는 마지막 단계만 반영함
- **원칙**: 파이프로 연결된 명령의 종료 코드($?)는 기본적으로 마지막 단계 결과만 반영함. 검증 대상 명령이 앞 단계에 있으면 tail/grep/jq 등 뒤 단계가 성공하는 순간 실제 실패가 은폐되어 거짓 통과(false green)로 읽힘. `set -o pipefail` 적용, `PIPESTATUS` 확인, 또는 검증 대상 명령을 파이프 없이 직접 실행해 종료 코드를 즉시 확보해야 함(단, 마지막 단계 자체가 의도된 검증이면 예외).
- **왜 뽑혔나**: 독립된 두 세션이 동일 실패를 겪었고 한 세션은 두 번 재현됨, 검증 신뢰성의 핵심 전제를 훼손함 · 신규 · ④⑤⑥ · 지지 2건
- **배치**: global CLAUDE.md §Tooling and Operational Safety, 기존 "coarse runtime signal" 불릿 옆 / 규칙 적용 시: 신규 tooling-gotchas 가이드

### [S4-02] grep이 텍스트 파일을 바이너리로 오판해 무응답 반환
- **원칙**: grep의 바이너리 감지 휴리스틱은 NUL 바이트나 비-ASCII 비중이 높은 콘텐츠가 있으면 정상 텍스트 파일도 바이너리로 오판해 매치 없음을 조용히 반환함(에러 없음). 결과가 다른 증거(git diff, 이전 읽기, 동료 보고)와 모순되거나 지나치게 깨끗하면, ripgrep 또는 `grep -a`로 재확인하거나 파일을 직접 읽어야 함.
- **왜 뽑혔나**: 독립 세션 2건 + 각 세션이 인용한 추가 세션들로 4~5건 수렴, 검증/리뷰 결과를 오염시키는 침묵성 오탐 · 신규 · ④⑤ · 지지 2건
- **배치**: global CLAUDE.md §Tooling and Operational Safety, "coarse runtime signal" 불릿 뒤 / 규칙 적용 시: 신규 tooling-gotchas 가이드

### [S4-03] ambient 쉘의 관용구 차이로 인라인 명령이 조용히 오동작 — 매번 확인이 아니라 인터프리터 고정으로 해결
- **원칙**: 기본 쉘은 환경마다 다르고(zsh/bash/dash…) bash 전용 관용구는 다른 쉘에서 에러 없이 다르게 동작함(예: zsh에선 인용 안 된 변수의 단어 분리가 안 되고, `read -r -d ''` 관용구가 조용히 멈춤). 해법은 매 명령마다 쉘을 확인하는 것이 아니라 쉘 정체성을 무의미하게 만드는 것: ① 인라인 한 줄 명령은 POSIX 공통 문법 범위로 작성 ② 쉘 특정 기능(배열, `read -d`, `PIPESTATUS` 등)이 필요하면 ambient 쉘에 맡기지 말고 인터프리터를 명시적으로 고정(`#!/bin/bash` 셔뱅 스크립트 또는 `bash -c '…'`) ③ 세션 환경 정보에 쉘이 이미 선언되어 있으면(예: "Shell: zsh") 추가 비용 없이 그것을 전제로 삼고, 별도 쉘 프로브는 오동작 진단 시에만. *(2026-07-18 사용자 피드백 반영: "항상 zsh" 전제 제거, 매번-확인 비효율 없는 해법으로 재정식화)*
- **왜 뽑혔나**: 독립 세션 2건이 같은 근본 원인(bash/zsh 괴리)의 서로 다른 두 증상(무한 대기, 단어 분리 왜곡)에서 걸림 · 신규 · ④⑤ · 지지 2건

### [S4-04] 종류가 다른 두 검증자가 같은 모델을 공유할 수 있음 — 실제 디스패치 경로 확인 필요
- **원칙**: 전제: 교차검증은 작성자와 리뷰어의 모델(패밀리)이 서로 달라야 성립하며, 비일상적·고위험 판단일수록 다른 모델의 리뷰어로 한 번 더 교차시켜야 함. 이 항목의 학습은 그 전제가 설정·라벨만으로는 보장되지 않는다는 것: "논리/권한" 대 "코드/실행" 리뷰어처럼 종류가 다르다고 표기된 두 검증자를 교차검증에 쓰기 전에, 각각이 실제로 어느 모델/제공자 계정으로 디스패치되는지 라이브 프로세스나 사용량/에러 증거로 확인해야 함. 래퍼나 orchestration 도구가 실제로는 다른 검증자와 같은 provider/model/계정을 공유하면 종류 다양성이 조용히 무너지고 "클린" 결과가 거짓 확신을 줌. 비일상적·고위험 판단(설계 리뷰, 돌이키기 힘든 행동 전 교차검증)에 한정.
- **왜 뽑혔나**: 독립 세션 2건이 서로 다른 계기(레이트리밋 장애, 라이브 프로세스 점검)로 같은 실패를 발견, 교차검증 다양성이라는 핵심 전제를 무력화 · 기존 확장 · ④⑤⑥ · 지지 2건

### [S4-05] diff 기반 리뷰가 스코프 일부(staged/untracked)를 놓칠 수 있음
- **원칙**: git 범위 기반 리뷰/검증 도구의 판정을 믿기 전, 검토 스코프가 완전하고 올바른 대상인지 확인해야 함(단순히 "비어있지 않음"이 아니라). staged/uncommitted 변경은 HEAD 대비 diff 도구에 안 보이고, untracked 신규 파일은 staging 여부와 무관하게 git-diff 계산에서 아예 빠짐(intent-to-add 등 명시적 추적 필요). 도구가 실제로 소비한 대상과 git status를 대조해야 함. **대안(절차)**: ① 리뷰 디스패치 전 `git status --porcelain`으로 subject 전체(스테이지드·언스테이지드·untracked)를 나열 ② untracked 파일이 subject에 속하면 `git add -N`(intent-to-add)으로 diff에 보이게 하거나 WIP 커밋으로 착지 ③ 도구가 실제 소비한 범위(HEAD 대비인지, index/worktree 포함인지)를 확인하고 리뷰된 파일 목록을 ①의 목록과 대조 — 불일치가 남으면 verdict를 불완전으로 취급. git diff 기반 도구에 한정, 전체 스냅샷 스캔 도구는 해당 없음. *(2026-07-18 사용자 피드백 반영: 대안 절차 명시)*
- **왜 뽑혔나**: 서로 다른 세션 2건이 같은 git-diff 사각지대의 다른 두 사례(staged 제외, untracked 비가시)에서 수렴, 크래시 없이 조용히 대상을 놓쳐 크래시보다 발견이 어려움 · 기존 확장 · ③④⑥ · 지지 2건
- **배치**: guides/review-request.md §Read participation before believing a verdict — 참여 건수 체크 옆에 스코프 완전성 체크 확장 / 규칙 적용 시: 기존 가이드: review-request.md

### [S4-06] 모든 비교·측정은 공통 기준으로 정규화하고 비대표 데이터는 제외 — 비용은 한 사례
- **원칙**: 두 대상을 비교해 결론 내리기 전(비용·성능·품질·빈도 등 무엇이든), ① 단위·분모·모집단·측정 표면을 공통 기준으로 먼저 고정하고 ② 원시 합계가 아니라 동등 산출물 기준(반사실적 비용, 수락된 산출물당 비용 등)으로 비교하며 ③ 이상 구간·프로모션/플랜 특가·스모크 슬라이스 같은 비대표 데이터를 식별해 제외하거나 별도 표기할 것. 비용 비교는 이 일반 원칙의 한 사례: 청구 표면·처리 모드·캐시 티어·통화·토큰 단위를 통일하고 input/cache-hit/cache-write/output 요율을 섞지 말 것. *(2026-07-18 사용자 피드백 반영: 비용 한정 → 일반 비교 원칙으로 승격)*

### [S4-07] 스폰한 서브프로세스/핸들의 전체 생명주기를 끝까지 책임질 것
- **원칙**: 서브프로세스(일회성 프로브든 장수 서비스든, 직접 스폰이든 래퍼를 통한 스폰이든)를 만들었으면 실행뿐 아니라 생명주기 전체를 소유해야 함: 스폰 시점에 프로세스 그룹을 세우고, 결과를 획득한 뒤, 종료 시 소유한 stdio 핸들을 닫고 정확히 그 그룹을 종료(래퍼 PID만 죽이지 말 것)하고 exit을 기다려 잔존 자식이 없는지 확인해야 함. unref 안 된 자식 핸들이나 열린 stdin 파이프는 부모의 이벤트 루프를 살려둬 정상 종료할 명령을 멈추게 하고, 래퍼 PID만 죽이면 실제 자식이 orphan으로 남음. 자신이 스폰한 프로세스에만 적용.

## Strength 3

### [S3-01] 명령 이름이 의도와 다른 바이너리로 resolve될 수 있음
- **원칙**: 명령 이름은 고정된 바이너리를 가리키지 않음 — 쉘 함수/alias가 인터랙티브 세션에서 가리고, 먼저 설치된 동명의 PATH 패키지가 시스템 도구를 가릴 수 있음. 인터랙티브 쉘은 보통 함수/alias를 PATH보다 먼저 resolve하지만 프로그래매틱 서브프로세스 스폰은 보통 raw PATH resolution만 해 서로 다른 바이너리가 실행될 수 있음. 결과를 다른 실행 맥락에서 신뢰하기 전(`which`/`type -a` 또는 절대경로 호출로) 실제 resolve 대상과 그것이 맞는 맥락인지 확인해야 함. 하류에 신뢰되지 않는 일회성 명령은 생략 가능.
- **왜 뽑혔나**: 독립 세션 2건이 각각 인터랙티브 shadowing과 동명 패키지의 시스템 도구 가림이라는 같은 메커니즘의 다른 증상에서 걸림, 특히 후자는 조용한 빈 출력으로 위장 · 신규 · ④⑤ · 지지 2건

### [S3-02] 자기 커밋 해시를 기록하는 핸드오프는 자기참조 모순을 만듦

### [S3-04] 병렬 세션의 행위 귀속은 실행 증거로, 텍스트 언급만으론 안 됨

### [S3-05] 베이크된 설정 파일 권한을 컨테이너의 non-root 실행 UID와 대조 확인
- **원칙**: non-root UID로 실행되는 컨테이너 이미지에 파일을 생성·서명·COPY하는 빌드/패키징 단계는, 그 파일이 런타임 UID로 읽을 수 있는 권한인지를 이미지 빌드 체크의 일부로 검증해야 함(첫 라이브 부팅 시가 아니라). 소유자 전용(0600) 기본값으로 출력하는 도구는 root 소유의 non-root 읽기 불가 파일을 이미지에 조용히 굽고, 실패는 컨테이너 시작 시에만 드러남. 도구가 런타임 읽기 가능한 권한(보통 0644)을 내도록 하거나 COPY 후 명시적 chmod를 추가하고, 이를 배포 시점이 아니라 빌드 시점 체크로 넣어야 함.
- **왜 뽑혔나**: 단일 세션 근거지만 실패 형태가 배포를 완전히 막는 고비용·침묵성 결함이고, 서명/코드젠 도구 + non-root 컨테이너를 쓰는 어떤 팀에도 일반화됨 · 신규 · ④⑤ · 지지 1건

### [S3-06] 환경 영향 명령 전, 클라우드 CLI의 활성 프로젝트/컨텍스트가 의도와 일치하는지 확인·고정
- **원칙**: 클라우드/인프라 CLI(gcloud, aws, kubectl, docker context, terraform workspace 등)는 명령 텍스트에 안 보이는 가변 ambient 컨텍스트(활성 프로젝트, 프로파일, 클러스터/네임스페이스)를 갖고 세션 간·무관한 작업 사이에 조용히 드리프트함 — git 브랜치/HEAD 오래됨과 같은 실패 형태지만 blast radius가 더 큼(오배포, IAM 변경, 테어다운). 세션의 첫 환경 영향 명령 전 또는 재개/이전 직후, 활성 ambient 컨텍스트를 의도한 대상과 대조해야 함. 어긋나면 전역 기본값을 다시 맞추지 말고 세션 나머지 동안 모든 명령에 대상을 명시적으로 고정(--project, --profile, --context)해 정정이 슬쩍 풀리지 않게 할 것.

### [S3-08] 되돌릴 수 없는 수집 스위치를 켜기 전, 하류 소비 경로부터 기존 샘플로 증명

### [S3-09] 동시 실행 중인 비동기 잡을 폴링할 땐 'latest'가 아니라 정확한 핸들/id를 고정
- **원칙**: 같은 종류의 잡(리뷰, 빌드, 큐 작업)이 동시에 여러 개 떠 있을 수 있는 상태에서 핸들/id로 폴링할 때, 'latest'/최근 항목 같은 편의 필터로 대상을 resolve하지 말 것. 디스패치 시점에 받은 정확한 id/핸들을 고정해 이후 폴링마다 재사용해야 함 — 'latest' 셀렉터는 동시 실행 중인 다른 잡을 조용히 가리켜 그럴듯하지만 틀린 결과를 낼 수 있고, 내용이 디스패치한 것과 안 맞아야 발견됨. 그 종류의 잡이 한 번에 하나만 떠 있을 수 있는 경우엔 해당 없음.

### [S3-10] 타임스탬프는 비교 전에 파싱 — ISO 문자열 비교는 producer별 정밀도 차이로 순서가 틀림
- **원칙**: 서로 다른 producer/시스템에서 온 타임스탬프를 비교·정렬할 때("최신 우선" 판단 등), 원시 문자열을 비교하지 말고 반드시 실제 datetime 타입으로 파싱한 뒤 비교해야 함. producer마다 정밀도가 다르면(하나는 초 단위, 하나는 밀리초 단위) ISO-8601 타임스탬프의 사전식 문자열 비교는 구두점/길이 차이 때문에 시간순과 다르게 조용히 잘못 정렬됨. 같은 producer에서 나온, 포맷이 보장상 동일한 두 타임스탬프 비교는 범위 밖.
- **왜 뽑혔나**: 단일 세션 근거지만 다중 라운드 검증에서만 발견된 침묵성 데이터 정확성 버그이고, 혼합 ISO-8601 정밀도는 멀티시스템 통합에서 흔히 재발하는 버그 유형 · 신규 · ⑤⑥ · 지지 1건

### [S3-11] allowlist 항목은 런타임 키 공간과 실제로 resolve되는지 확인 — 포맷만 맞으면 부팅은 통과하되 라우트 클래스 전체가 조용히 막힘
- **원칙**: 인가/권한/allowlist 설정 항목이 런타임이 요청 시점에 구성하는 키(그룹화·라우팅된 권한의 복합 키 등)와 일치해야 하는 경우, 스키마 형식 검증만으로 만족하지 말고 부팅·배포 시점에 모든 설정 항목을 실제 라이브 라우트/게이트 키 공간에 대해 resolve하는 체크를 추가해야 함. 형식이 어긋난 항목은 부팅·배포 검증을 깨끗이 통과하면서도 그 클래스의 모든 요청을 조용히 거부할 수 있음 — 형식 검증은 well-formed 여부만 확인하지 런타임 키 네임스페이스에 실제로 resolve되는지는 확인 못 하기 때문. 수정 후엔 config diff나 단위 테스트만이 아니라 명시적 negative/contrast control과 재배포된 시스템을 통한 실제 라이브 end-to-end 호출로 검증해야 함.
- **왜 뽑혔나**: 단일 세션 근거지만 실패 형태가 라우트 클래스 전체 요청을 100% 조용히 거부한 실제 프로덕션 사고였고 배포 체크는 모두 통과했음, 수정법이 재사용 가능한 검증 레시피로 일반화됨 · 기존 확장 · ⑤⑥ · 지지 1건

### [S3-12] 핸드오프/설계 문서의 코드 인용은 드리프트하는 줄번호 대신 안정적 심볼명으로

### [S3-14] 브랜치/버전 테스트 빌드를 프로덕션 데이터로부터 모든 상태 저장소·실제 실행 경로에서 격리
- **원칙**: 로컬로 빌드한 브랜치/버전을 실제 프로덕션·사용자 데이터/상태로 실행하기 전(특히 빌드의 데이터 스키마가 라이브와 다를 수 있으면), 격리를 가정하지 말고 명시적으로 데이터 저장소를 분리하고 그 격리가 앱이 건드리는 모든 상태 저장소(파일, DB, 시스템 키체인처럼 env 오버라이드를 무시하는 OS 수준 저장소 포함)를 실제로 커버하는지 검증해야 함. 또한 선택한 실행 방법이 그 격리 설정을 자식 프로세스에 실제로 전달하는지 확인할 것(일부 GUI 앱 런처는 환경변수를 조용히 떨어뜨림). 스키마/버전 불일치 가능성이 있으면 첫 실행 전 라이브 데이터를 백업하고, 불일치 스키마가 데이터를 그대로 통과시키리라 가정하지 말고 실제 소비 바이너리로 쓰기 동작을 검증할 것 — 알 수 없는 필드를 쓰기 시 조용히 버리는 것은 no-op이 아니라 데이터 손실임.

### [S3-15] 예약된 쉘 파라미터 이름(UID 등)은 값 저장 대신 실제 시스템 콜을 유발할 수 있음
- **원칙**: 라이브·프로덕션 부수효과(계정 생성, 자격증명 처리, 권한 변경)를 일으키는 스크립트/일회성 명령에서 임시 쉘 변수 이름을 고를 때, 쉘이 예약/특수 취급하는 이름(UID, EUID, GID, PPID 등)을 피해야 함. 일부 쉘에서는 이런 이름에 대입하는 것이 값 저장이 아니라 그 이름에 묶인 실제 시스템 콜을 호출함(예: 프로세스의 유효 사용자 id 변경) — 의도한 데이터 저장과 무관하게 권한/프로세스 상태를 조용히 바꿔버림. 명확하고 예약되지 않은 변수명을 쓸 것. 이미 부수효과를 일으키는 명령이 실행된 뒤에야 이런 이름 충돌을 발견했다면, 실수한 대입이 명령을 막았거나 no-op으로 만들었으리라 가정하지 말고 실제 결과 시스템 상태를 직접 검증할 것.
- **왜 뽑혔나**: 단일 세션 근거지만 실패 형태가 라이브 프로덕션 행위 중 침묵성 권한/상태 변경 부수효과였고(관리자 계정이 실수 발견 전 이미 생성됨), 원칙이 모든 예약 파라미터 이름을 쓰는 쉘로 일반화됨 · 신규 · ⑤⑥ · 지지 1건

### [S3-16] 설치/배포 덮어쓰기가 같은 파일에 있던 사용자 데이터를 조용히 파괴 — 배포 소유 상태와 사용자 소유 상태를 분리
- **원칙**: 설정/상태 파일을 전체 덮어쓰기 방식으로 관리하는 설치/배포 단계를 출시·확장하기 전, 라이브 앱이 그 동일 파일에 사용자 생성·커스텀 데이터도 쓰는지 확인해야 함. 그렇다면 향후 모든 재배포가 그 데이터를 조용히 버림. 배포 소유 기본값과 사용자 소유 상태를 별도 파일/레이어로 분리해 로드 시 병합하고, 배포 단계는 자신의 파일만 건드리게 하며, 분리 도입 자체가 데이터를 파괴하지 않도록 이미 공유 파일에 갇힌 사용자 데이터에 대한 1회성 마이그레이션을 추가할 것.

### [S3-17] 백그라운드 잡의 도구 관리 출력 디렉터리는 가비지 컬렉션될 수 있음 — 산출물을 영속적 위치로 복사
- **원칙**: 백그라운드/비동기 잡(리뷰 패스, 벤치마크 실행, 도구 관리 서브프로세스 등)이 리포트/산출물을 그 도구 자체의 기본 temp/cache/output 디렉터리에 쓰면, 그 파일이 현재 존재하더라도 그 위치를 일시적인 것으로 취급해야 함 — 그런 디렉터리는 흔히 세션과 무관한 도구 자체의 주기적/종료 시 정리 대상이기 때문. 세션 후반, 컨텍스트 리셋 이후, 또는 보류·인계된 결정의 증거로 그 리포트를 다시 신뢰하기 전에, 원시 출력을 도구의 정리 루틴이 관리하지 않는 프로젝트 소유의 영속적 위치로 복사·추출해야 함. 도구 관리 임시 저장소에 한정, 이미 프로젝트 소유/영속 경로에 쓰인 산출물엔 해당 없음.

### [S3-22] 업데이트 확인 시 디스크에 설치된 버전과 이미 실행 중인 프로세스의 버전을 구분하라
- **원칙**: 업데이트·설정변경·의존성 버전 변경이 라이브 시스템에 실제로 적용됐는지 확인할 때, 디스크/레지스트리에 설치된 아티팩트 확인에서 멈추지 말고 이미 실행 중인 프로세스의 실제 버전/동작을 직접 확인하거나 재시작·리로드를 강제할 것. 실행 중 프로세스는 재시작 전까지 이전 상태를 그대로 유지하므로 "설치됨"과 "실행됨"은 별개 사실.
- **왜 뽑혔나**: 설치는 됐지만 실행 중 프로세스가 갱신되지 않아 "설치됨=실행됨" 오판 위험, 지지 세션 1건. 기존 확장 · ④⑥ · 지지 1건

### [S3-23] A/B 측정에서 널 결과를 믿기 전에 두 arm이 실제로 다른 처치를 받는지 검증하라
- **원칙**: on/off·A/B 측정에서 널 결과(차이 없음)가 나오면, 두 arm이 측정 대상 메커니즘에서 실제로 다른 처치를 받는지 구조적으로 검증하기 전엔 그 결과를 그대로 받아들이지 말 것. 공유 기본값이나 무조건적 업스트림 단계가 "off" arm에도 이미 "on" 처치를 적용하고 있다면, 겉보기 널 결과는 confound일 뿐임.
- **왜 뽑혔나**: 61쌍 채점의 고비용 측정 끝 널 결과가 두 arm이 실은 같은 처치를 받은 confound였음이 한 턴 뒤 드러난 사례. 기존 확장 · ①② · 지지 1건

### [S3-24] 자기예약 웨이크업은 실행을 보장하지 않는다 — 목표 시각이 지났으면 즉시 실행하라
- **원칙**: 스스로 예약한 웨이크업/리마인더/지연 체크(cron 호출, self-issued sleep-then-resume 등)를 설정한 것 자체를 실행 보장으로 여기지 말 것. 이후 어느 시점에서든 목표 시각이 이미 지났고 약속한 행동이 실행되지 않았다면 다음 wake cycle로 미루지 말고 즉시 실행. 확인은 스케줄 생성이 아니라 행동 자체가 남기는 구체적 증거(산출물, 로그)로.
- **왜 뽑혔나**: 자기예약 웨이크업이 실제로 발화한다는 보장이 없다는 것을 보여준 사례, 지지 세션 1건. 신규 · ②⑤ · 지지 1건

### [S3-25] mutation testing의 빠른 수정-테스트 반복 사이 도구 캐시를 비워라
- **원칙**: mutate → test → restore를 빠르게 반복하는 루프(mutation testing 등)에서 pass/fail 결과를 액면 그대로 믿지 말 것. 많은 테스트/빌드 도구가 mtime/size 기준 컴파일·재작성 캐시를 쓰는데, 동일 타임스탬프 해상도 내 수정은 캐시에 걸려 이전 파일 결과를 재보고할 수 있음. 매 반복마다 캐시를 지우거나 no-cache 모드로 돌리고, 캐시 클리어 직후 baseline(비변형) 케이스가 여전히 통과하는지로 신선도를 확인.
- **왜 뽑혔나**: mutation testing 반복에서 mtime/size 캐시가 stale 결과를 재보고할 수 있음을 발견, 검증 신뢰성을 직접 훼손하는 사안이나 지지 세션 1건. 신규 · ④⑤ · 지지 1건

### [S3-26] 벤치마크를 전체 규모로 돌리기 전 소규모로 ceiling/floor 효과를 점검하라

- **왜 뽑혔나**: eval 규모 확장 전 소규모 calibration으로 ceiling/floor 변별력을 점검하는 단계가 기존 가이드에 없음을 확인, 지지 세션 1건. 기존 확장 · ①⑥ · 지지 1건

### [S3-27] 완료된 작업을 제자리에서 재개/덮어쓰기 하기 전 상태를 스냅샷하라

- **왜 뽑혔나**: 완료된 job을 제자리 재개/덮어쓰기 하기 전 스냅샷이 무손실 복구의 유일한 근거였던 사례, 지지 세션 1건. 기존 확장 · ⑤⑥ · 지지 1건

### [S3-28] 로컬은 통과, CI는 실패할 때 회귀로 단정하기 전 기존 CI 실패 여부부터 확인하라
- **원칙**: 동일한 변경에 대해 로컬은 통과, CI는 실패라면 곧바로 diff가 회귀를 일으켰다고 가정해 깊이 파고들지 말 것. 먼저 같은 CI job이 직전 커밋들이나 base/main의 최신 실행에서도 실패했는지 확인 — 그렇다면 diff 이전부터 있던 실패로, 환경 차이(OS/아키텍처/캐시/툴체인 드리프트/불안정한 외부 의존성) 가능성이 높으므로 그쪽을 먼저 조사.
- **왜 뽑혔나**: CI 실패를 회귀로 오판해 여러 턴·고토큰을 소모한 뒤에야 사전 실패였음을 확인한 사례, 지지 세션 1건. 신규 · ①⑤ · 지지 1건

### [S3-29] 무인 루프가 반복 호출하는 인증 발급 경로에는 캐시/멱등성 가드를 추가하라 (실패 기반 서킷브레이커는 항상-성공하는 부작용을 못 잡음)
- **원칙**: 무인/야간 에이전트 루프를 켜두기 전, 반복 경로상에 인증 토큰 발급 등 "호출할 때마다 항상 성공하는" 실제 부작용 스텝이 있는지 확인할 것. 항상 성공하는 호출은 연속 실패 기반 서킷브레이커에 걸리지 않으므로, 루프 빈도로 실제 부작용(반복 인증 프롬프트 등)이 사용자에게 쏟아질 수 있음 — 해당 경로에 캐시나 멱등성 가드를 별도로 추가.
- **왜 뽑혔나**: 항상-성공하는 인증 발급 호출이 실패기반 서킷브레이커를 통과해 무인 배치 중 실제 인증창 100건 이상을 유발한 사고, 지지 세션 1건. 신규 · ⑤ · 지지 1건

### [S3-30] 세션 간 메모리 인덱스가 읽기 한도를 넘기기 전에 압축하고, 인덱스 전용 상세는 먼저 이관하라
- **원칙**: 세션 간 지속되는 메모리 인덱스(auto-memory MEMORY.md 등)는 읽기 크기 한도가 있고, 한도를 넘으면 이후 세션이 에러 없이 잘린 인덱스를 조용히 받게 됨. 주기적으로 크기를 한도와 비교하고, 한 줄 요약으로 압축하기 전에 인덱스에만 있고 개별 파일엔 없는 상세가 있는지 먼저 확인해 이관한 뒤 압축, 압축 후에는 모든 링크가 살아있고 고아 파일이 없는지 확인.
- **왜 뽑혔나**: MEMORY.md 인덱스가 읽기 한도를 이미 넘긴 상태로 발견돼 인덱스 전용 정보를 이관 후 압축한 사례, 지지 세션 1건. 신규 · ⑤⑥ · 지지 1건

### [S3-31] git diff 두 점(..) 표기는 범위 제외가 아니라 스냅샷 직접 비교다 — 세 점(...) 표기를 merge-base 기준으로 사용하라
- **원칙**: git diff의 두 점 표기(A..B)는 커밋 범위 제외가 아니라 두 시점 스냅샷의 직접 비교 — git log/rev-list의 두 점 표기(공유 히스토리 제외)와 다름. base가 fetch로 최신이어도 merge-base가 target 최신보다 뒤처져 있으면(target에 독립적 커밋이 더 있으면) 두 점 diff(origin/base..HEAD)는 무관한 upstream 변경을 diff에 끼워넣음. PR/리뷰용 diff는 merge-base부터 HEAD까지만 비교하는 세 점 표기(origin/base...HEAD)를 쓸 것 — 두 점 diff가 예상보다 크거나 손댄 적 없는 파일의 삭제가 보이면 이 메커니즘부터 의심.
- **왜 뽑혔나**: git diff 두 점 표기가 git log와 다른 의미(스냅샷 직접 비교)임을 몰라 관련 없는 upstream 변경이 diff에 섞인 사례, 지지 세션 1건. 기존 확장 · ②④ · 지지 1건
- **배치**: global CLAUDE.md Tooling and Operational Safety, 기존 git-fetch 규칙 바로 뒤 / 규칙 적용 시: 신규 tooling-gotchas 가이드 (git diff 두점/세점 문법이라는 도구별 세부 함정)

### [S3-32] 전체 실행 선언 전, 스모크 테스트용 제한 설정이 남아있지 않은지 지우거나 확인하라
- **원칙**: 스모크 테스트로 이미 검증된 작업을 전체 규모로 실행 선언하기 전, 그 스모크 테스트에 썼던 임시 제한(최대 항목 수 캡, 행/페이지/샘플 크기 제한 등 env var/플래그/설정값)을 찾아 지우거나 부재를 명시적으로 확인하는 것을 전체 실행의 전제조건으로 삼을 것. 이런 제한은 에러 없이 남아있어 "전체" 실행이 잘린 슬라이스에서 조용히 성공한 것처럼 보이게 함.
- **왜 뽑혔나**: 스모크 테스트용 제한 설정이 남은 채 "전체 실행"이 잘린 슬라이스에서 조용히 성공한 것처럼 보였던 사례, 지지 세션 1건. 신규 · ⑤⑥ · 지지 1건

### [S3-33] 시크릿을 담은 사용자 설정을 프로비저닝할 땐 파싱-재직렬화보다 원문 구간 추출을 우선하라
- **원칙**: 시크릿·주석을 포함할 수 있는 사용자 기존 구조화 설정(TOML/YAML/INI/JSON)의 일부를 다른 환경/소비자로 프로비저닝할 때, 전체를 객체로 파싱해 일부를 재직렬화하기보다 해당 구간의 원문 텍스트를 그대로 추출할 것. 파싱-재작성은 주석/포맷/시크릿 값을 조용히 누락시킬 위험이 있고 좁은 용도에 새 파서 의존성까지 추가하게 됨. 단, 진짜 구조 변경(병합/키 이름 변경/스키마 마이그레이션)이 필요하면 파서를 쓰는 게 맞고, 실제 도입 전 단일/다중 항목·중첩 서브테이블 등 실제 형태로 슬라이싱 로직을 검증할 것.
- **왜 뽑혔나**: 시크릿을 담은 설정을 파싱-재직렬화하지 않고 원문 슬라이싱으로 프로비저닝해 시크릿/포맷 손상 위험을 피한 사례, 지지 세션 1건. 신규 · ⑤⑥ · 지지 1건
- **배치**: global CLAUDE.md §Coding Guidelines, "최소 실행 경로" 항목 근처 / 규칙 적용 시: 신규 tooling-gotchas 가이드 (파싱-재직렬화 vs 원문 슬라이싱이라는 구체 기법 함정)

### [S3-34] 공유 라이브 설정 파일 편집 후 유실을 단정하기 전, 동시 기록자 여부를 짧은 실시간 관찰로 확인하라
- **원칙**: 다른 라이브 프로세스(동시 실행 중인 다른 에이전트 세션 등)도 쓸 수 있는 공유 상태/설정 파일을 편집할 때, before/after diff 하나만으로 자신의 편집이 유실/손상을 일으켰다고 단정하지 말 것 — 무관한 필드가 동시 기록자의 경합만으로도 바뀔 수 있음. 결론 내리기 전 파일 mtime과 변경한 필드를 짧게 실시간 관찰해 원인을 정확히 귀속시키고, merge/union 작업은 의도한 필드로만 범위를 좁혀 무관한 동시 기록을 덮어쓰거나 오귀속하지 않도록 함.
- **왜 뽑혔나**: 공유 설정 파일에서 동시 기록자의 무관한 변경을 자신의 편집 탓으로 오귀속할 뻔한 사례, 이 세션 자체도 다중 에이전트 환경이라 구조적으로 흔한 상황. 신규 · ⑤⑥ · 지지 1건
- **배치**: global CLAUDE.md §Tooling and Operational Safety / 규칙 적용 시: global 유지 (원인 귀속 전 확인이라는 기존 상황-인지 원칙군과 동일 계열)

### [S3-35] 연결된 클라우드 문서의 정체성을 보존하라 — export-재import가 아니라 네이티브 권한으로 제자리 편집하라
- **원칙**: 기존 연결된 클라우드 문서(라이브 Google Sheet/Doc 등, 바인딩된 스크립트·트리거·권한·보호범위·명명된범위·검증·외부참조를 가진 파일)는 이동 가능한 파일이 아니라 라이브 통합 시스템으로 취급 — 사용자가 명시적으로 사본/export를 요청하지 않는 한 네이티브 권한(connected-document MCP/API)으로 제자리 편집. 쓰기 전에 셀/텍스트 이상의 요소(식별자, 바인딩 스크립트, 트리거, 공유권한, 보호범위, 명명범위, 검증, 인/아웃바운드 외부참조)를 목록화해 조용히 누락되지 않게 하고, 외부 로드 상태(로딩 중/타임아웃/쿼터/권한거부/참조깨짐)는 구분해 하나의 성공/실패로 뭉개지 않게 함.
- **왜 뽑혔나**: export-재import 방식이 연결 문서의 식별자/바인딩 스크립트/트리거/권한을 깨뜨릴 뻔해 네이티브 권한 편집으로 되돌린 사례, 지지 세션 1건. 신규 · ②③⑥ · 지지 1건
- **배치**: global CLAUDE.md §Coding Guidelines 신설 항목, 상세 상태 분류는 guides/mock-realization-boundary.md 또는 연결문서 전용 가이드 / 규칙 적용 시: 기존 가이드: guides/mock-realization-boundary.md

### [S3-36] 진단 프로브 시 프로덕션 데이터 노출을 서버 측 집계로 최소화하라
- **원칙**: 프로덕션 데이터 저장소에 개인정보/시크릿/고객 콘텐츠가 있을 수 있는 진단 프로브를 실행할 때, 원본 레코드를 끌어오기보다 서버 측 구조적 집계(카운트, 타입, 필드 존재 여부, 범위 메타데이터, 해시만)를 기본으로 삼고 원문 페이로드는 로그/프롬프트/트랜스크립트에 절대 넣지 말 것. 프로브는 read-only로 범위를 좁히고, 대상 환경을 명확히 지정하며, 민감 필드는 출력에서 억제하고, 진단 결정 후 임시 프로브 리소스(스크래치 쿼리/임시 테이블)를 삭제.
- **왜 뽑혔나**: 프로덕션 진단 프로브에서 원본 페이로드 대신 서버 측 집계만 노출하는 것이 기존 시크릿 규칙과 다른 방향(수신이 아닌 조회/노출)의 공백임을 확인, 지지 세션 1건. 신규 · ⑤⑥ · 지지 1건
- **배치**: global CLAUDE.md §Tooling and Operational Safety / 규칙 적용 시: global 유지 (기존 시크릿-비노출 규칙과 같은 계열의 일반 안전 원칙, 방향만 반대)

### [S3-37] 시크릿 로테이션 후 마운트뿐 아니라 잠재 볼륨 정의도 확인하라 — 업데이트 API는 교체가 아니라 병합일 수 있다
- **원칙**: 매니지드 서비스/배포 업데이트 API로 시크릿 로테이션이나 마운트 리소스 변경을 호출할 때, 그 호출이 기존 설정을 교체한다고 가정하지 말 것 — 많은 API가 기본적으로 새 정의를 기존 세트에 병합해, 더 이상 아무 것도 참조하지 않는 이전 정의를 그대로 남겨둠. 업데이트 후 최신 라이브 리소스 정의를 다시 읽어 전체 정의 목록과 활성 참조(마운트/바인딩) 목록을 따로 점검하고, 더 이상 참조되지 않는 정의는 명시적으로 제거한 뒤 재확인.
- **왜 뽑혔나**: 시크릿 로테이션 API가 교체가 아니라 병합으로 동작해 참조 안 되는 볼륨 정의가 잠재 노출로 남은 사례, 같은 세션 내 두 번 반복. 신규 · ④⑤⑥ · 지지 1건
- **배치**: global CLAUDE.md §Tooling and Operational Safety / 규칙 적용 시: 신규 tooling-gotchas 가이드 (매니지드 서비스 업데이트 API의 병합vs교체 동작이라는 도구별 함정)

### [S3-38] 발행 후 모든 릴리스 채널을 다이제스트로 검증하라 — 순서는 증거가 아니다
- **원칙**: 릴리스/배포가 동일 아티팩트 세트를 둘 이상의 독립적으로 쓰기 가능한 채널(서명된 매니페스트, 오브젝트 스토리지, 릴리스 호스트, 임베디드 업데이터 등)에 발행할 때, 발행 성공과 업로드 순서를 정확성의 증거로 여기지 말 것 — publish가 성공을 보고해도 채널들은 독립적으로 어긋날 수 있음. 발행 후 매니페스트가 참조하는 모든 오브젝트를 스테이징 원본과 바이트/다이제스트 단위로 검증하고 각 채널을 독립적으로 점검하며(한 채널 상태로 다른 채널을 추정하지 않음), 실제 설치기/업데이터를 기본 탐색 경로로 실행해볼 것. 불일치 채널은 수정 후 전체 검증 매트릭스를 처음부터 재실행.
- **왜 뽑혔나**: 매니페스트/스테이징/릴리스호스트가 모두 일치해도 오브젝트 스토리지 설치기 두 개가 stale 바이트를 조용히 유지했던 사례, 지지 세션 1건. 신규 · ②⑤⑥ · 지지 1건
- **배치**: guides/coding-staged-workflow.md §Verification Menus, 릴리스/배포 행 추가 / 규칙 적용 시: 기존 가이드: guides/coding-staged-workflow.md

### [S3-39] 세션을 채굴할 때는 적극적 출처 증거를 요구하라 — transcript 존재/이력은 관찰이지 오라클이 아니다
- **원칙**: 다운스트림 코퍼스의 증거로 쓰기 전에 저장된 AI 세션 아티팩트를 출처/카테고리로 분류할 때, transcript 존재나 이력 로그 소속, 넓은 메시지 패턴 같은 단일 휴리스틱 신호 하나만으로 소속을 추론하지 말 것. 신뢰 세트로 승격하기 전 적극적 출처 증거와 독립적으로 소싱된 여러 메타데이터 기반 부정 점검을 함께 요구하고, 이력 로그 소속을 포함한 어떤 단일 지표도 그 자체로 오라클이 아니라 교차검증할 관찰 하나로 취급. 모호하거나 상충하거나 출처가 없는 아티팩트는 기본 채택 대신 격리/제외 세트로.
- **왜 뽑혔나**: 단일 휴리스틱(이력 로그 소속)만으로 세션 227건을 채택했다가 195건(약 86%)이 자동화였음이 드러나 규칙을 반복 수정한 사례, 지지 세션 1건. 신규 · ②④⑤⑥ · 지지 1건
- **배치**: 신규 guides/session-mining.md §Provenance Classification (session-mining 파이프라인이 반복될 때만 생성) / 규칙 적용 시: global 유지 (기존 "사용자 제안·이전 진단·리뷰 결과를 사실 아닌 가설로 취급" 원칙과 동일 계열의 구체 사례)

### [S3-40] 어드미션/시작-동시성 제한과 쿼터 소진을 구분하라 — 복구 방법이 다르다
- **원칙**: 동시 세션/프로세스 시작이 실패하기 시작할 때 바로 쿼터 소진으로 단정하지 말 것. 이미 실행 중인 작업은 계속 진행되고 새 동시 시작만 거부되며 지연/직렬화된 시작은 성공하는 신호라면 이는 어드미션/시작-동시성 제한이지 용량 고갈이 아님 — 이 경우 추가 팬아웃을 멈추고 기존 서킷브레이커 하에서 지터를 둬 시작을 분산시키고, 항목별 상태를 보존하며, 낮은 동시성으로 복구를 프로브할 것(재시도 폭주 금지, 쿼터/결제 대응으로 확대 금지).
- **왜 뽑혔나**: 동시 시작 거부를 쿼터 소진으로 오판했다가 사용자가 정정 — 실제로는 어드미션/동시성 제한으로 복구 방법이 달랐던 사례, 지지 세션 1건. 기존 확장 · ②④⑥ · 지지 1건
- **배치**: guides/cli-multi-model-workflow.md §Unattended Batch Safety, 기존 서킷브레이커 항목 옆 / 규칙 적용 시: 기존 가이드: guides/cli-multi-model-workflow.md

### [S3-41] pull 전에 dirty worktree를 보호하라 (경로 중복 점검, ff-only, 파생 산출물 재검증)
- **원칙**: 스테이지/언스테이지/추적되지 않은 변경이 있는 worktree에 원격 변경을 pull하기 전, fetch 먼저 하고 들어오는 커밋들의 변경 경로를 모든 dirty 경로와 대조할 것. 경로가 겹치거나 fast-forward가 안 되면 멈추고 충돌 위험을 먼저 해소(stash, commit, 확인 요청). 겹치지 않으면 fast-forward-only로 pull해 우발적 merge/rebase가 dirty 상태 아래서 히스토리를 조용히 재작성하지 않게 하고, pull 후 기존 dirty 변경이 그대로인지 확인하며, 새로 pull된 파일이 로컬 파생 산출물의 입력이라면 그 산출물을 재생성/재검증.
- **왜 뽑혔나**: dirty worktree에 pull하며 경로 중복·비-ff 병합으로 우발적 히스토리 재작성 위험이 있음을 확인한 사례, 지지 세션 1건. 신규 · ⑤⑥ · 지지 1건
- **배치**: global CLAUDE.md Tooling and Operational Safety, 기존 git-fetch 규칙 바로 뒤 / 규칙 적용 시: 신규 tooling-gotchas 가이드 (pull 시 경로 중복·ff-only라는 git 절차별 함정)

## Strength 2

### [S2-01] 로그 테일 모니터의 숫자 에러코드 정규식은 필드 경계에 앵커링해 부분 문자열 오탐을 피하라
- **원칙**: 스트리밍/테일된 로그 텍스트에서 숫자 에러/상태 코드를 탐지하는 정규식/문자열 매치를 작성할 때, 단순 부분 문자열 검색 대신 필드 경계(공백이나 라벨 키 앞, 다른 숫자와 인접하지 않음)에 앵커링할 것. 같은 줄의 무관한 숫자 필드(타이밍, 바이트 수, id, 포트)가 같은 숫자열을 담을 수 있어, 앵커링 없는 패턴은 조사 시간을 낭비시키거나 장시간 워치의 이벤트-폭주 자동정지를 잘못 유발할 수 있음.
- **왜 뽑혔나**: 로그 텔 모니터의 비앵커 정규식이 무관한 숫자 필드(타이밍/바이트수 등)에 오탐해 조사 시간을 낭비할 뻔한 사례, 지지 세션 1건이라 강도 낮게 책정. 신규 · ④⑤ · 지지 1건
- **배치**: guides/cli-multi-model-workflow.md §Unattended Batch Safety, 로그탐지 정규식 항목 추가 / 규칙 적용 시: 기존 가이드: guides/cli-multi-model-workflow.md

### [S2-02] 처리 로직을 다운스트림으로 옮기는 것과 원본 필드를 버리는 것을 분리하라 — 확인 없이 정보량을 줄이지 마라
- **원칙**: 데이터 수집/로깅/정규화 파이프라인을 가볍게 재설계할 때, (a) 파생/해석 처리를 다운스트림 단계로 옮기는 것과 (b) 현재 소비자가 안 읽는다는 이유로 원본 필드 캡처 자체를 없애는 것을 분리할 것. (a)는 요청된 단순화의 일부로 자유롭게 하되, (b)는 훨씬 위험도 높은 별개 결정으로 사용자의 명시적 확인 없이 진행하지 말 것 — "현재 소비자 없음"은 오늘 안 쓰인다는 증거일 뿐 미래 가치가 없다는 증거가 아니며, 원본 보존은 파생/집계값이 복원 못 하는 재처리 옵션을 지켜줌. 확인 전엔 현재 정보량 유지가 기본.
- **왜 뽑혔나**: "처리를 다운스트림으로 옮기자"는 요청을 "원본 필드를 버려도 된다"로 확대 해석했다가 사용자가 정정한 사례, 지지 세션 1건. 기존 확장 · ②⑥ · 지지 1건
- **배치**: guides/coding-staged-workflow.md 고수준 설계 단계, CLAUDE.md Coding Guidelines "최소 실행 경로" 항목에서 상호참조 / 규칙 적용 시: 기존 가이드: guides/coding-staged-workflow.md

### [S2-03] 기존 구현 실패 사례를 실증 조사 후 카탈로그화하여 설계 반영
- **원칙**: 유사한 기존 구현이 여럿 있는 영역에서 설계할 때는 기억에 의존한 선호가 아니라 실제 선례 조사를 고수준 설계에 포함시킬 것. 병렬 검색/추출 작업으로 대표 사례들을 조사해 각 실패 유형에 이름을 붙여 카탈로그화하고, 그 구체적 실패를 근거로 설계를 결정할 것. 조사 결과는 문서로 남겨 이후 설계 선택의 근거를 추적 가능하게 하되, 비교 대상이 없는 그린필드 설계에는 적용하지 않음.
- **왜 뽑혔나**: Stage 1에 선례조사/실패 카탈로그화 단계가 전혀 없어 공백은 확인되나 근거 세션이 1건뿐. 신규 · ⑥ · 지지 1건.
- **배치**: guides/coding-staged-workflow.md Stage 1(고수준 설계)에 선택적 하위 단계로 추가 제안 / 규칙 적용 시: 기존 가이드 coding-staged-workflow.md 유지.

### [S2-04] 확률적(LLM) 메커니즘은 프로브를 반복해 실패율을 측정 — 1회 실행은 판정이 아님
- **원칙**: 검증 대상 메커니즘 자체가 비결정적(LLM 기반, 샘플링 생성 등)이면 단 1회의 실제 프로브 결과(성공/실패 무관)를 최종 판정으로 삼지 말 것. 하네스 자체를 저비용 대조군으로 먼저 검증한 뒤, 같은 프로브를 여러 번 반복해 성공/실패 비율을 추정하고 이를 근거로 건전성을 판단할 것. 결정적 코드 경로에는 기존의 N=1 프로브 방식을 그대로 적용.
- **왜 뽑혔나**: 기존 N=1 프로브 원칙의 사각지대(비결정적 대상을 결정적처럼 다룸)를 메우는 세부화이나 단일 세션 근거. 기존 확장 · ⑤⑥ · 지지 1건.
- **배치**: global CLAUDE.md §Verification Discipline, 기존 N=1 프로브 불릿 바로 뒤에 추가 제안 / 규칙 적용 시: global 유지.

### [S2-05] 셸 특수문자가 섞인 프롬프트는 CLI 인자 대신 stdin/파일로 전달
- **원칙**: 프롬프트·파일명·콘텐츠 문자열 등 셸 특수문자($, 백틱, 따옴표, 글롭 등)나 특수 접두어처럼 보이는 토큰을 포함할 수 있는 값을 CLI 명령에 넣을 때는 원시 커맨드라인 인자로 직접 삽입하지 말 것. stdin, heredoc, 임시 파일 등을 통해 전달해 셸이 대상 프로세스에 도달하기 전에 값을 확장·글롭·훼손하지 않도록 할 것. 사전에 검증된 정적 리터럴 인자에는 적용하지 않음.
- **왜 뽑혔나**: 셸 안전성 관점의 stdin 사용 근거가 베이스라인에 전혀 없음을 grep으로 확인했고 기법 자체는 일반적이나 단일 세션 근거. 신규 · ⑤⑥ · 지지 1건.
- **배치**: global CLAUDE.md §Tooling and Operational Safety에 추가 제안(스크리너는 Codex 전용 섹션에서 여기로 이동시킴) / 규칙 적용 시: 신규 tooling-gotchas 가이드.

### [S2-06] 여러 작업 트랙이 있을 때 "메모리 확인/다음 할 일"은 모호한 요청으로 취급
- **원칙**: 메모리/핸드오프/상태 인덱스가 여러 개의 독립적인 작업 트랙(다른 저장소·워크트리 등)을 동시에 추적하고 있을 때, "메모리 확인해줘"나 "다음 뭐하지" 같은 맨몸 요청은 모호한 것으로 취급할 것. 가장 눈에 띄거나 최근에 손댄 항목으로 임의로 넘겨짚지 말고 어떤 트랙(저장소/워크트리)을 말하는지 먼저 확인할 것. 추적 대상이 하나뿐이거나 현재 항목이 명시적으로 고정된 경우는 예외.
- **왜 뽑혔나**: 잘못된 트랙에서 여러 턴을 낭비한 실제 사고가 있었으나 단일 세션 근거이며, 기존 핀 고정 핸드오프 규칙에 붙는 한 문장 확장 수준. 기존 확장 · ②④ · 지지 1건.
- **배치**: guides/cli-multi-model-workflow.md의 Sessions, Branches, Worktrees 섹션(기존 핀 고정 핸드오프 규칙 옆)에 추가 제안 / 규칙 적용 시: 기존 가이드 cli-multi-model-workflow.md 유지.

### [S2-07] 팀원의 idle 알림은 결과 보고와 별개 — 결과는 명시적으로 요청
- **원칙**: 팀원/서브에이전트의 idle(유휴) 알림은 결과 보고 여부와 무관한 순수 생존 신호로만 취급할 것. idle이 보고보다 먼저, 나중에, 중복으로, 또는 보고 없이 단독으로 올 수 있으므로 idle을 곧 보고 완료로 넘겨짚지 말 것. idle만 오고 보고가 없다면 조용히 기다리거나 완료로 간주하지 말고 팀원에게 보고를 명시적으로 요청할 것.
- **왜 뽑혔나**: idle과 보고 완료를 동일시해 조용히 대기하는 실패가 한 세션 내 반복 관찰됐으나 교차 세션 근거는 없고, 손실 없이 회복 가능한 중간 강도 이슈. 기존 확장 · ④ · 지지 1건.
- **배치**: guides/cli-multi-model-workflow.md §Delegation Mechanics And Teammate Persistence의 기존 "idle 알림은 가설" 불릿 확장 제안 / 규칙 적용 시: 기존 가이드 cli-multi-model-workflow.md 유지.

### [S2-08] 공유 쿼터 지연은 현재 작업만이 아니라 계정 전체 동시성으로 진단
- **원칙**: 세션/프로세스/계정 간에 공유되는 레이트리밋·쿼터 하에서 간헐적 지연·타임아웃·스로틀링이 발생하면 현재 작업 자체의 동시성만으로 원인을 단정하지 말 것. 실패 시점의 쿼터 전체 동시 사용량을 실패 없던 대조 구간과 비교한 뒤 원인을 지목할 것. 특히 자기 작업의 동시성이 낮은데도 간헐적 실패가 계속되는 경우(형제 세션의 경합 신호)에 적용.
- **왜 뽑혔나**: 공유 쿼터 오귀인 사례 1건에 근거하며, 이미 있는 "거친 신호를 권위 있는 근거로 재검증하라"는 원칙의 구체적 특화. 기존 확장 · ⑤⑥ · 지지 1건.
- **배치**: guides/cli-multi-model-workflow.md §Unattended Batch Safety에 서킷브레이커 불릿 옆 진단 불릿으로 추가 제안 / 규칙 적용 시: 기존 가이드 cli-multi-model-workflow.md 유지.

### [S2-09] 여러 줄로 붙여넣은 CLI 명령이 플래그까지 온전히 실행됐는지 검증
- **원칙**: 연속 표시(줄바꿈 기호) 없이 여러 줄로 붙여넣은 CLI 명령에서 중요한 플래그/인자가 이어지는 줄에 있다면, 전체가 하나의 호출로 대상 프로세스에 도달했다고 가정하지 말 것. 터미널/채팅/클립보드 렌더링이 이를 두 개의 명령으로 조용히 재래핑해 뒤따르는 플래그를 잘라낼 수 있으므로, 실행 후 대상의 실제 상태(부여된 스코프, 적용된 설정값 등)를 직접 확인할 것. 재실행 시에는 한 줄로 합치거나 명시적 셸 연속 문자를 써서 모호성을 없앨 것.
- **왜 뽑혔나**: 여러 줄 붙여넣기가 --scopes 플래그를 조용히 잘라내 인증이 기본 스코프로만 완료된 실제 사고이며, 재현이 어려운 조용한 실패지만 단일 세션 근거. 신규 · ④⑤ · 지지 1건.
- **배치**: global CLAUDE.md §Tooling and Operational Safety에 추가 제안 / 규칙 적용 시: 신규 tooling-gotchas 가이드.

### [S2-10] 구현 전 UI 목업은 실제 프레임워크의 헤드리스 렌더로 증명하고 프로그램적으로 검증
- **원칙**: 구현 전 산출물이 UI/레이아웃 미리보기이고 대상 프레임워크가 헤드리스 렌더·테스트 모드 내보내기·스냅샷 기능을 제공한다면, 설명이나 손그림 목업 대신 그 실제 렌더를 프리뷰 산출물로 사용할 것. 캡처한 렌더의 텍스트/구조/노드 순서 등을 프로그램적으로 검증한 뒤 증거로 제시할 것. 그런 기능이 없는 프레임워크라면 최선의 시각적 대안을 쓰되 실제 렌더가 아님을 명시할 것.
- **왜 뽑혔나**: 헤드리스 렌더 + 프로그램적 검증이라는 구체 요구사항은 기존의 "렌더 후 점검" 원칙을 한 단계 더 좁힌 것이며, 단일 세션·중간 강도. 기존 확장 · ⑥ · 지지 1건.
- **배치**: guides/coding-staged-workflow.md §Stages(Stage 1, 설계 단계 프리뷰)에 추가 제안 / 규칙 적용 시: 기존 가이드 coding-staged-workflow.md 유지.

### [S2-11] 가이드라인이 실제로 모델 행동을 바꾸는지 단계적 적대적 테스트로 검증
- **원칙**: 행동 지침/가드레일이 모델의 실제 행동을 바꾸는지 검증할 때는 모델이 규칙을 암송·설명할 수 있다는 것만으로 만족하지 말고, 단계적으로 확대되는 테스트 배터리로 확인할 것 — (1) 트리거를 명시한 케이스, (2) 아무것도 이름 붙이지 않은 암묵적/위장 케이스, (3) 테스트임을 알아채기 어려운 디컨파운드 케이스, (4) 위험 범주 전체에 효과가 유지되는지, (5) 중립적 프레이밍에서 변수 하나만 격리한 케이스. 고정 배터리를 깨끗이 통과해도 "현재까지 알려진 결함 없음"일 뿐이므로 모델이 바뀔 때마다 같은 배터리를 재실행할 것.
- **왜 뽑혔나**: 기존의 eval/A-B 검증 정신은 있으나 5단계 확대 배터리와 "클린 패스는 무결함 증명이 아니다"는 경고는 부재하며 단일 세션 근거. 기존 확장 · ⑥ · 지지 1건.
- **배치**: global CLAUDE.md §Verification Discipline에 별도 불릿으로 추가하고 claude-prompting.md/gpt-prompting.md의 verification_focus에서 상호참조 제안 / 규칙 적용 시: 기존 가이드 claude-prompting.md/gpt-prompting.md 유지.

### [S2-12] 설계 문서 수정 시 공동 권위로 선언된 미러 섹션(픽스처/컨포먼스)까지 전파
- **원칙**: 설계/스펙 문서가 픽스처 블록, 예제, 컨포먼스 부록 같은 보조 섹션을 어떤 규범적 규칙에 대해 독립적 권위로 명시적으로 선언했다면, 그 규칙의 모든 등장 지점을 하나의 논리적 값이 여러 곳에 복제된 것으로 취급할 것. 리뷰나 수정으로 본문의 규칙을 바꿀 때는 같은 편집 단계에서 공동 권위로 선언된 모든 섹션에 동일 변경을 전파하고, 리뷰 단계에서 전파 완결성 자체(문서가 권위를 주장하는 모든 곳에 반영됐는지)를 명시적으로 점검할 것. 권위가 선언되지 않은 단순 예시 반복에는 적용하지 않음.
- **왜 뽑혔나**: 문서가 스스로 공동 권위로 선언한 섹션 간 동기화 요구라는 패턴은 베이스라인에 이름 붙여진 적 없고, 실제로 1.55M 토큰짜리 고비용 리뷰 라운드를 한 번 더 유발한 사례. 신규 · ①②④ · 지지 1건.
- **배치**: global CLAUDE.md §Documentation Hygiene에 추가하고 §Coding Guidelines의 "근본원인을 권위 지점에서 고쳐라" 불릿과 상호참조, 대안으로 coding-staged-workflow.md §Review Loop도 제안 / 규칙 적용 시: global 유지.

### [S2-13] 커밋/PR 관례는 저장소별로 실제 확인 후 기본 템플릿 적용
- **원칙**: 저장소에 커밋/PR을 만들기 전에, 어테스테이션 트레일러 포함 여부, 커밋 단위/원자성, 커밋-브랜치-PR 워크플로에 대한 그 저장소 고유의 실제 관례를 확인할 것 — 자신의 기본 템플릿을 그냥 적용하지 말고 저장소의 CLAUDE.md/AGENTS.md, 핸드오프 문서, 실제 git log를 확인할 것. 기본 템플릿과 충돌하더라도 저장소 관례를 따르고, 관례는 프로젝트마다 다시 확인할 것(이전 프로젝트에서 이어지지 않음).
- **왜 뽑혔나**: 저장소별 커밋/PR 관례 확인 없이 기본 어테스테이션 템플릿을 그대로 적용하는 문제는 베이스라인에 전혀 없으나, 단일 세션·좁은 범위. 신규 · ③⑥ · 지지 1건.
- **배치**: global CLAUDE.md §Coding Guidelines의 "표면적 변경만 하라... 기존 스타일 유지" 불릿 옆에 새 불릿으로 추가 제안 / 규칙 적용 시: global 유지.

### [S2-14] PR의 "mergeable" 표시는 base 대비일 뿐 — 형제 PR과의 충돌은 별도 확인
- **원칙**: 같은 base를 대상으로 여러 PR/브랜치가 동시에 열려 있을 때, 각각의 개별 mergeable/충돌없음 상태만으로 서로 호환된다고 넘겨짚지 말 것 — 그 상태는 base 대비로만 계산되고 형제 브랜치와는 비교되지 않으므로 개별로는 깨끗해도 서로 충돌할 수 있음. 병합 순서를 정하기 전에 열린 브랜치들의 변경 파일 집합이 겹치는지 명시적으로 diff하고, 순차 병합을 스크래치 머지/리베이스로 시뮬레이션해 플랫폼 상태로는 보이지 않는 교차 충돌을 드러낼 것.
- **왜 뽑혔나**: 개별 PR의 mergeable 표시가 형제 PR과의 충돌을 못 잡는다는 사례이며, 기존 git-fetch/base-range 점검과 인접하지만 새로운 검증 단계. 기존 확장 · ⑤⑥ · 지지 1건.
- **배치**: global CLAUDE.md §Tooling and Operational Safety의 기존 git-fetch/base-range 불릿 뒤에 추가 제안 / 규칙 적용 시: global 유지.

### [S2-15] 반복되는 리뷰 지적은 회귀인지 동일 근본원인의 재발인지 분류 후 패치/재설계 결정
- **원칙**: 반복 리뷰 루프에서 매 라운드 유의미한 지적이 계속 나오면, 계속 반복할지 에스컬레이션할지 정하기 전에 각 라운드의 새 지적을 분류할 것. 직전 라운드의 수정이 유발한 회귀라면 그 증분을 좁혀 계속 반복하고, 사전에 존재하던 동일 근본원인의 새로운 사례(직전 수정에서 비롯된 회귀가 전혀 없는 경우)라면 사례별 패치가 한계에 달했다는 신호이므로 클래스/아키텍처 수준 수정으로 갈지를 정지-후-질문 선택지로 명시적으로 제기할 것.
- **왜 뽑혔나**: 반복 리뷰 지적을 회귀 vs 동일 근본원인 재발로 분류하는 진단은 재설계-지속 정지조건 판단에 직결되나 단일한 2라운드 사례에 근거. 기존 확장 · ②⑥ · 지지 1건.
- **배치**: guides/coding-staged-workflow.md §Stop Conditions에 추가 제안 / 규칙 적용 시: 기존 가이드 coding-staged-workflow.md 유지.

### [S2-16] 리뷰어/서브에이전트는 살아있는 작업 트리에서 격리하고 공유 상태는 재검증
- **원칙**: 커밋되지 않은 변경이 남아있는 작업 트리에 리뷰어/서브에이전트를 붙일 때는, 메인 세션이 실제로 편집 중인 동일한 라이브 트리에 직접 접근시키지 말고 읽기 전용 diff/스냅샷이나 격리된 워크트리/클론을 줄 것. 리뷰어/서브에이전트가 커밋되지 않은 작업이 있는 트리에서 checkout --, reset --hard, stash, clean 같은 파괴적 git 작업을 수행하게 하지 말 것. 리뷰 결과가 편집 도중 상태를 읽어 생성됐을 가능성이 있다면(메인 세션 자신의 임시 되돌리기-복원 프로브 포함), 그 지적이나 "상태가 깨끗이 복원됐다"는 주장을 신뢰하기 전에 현재 트리의 무결성/내용을 독립적으로 재검증할 것.
- **왜 뽑혔나**: 커밋되지 않은 라이브 트리에 리뷰어를 직접 붙였다가 문제가 생긴 실제 사고이며, 후보가 자체 보고한 recurrent_error 근거는 부족해 하향 조정됨. 기존 확장 · ②⑤⑥ · 지지 1건.
- **배치**: guides/cli-multi-model-workflow.md §Delegation Mechanics And Teammate Persistence에 추가 제안 / 규칙 적용 시: 기존 가이드 cli-multi-model-workflow.md 유지.

### [S2-17] 기본 분석 렌즈(예: 보안) 적용 전 시스템의 목적 프레이밍부터 확인
- **원칙**: 보안/최소권한/제한 같은 도메인 기본 분석 렌즈로 시스템을 분석·설계하기 전에, 그 렌즈가 실제로 맞는지 사용자나 시스템의 명시된 목적으로부터 먼저 확인할 것. 일부 시스템은 정보/기능을 널리 퍼뜨리도록 의도적으로 설계되며, 제한적 기본 렌즈를 조용히 들여오면 분석을 통째로 다시 해야 하는 결과를 낳음. 시스템이 제한하려는 것인지 확산/공유하려는 것인지 불분명하면 전체 작성에 들어가기 전에 먼저 물어볼 것.
- **왜 뽑혔나**: 사용자가 두 차례("보안 관점이 아니라 정보 공유 관점으로") 강하게 정정해야 했던 프레이밍 재작업 사례이며, 원칙 자체는 널리 일반화되나 단일 세션 근거. 신규 · ② · 지지 1건.
- **배치**: global CLAUDE.md §Decision Framing의 "사용자 제안을 목표 적합성 등으로 평가한 뒤 구현 계획화" 불릿 옆에 추가 제안 / 규칙 적용 시: global 유지.

### [S2-18] 검증/게이트 코드는 기대 형태를 단언하고 실패 시 크게 알릴 것 — 관대한 폴백 금지
- **원칙**: 스키마/설정/산출물에서 특정 필드·키·형태를 읽는 검증/감사/게이트 코드를 작성할 때는 기대되는 키/형태를 명시적으로 단언하고 없으면 크게 실패시킬 것 — 그럴듯한 대안 키/형태들을 넘나드는 관대한 폴백(`a || b` 식)을 쓰지 말 것. 체크 코드 내부의 폴백 체인은 대상 구조에 대한 잘못된 가정을 조용히 흡수해, 검사가 정작 방지하려던 그 결함을 놓친 채 계속 통과시킬 수 있음. 여러 형태를 받는 것이 의도된 문서화된 동작인 정상적인 다중 포맷 파싱에는 적용하지 않음.
- **왜 뽑혔나**: `$defs` vs `definitions` 같은 폴백이 검증 스크립트를 조용히 항상 green으로 만든 사례이며, "체크 코드 내부의 폴백"이라는 구체 안티패턴은 베이스라인에 문자 그대로 없음. 기존 확장 · ⑥ · 지지 1건.
- **배치**: global CLAUDE.md §Verification Discipline의 "체크가 예상보다 빠르거나 비어 있으면 실제로 무엇을 훑었는지 덤프하라" 불릿 옆에 추가 제안 / 규칙 적용 시: global 유지.

### [S2-19] 백그라운드 작업의 완료 알림이 지연되면 대상 산출물을 직접 확인
- **원칙**: 백그라운드 작업의 예상 완료 신호(종료 코드, 워처/테일 콜백, 알림 파이프)가 지연되고 있을 때, 프로세스/모니터가 완료를 보고하지 않았다는 이유만으로 아직 진행 중이라고 가정하지 말 것. 프로세스가 실제 작업은 끝냈는데도 살아있고 그 신호를 영영 내지 않을 수 있음(예: 타이머나 열린 연결 같은 닫히지 않은 핸들이 파이프를 못 닫게 막는 경우). 이럴 때는 대상 산출물(존재 여부, 크기 안정성, mtime, 내용)을 직접 확인해 근거로 삼고, 알림 채널과 어긋나면 산출물을 신뢰할 것.
- **왜 뽑혔나**: 타이머 등 닫히지 않은 핸들 때문에 완료 신호가 영영 오지 않는 구체 메커니즘이며, 베이스라인은 반대 방향(유휴/조용함을 실패로 오인)만 예시함. 기존 확장 · ⑤⑥ · 지지 1건.
- **배치**: global CLAUDE.md §Tooling and Operational Safety의 기존 거친 런타임 신호 불릿을 반대 방향(완료됐는데 신호가 안 옴)까지 확장 제안 / 규칙 적용 시: global 유지.

### [S2-20] diff/패리티 하네스는 입력 파이프라인이 실제 호출부와 다르면 거짓 불일치를 낼 수 있음
- **원칙**: diff/패리티나 바이트 비교 하네스가 이동/추출/리팩터링된 코드와 프로덕션 정답 사이의 불일치를 보고하면, 이를 진짜 회귀로 취급하기 전에 하네스가 실제 호출부와 동일한 전처리/정규화 단계를 거쳐 입력을 공급하는지 먼저 확인할 것. 프로덕션 경로가 수행하는 업스트림 변환을 건너뛰는 하네스는 정확히 결함처럼 보이는 거짓 불일치를 만들어냄. 파이프라인 충실도를 확인한 뒤 남는 불일치는 진짜 신호로 취급할 것.
- **왜 뽑혔나**: 검증 실패의 "거짓 양성"(모크·크래시 등)은 베이스라인에 풍부하나, 하네스 자체가 오염되어 거짓 불일치를 내는 반대 방향은 대응 조항이 없음. 신규 · ⑥ · 지지 1건.
- **배치**: guides/coding-staged-workflow.md §Verification Menus(Code 행)에 추가하고 global CLAUDE.md §Verification Discipline의 "그린 체크는 실제 변경 코드를 거쳤을 때만 신뢰" 불릿과 상호참조 제안 / 규칙 적용 시: 기존 가이드 coding-staged-workflow.md 유지.

### [S2-21] OTP/2FA 단계만 정확히 분리해 인계하고 결과는 권위 있는 소스에서 확인
- **원칙**: 필요한 단계가 OTP/2FA, 푸시 승인, 하드웨어 키 확인처럼 에이전트가 구조적으로 제공할 수 없는 대화형 2차 인증을 요구하면, 우회·프록시·대체 자격증명을 시도하지 말고 다른 모든 단계(빌드, 버전 관리, 스테이징, 커밋/태그, 노트)를 미리 준비해 인증 단계 하나만 남긴 뒤 정확한 명령/동작과 함께 그 한 단계만 사용자에게 인계할 것. 사용자가 완료를 보고해도 그 자체로 충분하다고 여기지 말고, 그 동작이 실제로 영향을 미치는 권위 있는 외부 소스(패키지 레지스트리, 배포된 엔드포인트, 계정/결제 기록 등)에서 결과를 확인한 뒤 완료로 선언할 것.
- **왜 뽑혔나**: OTP/2FA 단계만 정확히 분리해 인계하는 절반은 새 내용이나, 결과를 권위 소스에서 재확인하는 절반은 기존 규칙과 겹침. 기존 확장 · ⑤⑥ · 지지 1건.
- **배치**: global CLAUDE.md §Tooling and Operational Safety에 추가 제안 / 규칙 적용 시: global 유지.

### [S2-22] 주요 의존성 업그레이드는 격리된 검증 계층으로, 런타임 결합 패키지는 배포 대상에 고정
- **원칙**: 메이저 버전을 포함해 여러 오래된 의존성을 한 번에 올릴 때는 위험도 순으로 독립적인 계층으로 묶어 각 계층마다 전체 검증 게이트(타입체크/린트/테스트/빌드)를 실행할 것 — 그래야 실패한 계층이 분리되어 그 자체로 되돌릴 수 있고 여러 동시 업그레이드 사이에서 이분탐색하지 않아도 됨. 특정 런타임에 정확성이 결부된 패키지(타입 정의 패키지, 엔진/툴체인 제약, 언어·플랫폼 버전에 묶인 피어 의존성 범위)는 배포 설정에서 확인한 실제 배포 대상 런타임 버전에 고정할 것 — 'latest'나 로컬 개발 머신 버전에 고정해 배포본에서만 깨지는 일을 막을 것.
- **왜 뽑혔나**: 계층별 격리 업그레이드와 검증, 런타임 결합 패키지의 배포 대상 고정이라는 구체 기법은 베이스라인에 없으며, 실제로 메이저 버전 비호환 2건을 잡아낸 사례. 신규 · ⑥ · 지지 1건.
- **배치**: global CLAUDE.md §Coding Guidelines의 "위험하거나 행동을 바꾸는 작업은 기본값-꺼짐 경로 뒤에 두라" 불릿 근처에 새 불릿으로 추가 제안 / 규칙 적용 시: global 유지.

### [S2-23] Read 도구는 NUL/비출력 바이트를 공백으로 렌더링 — 바이트 단위 검증 필요
- **원칙**: 파일 뷰어/읽기 도구의 렌더링된 텍스트는 NUL 같은 비출력 바이트를 눈으로는 진짜 공백과 구분되지 않는 빈 칸으로 조용히 정규화할 수 있음. 구분자 문자, 인코딩, 바이너리(유사) 콘텐츠처럼 정확성이 바이트 단위 일치에 좌우되는 경우, 도구의 렌더링된 화면을 신뢰하지 말고 hexdump/od나 원시 바이트를 비교하는 스크립트로 검증할 것. 바이트 일치가 중요하지 않은 일반적인 산문/코드 읽기에는 적용하지 않음.
- **왜 뽑혔나**: Read 도구가 NUL 바이트를 육안으로 구분 안 되는 공백으로 렌더링한다는 사실은 베이스라인에 전혀 없던 구체적 도구 결함이며, 바이트 단위 우회 검증법도 명확. 신규 · ④⑤⑥ · 지지 1건.
- **배치**: global CLAUDE.md §Tooling and Operational Safety의 "실물/설치된 아티팩트로 실증 확인하라" 불릿 바로 뒤에 추가 제안 / 규칙 적용 시: 신규 tooling-gotchas 가이드.

### [S2-24] 고정 버전 경로가 박힌 플러그인/설정은 조용한 실패의 징후로 인식
- **원칙**: 이전에 잘 작동하던 연동(상태줄, 훅, 플러그인 명령 등)이 설정은 되어 있는데 아무 효과도 내지 않는다면 조용한 고장 신호로 취급하고, 그 명령 경로에 하드코딩된 절대 버전 문자열이 박혀 있는지 확인할 것 — 플러그인/도구 자동 업데이트나 수동 설정 통합이 에러 없이 이런 경로를 매달린 채로 방치하는 경우가 흔함. 설정을 하드코딩된 버전 문자열 대신 안정/최신 심볼릭 링크나 버전 조회 명령으로 현재 설치된 버전에 연결되도록 할 것. 버전을 하드코딩해야 한다면 해석된 경로가 실제로 존재하고 명령이 실행되는지 확인한 뒤에야 연동이 고쳐졌다고 선언할 것.
- **왜 뽑혔나**: 베이스라인은 "버전을 실증 확인하라"는 일반 규칙만 있고, "조용한 무효과 + 하드코딩된 버전 경로"라는 구체 진단 신호와 심볼릭링크 선호 교정책은 없음. 기존 확장 · ③④ · 지지 1건.
- **배치**: global CLAUDE.md §Tooling and Operational Safety의 "실증 확인" 불릿 확장 또는 그 바로 옆 새 불릿으로 추가 제안 / 규칙 적용 시: global 유지.

### [S2-25] 모델 가용성·라우트 활성화·인증은 서로 독립된 상태로 보고
- **원칙**: LLM 모델이나 다른 플러그인형 런타임 기능의 목록/현황을 보고할 때는 레지스트리 등재 여부, 라우트/접근 권한, 실제 설정된 소비, 조건부·미배선 소비, 인증/검증 근거를 서로 독립적으로 검증된 별개의 사실로 진술할 것. 가용성만으로 인증을 추론하거나 인증 부재만으로 가용 불가를 추론하지 말 것. 인증을 주장할 때는 그것이 정확히 어떤 단위(역할별, 파이프라인별, 호출 지점별 등)를 커버하는지 명시하고 전면 커버리지를 암시하지 말 것.
- **왜 뽑혔나**: 가용성과 인증을 혼동해 결론을 번복해야 했던 실제 사례이며, 교정된 프레임은 널리 일반화되나 단일 세션 근거. 기존 확장 · ②⑥ · 지지 1건.
- **배치**: guides/llm-capability-boundary.md §Capability Surface에 추가 제안 / 규칙 적용 시: 기존 가이드 llm-capability-boundary.md 유지.

### [S2-26] 저장소 전용 도구는 프로젝트-로컬 고정 설치가 기본값, 스코프 이전은 양방향 검증
- **원칙**: 하나의 저장소에서만 쓰이는 CLI/개발 도구는 머신 전역 설치 대신 프로젝트-로컬 고정 설치(락파일과 함께 의존성으로 선언, 설치 디렉터리는 gitignore)를 기본값으로 할 것 — 전역 설치는 여러 프로젝트에서 의도적으로 공유하는 도구에만 남겨둘 것. 기존 도구의 설치 스코프를 전역↔로컬로 이전할 때는 양방향을 독립적으로 검증할 것 — 이전 경로가 더 이상 해석되지 않음과 새 경로가 고정된 버전으로 해석됨을 각각 확인하고, 어느 한쪽에서 다른 쪽을 추론하지 말 것.
- **왜 뽑혔나**: install-scope/global-local/lockfile 관련 언어를 전체 코퍼스에서 grep했으나 전혀 없음을 확인한 진짜 공백이나, 단일 세션·중간 비용 사례. 신규 · ②⑥ · 지지 1건.
- **배치**: global CLAUDE.md §Tooling and Operational Safety에 추가 제안 / 규칙 적용 시: global 유지.
