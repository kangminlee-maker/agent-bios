## Findings (as filed, after refutation)

### 1. HIGH — Principles review-floor prerequisite versus §1 Method descriptor and §4 grading

**Claim.** The design states that same-model/same-effort review is a real floor only with isolation plus “two or more distinct perspectives.”

**Conflicts with.** §4 applies `otherwise -> perspective_floor` to every method row without a perspective-count condition, while §1 imposes the two-perspective minimum only on the reserved `panel`; generic methods permit one trial and have no stated minimum number of perspectives. The implementation follows the unconditional rule: `launch/agent-launch.py:parse_review_method` accepts generic methods with zero or one perspective, and `launch/agent-launch.py:independence_grade` returns `perspective_floor` solely from the seat comparison.

**Consequence.** A capability-backed method with zero or one lens, running on the same model at equal or lower effort, is reported `OK/perspective_floor` and can contribute the plan’s best grade even though it does not meet the design’s own condition for being review at that floor.

**Why it survived refutation.** The contradiction is real and no Correction resolves it. The Principles make the same-model/same-effort floor conditional on isolation plus at least two requested perspectives, and §1 mechanically enforces that condition only for the reserved `panel`. Generic methods may omit `perspectives` or provide one and may use one trial. Nevertheless, §4 defines `otherwise -> perspective_floor` for the per-method grading function without examining method controls. The implementation follows §4 literally: `parse_review_method` permits those generic descriptors, `_resolve_one` calls seat-only `independence_grade`, and the resulting row is `OK/perspective_floor`; non-dropped row grades are also included in the `best_grade` calculation. The parity fixtures explicitly exercise one-perspective, one-trial generic methods, confirming this is supported behavior rather than merely hypothetical invalid input. C20's same-seat `perspective_floor` decision concerns the mandatory base, which is always the multi-perspective `panel`, so it does not authorize this treatment for generic methods. The mandatory base means such a generic row cannot by itself raise the plan above the floor—the base already supplies at least that grade—but that moderates impact rather than removing the false per-method `OK/perspective_floor` classification or its participation in the summary.

### 2. MEDIUM — Goal and corpus mandate versus §1 panel aggregation default

**Claim.** The Goal adopts the corpus rule that different-lens divergence is expected signal and reviewers must “act on the union.”

**Conflicts with.** §1 makes `majority` the reserved panel’s default aggregation, and `launch/agent-launch.toml:[review_methods.panel]` selects `aggregation = "majority"`. The design never qualifies majority as applying only to duplicate verdicts while preserving the union of findings.

**Consequence.** Someone implementing the declared aggregation literally can suppress a defect reported by only one perspective—or even produce a clean majority—when that minority divergence is exactly what the governing union rule says must be retained and acted on.

**Why it survived refutation.** The contradiction is real as a current design ambiguity. The Goal adopts the governing rule that different-lens divergence is signal and requires acting on the union, while §1 makes `majority` the panel default without defining what is voted on or requiring minority findings to survive. No Correction resolves this. The implementation confirms there is no hidden qualification: `launch/agent-launch.toml` sets the panel to `aggregation = "majority"`, while `render_review_method` neither projects `method.aggregation` nor offers an `{aggregation}` slot; the reviewer is merely told to “aggregate.” Majority voting could coexist with union-of-findings if it applied only to duplicate verdicts, but that distinction is unstated, so an equally literal implementation may majority-filter findings or return a clean majority. That would discard exactly the single-lens divergence the Goal says must be retained and acted on.

### 3. MEDIUM — Goal versus §1 Capability operations and Decided question Q1

**Claim.** The Goal says the limiting factor should be which reviewers a user can actually reach, and adds that because interface and method are degrees of freedom, “anything reachable can be registered.”

**Conflicts with.** §1 restricts registrations to core-owned adapter tags and says adding an interface is a core change; Q1 explicitly places a reachable tool out of scope when its protocol cannot be expressed declaratively.

**Consequence.** A user who can reach a reviewer through an unsupported protocol is still blocked until this repository ships new core code. The effective limit therefore remains partly the interfaces the repo happened to ship, contrary to the design’s stated success criterion.

**Why it survived refutation.** The contradiction is real. The Goal is unconditional and explicitly treats interface as a degree of freedom: the limiting factor should be what the user can reach, and “anything reachable can be registered.” But §1 defines a closed, core-owned adapter set and says a new interface requires a core change, while Q1 excludes tools whose protocols cannot be represented by that declarative surface. The implementation confirms this is a substantive boundary: `REVIEW_ADAPTERS` contains only four tags, `parse_capability_offers` rejects every other tag as “not a core adapter,” and the parity gate deliberately asserts that an unsupported tag is rejected. Its unknown-method canaries only demonstrate that a new method can reuse an already shipped adapter, not that a reachable reviewer using a new protocol can be registered. No Correction C4–C23 revises this boundary; Open evidence item 2 instead acknowledges that real third-party protocols may exceed the declared tags. Thus such a reviewer remains blocked on repository core work, so the stated consequence follows and the absolute Goal is not presently satisfied.

### 4. HIGH — §4 receipt requirements and §5 stage 7 versus implemented receipt schema

**Claim.** §4 requires adapter-owned receipts containing both plan and method IDs and a process/request identifier that proves a fresh dispatch; §5.7 says wrong-plan and same-context receipts cannot mark independence achieved.

**Conflicts with.** `launch/agent-launch.py:RECEIPT_KEYS` has `method_id` but no `plan_id` and rejects unknown receipt keys. `launch/agent-launch.py:_receipt_reason` treats any non-empty `dispatch_id` as sufficient unless it equals the caller-supplied main ID or duplicates another ID in the same bundle; `launch/agent-launch.py:verify_review_receipts` performs no plan-identity or adapter-provenance check. `gates/check_parity.py:launcher_receipts` exercises this using locally generated arbitrary strings as dispatch IDs.

**Consequence.** A receipt from another execution of the same packet and seat—or a hand-authored JSON record with fresh-looking strings—can be credited to the current report and move `achieved_grade` away from unknown. The implementation therefore cannot establish the plan binding or fresh adapter-owned dispatch that the design says is required before independence is achieved.

**Why it survived refutation.** The contradiction is real and no Correction resolves it. §4 requires adapter-owned receipts bound to both the plan and method, with a process/request identifier that proves a fresh dispatch; §5.7 requires wrong-plan and same-context receipts not to establish achievement. The implemented ReviewReceipt/v1 schema has no plan_id, and ReviewPlan/v1 has no plan identity to compare. `_receipt_reason` accepts any non-empty `dispatch_id` unless it matches the bundle-supplied `main_dispatch_id` or another receipt in that same bundle; both the dispatch IDs and main ID are unauthenticated caller-supplied strings. It also has no adapter identity, signature, trusted producer channel, or lookup of an actual process/request, so `verify_review_receipts` cannot distinguish adapter-produced evidence from hand-authored JSON or establish freshness. `launcher_receipts` confirms the gap rather than closing it: its happy path manufactures arbitrary packet, result, main-dispatch, and per-method dispatch strings locally. Thus a receipt from another compatible execution—or fabricated data matching the selected method's projected seat and the bundle's self-declared packet hash—can be accepted and move `achieved_grade` away from `UNKNOWN_UNTIL_RECEIPTS`, without proving current-plan binding or a fresh isolated adapter dispatch.

### 5. HIGH — §1 Seam — Registry isolation and mechanism derivation; §3 Gate

**Claim.** The design says registry data may never assert isolation because isolation, exact binding projection, safe tokenization, and read-only dispatch are guaranteed by core adapters; deriving only those adapters allegedly makes a tool that needs the designing context “structurally inexpressible.”

**Conflicts with.** The implementing seam does not contain adapter codecs that establish those properties. launch/agent-launch.py:REVIEW_ADAPTERS maps tags only to descriptive strings; parse_capability_offers accepts a registry-authored tag; derive_review_mechanism copies that tag and the capability command into a ReviewMechanism; _resolve_one treats membership in the same tag dictionary as core attestation; and render_review_method merely interpolates the command into author-authored prose. project_args registers an MCP command or injects that prose into the main session, but does not itself dispatch the review command in a fresh, read-only, exactly pinned process. gates/check_parity.py:launcher_review_contract demonstrates the premise failure directly: an arbitrary shell file containing only `exit 0` is declared `mcp-stdio-v1` and accepted as the unseen-reviewer canary without proving an MCP protocol, a fresh context, read-only execution, or delivery of the bound seat. gates/capture-review-goldens.py uses the same fake-endpoint shape.

**Consequence.** A locally registered capability can select a core-looking tag for a stateful, same-context, non-read-only, or seat-ignoring command and receive an OK independence row and projected provider/model grade. Someone building on the asserted “I2 by construction” invariant will therefore treat an author assertion encoded as an adapter tag as core evidence, allowing the design’s hard definition of review to be bypassed silently.

**Why it survived refutation.** The contradiction is real. §1 and the Synthesis explicitly decide that registry data cannot assert isolation, that adapters are core-owned protocol codecs guaranteeing fresh context, exact binding, safe dispatch, and read-only execution, and that opaque tools such as onto/ultracode are only evidence sources unless a core adapter independently attests their reviewer. The implemented seam does not provide that attestation: parse_capability_offers accepts a locally authored adapter tag; derive_review_mechanism copies that tag and the registry command; _resolve_one treats membership in REVIEW_ADAPTERS as sufficient I2 evidence; and render_review_method turns the binding and command into instructions for the designing session. project_args registers an MCP server or carries those instructions in the main contract, but does not wrap the capability in a core-controlled reviewer dispatch that enforces the claimed properties. The launcher_review_contract canary confirms the trust-boundary error: an executable containing only `exit 0` is labeled `mcp-stdio-v1` and receives an OK, provider-graded row without demonstrating MCP behavior, isolation, read-only execution, or consumption of the bound seat. The golden harness uses the same fake endpoints. No authoritative Correction resolves this. C4 only confirms that this path was wired live; C8 actually acknowledges that a false capability `hosts` claim resolves successfully because a derived invariant cannot detect a lie in registry data, then pins only the shipped ultracode declaration. Open evidence #1 and #2 also leave verifier identity/isolation and real adapter expressiveness unsettled. Reporting availability as `projected` and achievement as `UNKNOWN_UNTIL_RECEIPTS` avoids claiming that review completed, but it does not cure the false launch-time claim that I2 was core-attested by construction. Therefore a locally registered command can obtain the asserted isolation row and projected independence grade solely by selecting a trusted-looking tag, so the stated consequence follows.

### 6. MEDIUM — §1 Method descriptor; §3 asserted parity

**Claim.** A required severity_map is supposed to be total over an external reviewer’s severities; an unmapped severity makes the result malformed and cannot produce a clean verdict, and §3 says the gate asserts that severity maps are total.

**Conflicts with.** The descriptor contains no declaration or authoritative source for the external severity domain, so totality is not decidable from the proposed data. launch/agent-launch.py:parse_review_method accepts any non-empty map whose values lie on the canonical ladder; it neither knows nor checks all severities the tool can emit. gates/check_parity.py:launcher_review_methods treats a canary map containing only `CRITICAL` and `WARN` as valid and its malformed cases test only an empty map or an off-ladder target. ReviewMethod stores the map, but render_review_method, review_plan_v1, and the receipt verifier carry no fact that could establish its source domain.

**Consequence.** A reviewer that can also emit, for example, `ERROR` or `NOTICE` is selectable and passes parity with those severities unmapped. An implementer relying on the design’s claimed static totality has no basis for recognizing the omission, so a real finding can be unnormalizable or discarded while the method remains eligible to produce what appears to be a clean canonical review.

**Why it survived refutation.** The contradiction is real and no Correction C4–C23 resolves it. §1 defines totality over the external reviewer’s severity domain and says an unmapped value must make the result malformed; §3 claims the gate asserts that property. But the descriptor declares only `severity_map` and `output = "review-v1"`, with no source-domain enum or authoritative schema against which totality can be decided. `parse_review_method` checks only that the map is non-empty and that each target is on the canonical ladder. More decisively, `launcher_review_methods` intentionally accepts the unseen-method canary with only `CRITICAL` and `WARN`, while its negative cases cover only an empty map and an off-ladder target. The map is then merely stored on `ReviewMethod`; it is not carried into `ReviewPlan/v1`/`ReviewReport`, and `verify_review_receipts` accepts any non-empty `result_sha256` without inspecting result severities before marking the method achieved. Thus a reviewer whose real domain also includes `ERROR` or `NOTICE` remains selectable, passes the claimed parity gate, and can receive achievement credit although the system has no static or receipt-time basis for establishing that its findings are normalizable. That directly contradicts the design’s asserted totality and fail-closed guarantee.

### 7. MEDIUM — Principles — same-seat review floor; §4 Independence report

**Claim.** The design states that same-model/same-effort isolation is a real review floor only when combined with two or more distinct perspectives, and names the bottom grade `perspective_floor`.

**Conflicts with.** The design also admits that genuine perspective diversity cannot be machine-forced and that unique labels do not prove it. More concretely, launch/agent-launch.py:parse_review_method enforces two perspectives and two trials only for the reserved panel; every optional or user method may have zero or one perspective and one trial. independence_grade nevertheless returns `perspective_floor` solely from seat equality, without receiving the method, and _resolve_one applies that grade to every method. The shipped launch/agent-launch.toml ultracode descriptor itself has one perspective (`orchestration`) and one trial, showing this is a reachable descriptor shape rather than a hypothetical malformed input.

**Consequence.** A same-seat, single-pass custom method is reported as satisfying the perspective review floor even though the condition used to justify that floor is absent. Someone consuming per-method rows or coverage will count ordinary isolated self-review as the corpus’s distinct-lens minimum, overstating review discipline precisely on the fallback path where model independence supplies no other protection.

**Why it survived refutation.** The contradiction is real and no Correction resolves it. DESIGN.md Principles conditions the same-model/same-effort floor on isolation plus at least two distinct perspectives (lines 61–67), and §1 makes the mechanically checkable panel constraints explicit: the reserved panel requires at least two perspective labels and two trials (lines 172–181). But §4 assigns `perspective_floor` in the unconditional final branch of a purported per-method grading rule (lines 297–312), even though that branch has no method/perspective/trial condition. The implementation confirms the current decision rather than narrowing the issue: `parse_review_method` enforces the two-perspective/two-trial minimum only when `method_id == "panel"` (`launch/agent-launch.py:710–737`), while `_resolve_one` calls `independence_grade(binding, main)` for every method and that function returns `perspective_floor` solely from seat comparison (`:909–967`). `ReviewPlan/v1` then exposes that grade on each method row without exposing perspectives or trials (`:1097–1129`), and receipt adjudication can credit such a row at that grade (`:1211–1258`). The shipped ultracode descriptor demonstrates reachability with one perspective and one trial (`launch/agent-launch.toml:76–88`). The admission that genuine diversity cannot be machine-proved does not resolve this: the design separately says the requested mechanical controls are checkable and uses them to justify the floor. Although every composable plan also has a qualifying base panel, that prevents the whole plan from lacking the floor; it does not make the optional method’s per-method `perspective_floor` label true. A consumer of the per-method row or its accepted receipt can therefore over-credit an isolated single-pass same-seat method.

### 8. HIGH — §3 canonical `ReviewPlan/v1` and §4 receipt identity; `launch/agent-launch.py:review_plan_v1`, `review_plan_from_v1`, `RECEIPT_KEYS`, `_receipt_reason`; `gates/check_parity.py:launcher_review_contract`, `launcher_receipts`

**Claim.** The design says the contract carries a canonical `ReviewPlan/v1` that round-trips to the typed plan, and that a valid receipt identifies the plan and method and hashes the reviewed packet; §5.7 specifically requires a wrong-packet receipt to be unable to mark independence achieved.

**Conflicts with.** `review_plan_v1` accepts a `ReviewReport`, serializes report rows, and `review_plan_from_v1` returns a `ReviewReport`; the parity gate correspondingly asserts `restored != report`, not a round-trip to `ReviewPlan`. The record contains neither a plan id nor a packet hash. `RECEIPT_KEYS` also contains no plan id, and `_receipt_reason` compares `receipt.packet_sha256` only with `bundle.packet_sha256`—a value supplied by the same receipt bundle—not with anything committed by the plan. `launcher_receipts` tests only a receipt hash changed independently of the bundle hash.

**Consequence.** A bundle and all its receipts can name the same arbitrary hash for an unrelated packet and still mark the captured plan `ACHIEVED`. The supposed plan artifact cannot establish what was reviewed, so a consumer relying on the design's receipt semantics can credit independent review of different work.

**Why it survived refutation.** The contradiction is real. §4 requires adapter-owned receipts to identify both the plan and method and to hash the reviewed packet, while §5.7 requires a wrong-packet receipt to be unable to establish achievement. No Correction through C23 relaxes those requirements. Yet `ReviewPlan/v1` contains no plan ID or packet hash, `RECEIPT_KEYS` contains no plan ID, and `_receipt_reason` compares each receipt’s `packet_sha256` only with `bundle.packet_sha256`. Because both values come from the same submitted receipt bundle, changing the bundle hash and every receipt hash together is accepted; `launcher_receipts` tests only a receipt/bundle mismatch and therefore misses this coordinated substitution. With otherwise matching method/seat fields and valid dispatch/result evidence, receipts for an unrelated packet can mark the report `achieved`. The §3 mismatch also exists: `review_plan_v1` serializes a `ReviewReport`, `review_plan_from_v1` returns a `ReviewReport`, and the gate compares the restored object to `report`, not to the typed `ReviewPlan`. C4/C5 discuss wiring and a formerly vacuous round-trip assertion but do not explicitly overturn the canonical typed-plan or receipt-identity decisions. Thus the artifact cannot establish which planned packet was reviewed, and the stated consequence follows.

### 9. HIGH — Principles mechanical exception, §1 Method descriptor, and §4 receipts; `launch/agent-launch.py:ReviewMethod`, `render_review_method`, `review_plan_v1`, `_receipt_reason`, `verify_receipts_command`; `gates/check_parity.py:launcher_review_methods`, `launcher_receipts`

**Claim.** The design makes `trials`, `order`, `swap_augmentation`, and `aggregation` the method's trial policy, says randomized ordering being requested is mechanically checkable, and requires receipts to prove the requested panel controls.

**Conflicts with.** Although `ReviewMethod` stores all four fields, `render_review_method` projects only `trials` and `perspectives`; `ReviewPlan/v1` carries none of the four. `order`, `swap_augmentation`, and `aggregation` have no operational reads after parsing. `_receipt_reason` instead requires both an ordering seed and swap group whenever `required_passes > 1`, irrespective of whether the descriptor says `order="fixed"` or `swap_augmentation=false`, and it never checks aggregation. `verify_receipts_command` recovers only `trials` by reloading the current registry, not from the launched artifact.

**Consequence.** A method authored as fixed-order, no-swap, union aggregation is audited as though randomization and swapping were required, while a method requesting randomized, swap-augmented majority review never communicates or proves those requirements. Registry changes after launch can also change whether the same receipts pass. Builders therefore cannot rely on the descriptor to preserve the requested review discipline.

**Why it survived refutation.** The contradiction is real and no Correction resolves it. The authoritative design treats `trials`, `order`, `swap_augmentation`, and `aggregation` as the method’s requested trial policy, calls randomized N-pass requests mechanically checkable, and says receipts for panel controls carry pass IDs, ordering seed, and swap group. In code, `ReviewMethod` parses all four fields, but `render_review_method` exposes only `trials` and `perspectives`; `ReviewPlan/v1` serializes report rows without any trial-policy fields. Receipt verification then reloads only `method.trials` from the current registry. `_receipt_reason` requires a truthy ordering seed and swap group whenever `required_passes > 1`, without consulting `order` or `swap_augmentation`, and receipt schema/verification contains no aggregation evidence. Consequently, a fixed-order, no-swap multi-trial method is rejected unless it supplies irrelevant seed/swap claims, while randomized/swap-augmented policy is not actually compared with the descriptor and aggregation is wholly unaudited. Changing registry `trials` after launch also changes adjudication of an unchanged plan and receipt bundle. The parity gates cover only the shipped panel defaults and do not test fixed/no-swap policy, aggregation, or registry drift. This is not merely missing implementation: accepted descriptor values are given contradictory audit semantics, so the launched artifact does not preserve the requested discipline.

### 10. MEDIUM — §4 Independence report; `launch/agent-launch.py:ReviewReport`, `verify_review_receipts`, `render_receipt_verdicts`; `gates/check_parity.py:launcher_receipts`; `gates/capture-review-goldens.py:composable_module_cell`

**Claim.** The design explicitly separates the concepts: “Achieved ≠ available.” Launch-time availability is `projected`, while runtime evidence updates `achieved_grade`.

**Conflicts with.** `verify_review_receipts` changes `ReviewReport.availability` from `projected` to the value `achieved` when all selected rows have accepted receipts, and `render_receipt_verdicts` and `launcher_receipts` treat `availability=achieved` as the success signal. Partial achievement leaves the same field as `projected`, even though `achieved_grade` may already be populated.

**Consequence.** Consumers built to the design cannot treat `availability` as an availability projection: after verification it becomes an achievement/completeness state, while partial achievement is hidden behind the old availability value. This duplicates `achieved_grade` and makes one field carry two incompatible meanings, producing incorrect UI, persistence, or gating logic.

**Why it survived refutation.** The contradiction is real and no Correction C4–C23 resolves it. §4 deliberately models launch-time availability as `projected` and runtime evidence separately as `achieved_grade`, under the explicit rule “Achieved ≠ available.” The implementation instead defines `AVAILABILITY_ACHIEVED = "achieved"`; `verify_review_receipts` writes that value into `ReviewReport.availability` only when every selected method has an accepted receipt, while independently populating `achieved_grade` even for partial achievement. `verify_receipts_command` then gates success on `verified.availability == AVAILABILITY_ACHIEVED`, `render_receipt_verdicts` exposes that overloaded field, and `launcher_receipts` pins `availability=achieved` as the all-valid success signal. Thus `availability` changes from a projection concept into an all-method receipt-completeness flag, while partial achievement remains labeled `projected`. The stage-7 phrase “Until then reports stay projected” does not clearly authorize this reuse and, read against “Achieved ≠ available,” at minimum leaves the current contract genuinely ambiguous. Consumers following the stated separation can therefore misinterpret verified and partially verified reports; `achieved_grade` and per-method verdicts do not repair the incompatible meaning assigned to `availability`.

### 11. HIGH — §4 “Achieved ≠ available” and §5 Stage 7

**Claim.** The design says real achievement requires “adapter-owned receipts,” that a model echo is insufficient, and that the process/request identifier proves a fresh dispatch; Stage 7 then treats wrong-packet, same-context, and identity-mismatched receipts as controls that cannot mark independence achieved.

**Conflicts with.** launch/agent-launch.py:_receipt_reason and verify_receipts_command accept an unauthenticated caller-supplied JSON bundle. Freshness is reduced to a non-empty dispatch_id unequal to the caller-supplied main_dispatch_id; packet identity is only equality between two caller-supplied strings; result existence is only a non-empty caller-supplied result_sha256; provider/model/effort are only compared with the plan. There is no adapter provenance, signature, process observation, or result from which either hash is recomputed. gates/check_parity.py:launcher_receipts demonstrates the hole in its “all-valid” case by manufacturing every supposedly evidentiary field itself—including a packet value that is not even a SHA-256 digest—and then expecting availability=achieved.

**Consequence.** A user or reviewing model can fabricate a plan-matching bundle without dispatching any reviewer and receive an achieved independence grade. The proposed Stage-7 completion criterion therefore tests only whether self-reported metadata is internally consistent, not the property it claims to falsify; building policy or release gates on achieved_grade would certify reviews that never occurred.

**Why it survived refutation.** The finding is substantiated. §4 requires adapter-owned receipts and explicitly says a model echo is insufficient; Stage 7 requires receipts to evidence fresh, isolated dispatches. No Correction C4–C23 supersedes that decision. In the implementation, `verify_receipts_command` accepts a caller-selected plan/contract file and a caller-supplied JSON bundle. `_receipt_reason` establishes no adapter provenance: `dispatch_id` need only be a non-empty string distinct from the bundle’s equally caller-supplied `main_dispatch_id`; `packet_sha256` is only compared with the bundle’s value and is not tied to packet bytes or even validated as a digest; `result_sha256` is not recomputed from a result and need not be a valid digest; and provider/model/effort are merely compared with the supplied plan. There is no signature, trusted adapter channel, process/request observation, or result artifact. The parity gate confirms this behavior: `launcher_receipts` manufactures the entire successful bundle, uses `packet-<hex>` rather than a SHA-256 digest, and expects `availability=achieved`. Therefore a fabricated, internally consistent bundle can mark every selected method accepted and set achieved availability/grade without any reviewer dispatch. The stated consequence follows for any policy or release gate that treats this output as evidence that review occurred.

### 12. MEDIUM — §5 Stage 7 receipt control

**Claim.** Stage 7 states that “three valid non-empty pass receipts can mark controls run,” while missing or duplicate receipts must not do so.

**Conflicts with.** The §4 receipt shape supplies one method-level process/request identifier and one result hash plus pass IDs. Correspondingly, launch/agent-launch.py:_receipt_reason merely requires required_passes distinct truthy strings in receipt["passes"] and one result_sha256 for the entire receipt. gates/check_parity.py:launcher_receipts marks the panel valid with one ReviewReceipt/v1, one dispatch_id, one result hash, and passes=["p1","p2","p3"]; it never supplies or validates three non-empty pass receipts or three pass results.

**Consequence.** Even after receipt provenance is made trustworthy, a single completed dispatch/result can claim three arbitrary pass labels and mark the panel’s randomized multi-trial controls achieved. Someone implementing the Stage-7 acceptance bar from the current schema would incorrectly certify three-pass breadth, ordering, and swap controls without evidence that three non-empty passes ran.

**Why it survived refutation.** The contradiction is real and no Correction C4–C23 resolves it. Stage 7 requires three valid, non-empty pass receipts before panel controls can be marked run, but §4 describes only a method-level receipt with one dispatch identifier and one result hash plus pass IDs. The implementation follows that weaker §4 shape: `_receipt_reason` accepts one `ReviewReceipt/v1` when `passes` contains at least `required_passes` distinct truthy values and the ordering/swap fields are truthy; it does not require a result or dispatch record for each pass. `launcher_receipts` proves the positive path with exactly one panel receipt, one dispatch, one result hash, and `passes=["p1","p2","p3"]`. It also does not test per-pass results, and duplicate receipts for an already-accepted method are ignored because the first verdict wins. Consequently, a provenance-trusted method receipt can attest three labels while evidencing only one completed result, yet the panel is marked achieved. That does not establish that three non-empty trials—or their breadth, ordering, and swap execution—actually ran, so the stated consequence follows.

### 13. MEDIUM — §4 per-method status, as amended by C1

**Claim.** The current decision retains ADVISORY(effort) for “when a capability’s seat does not consume it” and explicitly says it “must be reachable without being reached,” although C1 removes onto as an instance.

**Conflicts with.** §1 requires every binding to contain a validated effort and says mechanism derivation discards any candidate that cannot guarantee the exact model/effort. Its method and offer schemas define no field for declaring that a seat does not consume effort. The implementation matches that closed surface: launch/agent-launch.py:METHOD_KEYS and OFFER_KEYS contain no effort-consumption capability, derive_review_mechanism always carries the exact ReviewBinding, and _resolve_one produces STATUS_ADVISORY only for a non-default service_tier. No configuration or normal resolver path can produce ADVISORY(effort).

**Consequence.** A future reachable reviewer whose protocol cannot consume effort cannot be represented with the status the design promises: it must either be credited as though it received the exact effort or be dropped as unable to deliver the binding. Implementers cannot write the required falsifying subject, and consumers that rely on ADVISORY(effort) to distinguish an honest partial seat from an unavailable reviewer will never observe that state.

**Why it survived refutation.** The contradiction is real. C1 resolves only the factual question about onto: onto consumes the bound effort, so it is not an ADVISORY(effort) instance. It does not retract §4’s generic promise that a future capability whose seat does not consume effort can run with ADVISORY(effort). That promise conflicts with §1 and the synthesis: the selected Codex approach credits only an exactly bound reviewer, mechanism derivation must discard candidates that cannot guarantee the exact model/effort, and the rejected Claude approach was precisely to credit opaque reviewers with ADVISORY(effort). No declarative or core-derived distinction reconciles those rules: METHOD_KEYS and OFFER_KEYS cannot express effort consumption, ReviewMechanism always carries the exact binding, and the normal resolver emits ADVISORY only for an unprojectable service tier. Thus “must be reachable without being reached” names a desired latent state but supplies no path by which it is reachable. A future protocol unable to consume effort must either be dropped under §1 or be represented as having received an effort it did not receive; it cannot produce the promised honest ADVISORY(effort) state. No later Correction resolves this.

### 14. HIGH — Principles “base plus composable axes,” §1 Seam, and Corrections C8/C20

**Claim.** The design says specialised methods compose on top of the base “as availability and cost allow,” that method diversity is separate from the graded provider/model/effort axis, and that even a same-seat isolated panel is a real review floor. C20 further decides that cross-family review is “a strong recommendation, not a mandate.” Nevertheless, the current role rule is: “the base falls back, an optional method drops,” because an optional method is never rebound from its one exact binding.

**Conflicts with.** That rule discards a reachable review kind merely because it cannot achieve the preferred I1 grade. C8 supplies the concrete default: Ultracode is Codex-backed and can be seated only on Codex, so the Codex arms stopped binding it. The shipped `launch/agent-launch.toml:[presets.deep-review.review.hosts.codex.methods]` and `[presets.session-distill.review.hosts.codex.methods]` consequently contain onto but not Ultracode, even though those preset descriptions promise hybrid/Ultracode review and the capability is reachable on that same Codex host. More generally, `launch/agent-launch.py:resolve_composable_review` turns an unseated optional binding into `DROPPED`, while only the base is retried on the main seat. This conflicts with the Goal’s limit-by-reachability rule and with C20’s recommendation-not-mandate decision.

**Consequence.** A Codex user who installs Ultracode and selects Deep review does not receive that reachable lens at all; likewise, a one-provider user with an installed optional reviewer loses it when the shipped cross-provider binding is unavailable. They get only the base rather than a loudly degraded same-family structured/workflow review. Thus the repo’s single-seat default policy—not the reviewers the user can reach—still narrows the requested union of review kinds.

**Why it survived refutation.** The contradiction and consequence are real. The Goal limits review discipline by what the user can reach, while the Principles make method diversity independent of the I1 provider/model/effort grade and explicitly recognize a same-seat isolated review as a valid floor. C20 then overturns mandatory cross-family behavior for the base but preserves an unexplained role split: the base loudly falls back to the main seat, whereas an optional method is never retried there and drops. The implementation enforces that exact decision: `resolve_composable_review` retries a failed or unseated base on `main`, but an unseated method becomes `DROPPED`; the parity gate explicitly requires that behavior. C8 also narrows Ultracode's offer correctly to Codex, but the Codex arms of `deep-review` and `session-distill` respond by omitting Ultracode rather than binding that reachable method to a same-Codex isolated seat. Thus a Codex user can have Ultracode installed while the shipped Deep review preset—whose description promises hybrid onto/native/Ultracode review—never selects it; on a one-host profile, reachable same-host methods such as onto likewise drop with their unavailable cross-provider bindings, leaving only the base. This is not merely stale body text or an accepted installation cost: C20 says cross-family is only a recommendation, and the later C23 expressly identifies the unresolved “base/method role split” as a design-level contradiction. No later Correction reconciles it.

### 15. HIGH — §1 Seam provider→host rule and Correction C7

**Claim.** The design presents the registry as interface-independent, says “anything reachable can be registered,” includes a stateless API adapter among possible mechanisms, and C7 claims that “with a third host added in config alone” reviewers from multiple families resolve. At the same time, §1 requires every credited provider to map to a host so its effort can be validated.

**Conflicts with.** The implementing model makes the shipped host vocabulary a prerequisite, not merely configuration. `launch/agent-launch.py:host_for_provider` rejects a configured host absent from the hardcoded `HOST_EFFORTS`; `validate_effort` indexes that same codex/claude-only table; `load_config` fixes the structural codex and claude hosts to OpenAI and Anthropic respectively; and `review_provider_options` omits any host not present in `HOST_EFFORTS`. The gate’s supposed third-family case confirms the contradiction: `gates/check_parity.py:launcher_review_editor` has to mutate `launcher_module.HOST_EFFORTS["gate-third"]` before the config-added host becomes selectable, then removes the mutation afterward. That is not “config alone.”

**Consequence.** A reviewer reachable directly through a registered HTTP/MCP/CLI capability on a provider or host this repo has never encoded cannot receive a binding, even when the capability itself can deliver the request. Supporting it requires changing launcher code to add an effort vocabulary—and a new main host also requires extending the CLI host enum—so the practical limit remains which provider hosts the repo shipped rather than which reviewer the user can reach.

**Why it survived refutation.** The contradiction is real. C7’s “third host added in config alone” assertion is directly falsified by the gate that purportedly demonstrates it: adding `three["hosts"]["gate-third"]` is insufficient, so `launcher_review_editor` must also patch the code-owned `HOST_EFFORTS["gate-third"]` before `review_provider_options` will expose the provider. In production, `host_for_provider` likewise rejects that host, and no TOML field or capability offer can supply its effort vocabulary. C20 does not cure this: it confirms that a host without a vocabulary remains a hard error, but it neither retracts nor reconciles C7’s config-alone claim. The design’s requirement that effort be validated is compatible with pluggability in principle; the contradiction is that the only vocabulary source is a shipped Python table despite C7’s data-only scalability premise and the stated goal that shipped reviewer support not be the limiting set. Consequently, a reachable reviewer on an unseen provider family cannot become a credited binding through registry/configuration alone, even when an existing adapter can deliver it; launcher code must first be extended, and supporting that family as a main host also requires extending the CLI host choices.

### 16. HIGH — §1 Mechanism derivation and §3 unknown-method canary

**Claim.** The design says core derives a mechanism that guarantees isolation and the exact provider/model/effort, discards any candidate that cannot guarantee that exact binding, and proves the generic seam with an unknown-method canary. Registry prose is therefore supposed to describe a method, not be trusted to establish the credited seat.

**Conflicts with.** For capability-backed methods, `launch/agent-launch.py:derive_review_mechanism` only joins an operation/host to an adapter tag and raw command; it does not encode the binding into the dispatch. `render_review_method` substitutes only whichever slots the author happened to place in free-form `instructions`, then appends a model/effort suffix that is metadata rather than an invocation. `parse_review_method` accepts instructions such as `"x"` or `"run {command}"` with no provider/model/effort at all, and `_resolve_one` still grades the row from the configured ReviewBinding. `gates/check_parity.py:launcher_review_methods` avoids exposing this by giving its canary the purpose-built instruction `run {command} on {model}/{effort}`; its exact-seat body checks cover shipped methods, while the user registry is deliberately outside parity.

**Consequence.** Someone onboarding an unseen reviewer can produce a plan reported as `provider_difference` even though the instruction never tells the tool to use that provider/model/effort—or explicitly tells it to use another seat. The actual reachable tool can then fall back to its own same-family/default reviewer while ReviewPlan/v1 advertises the configured independent one, silently narrowing the discipline and invalidating the design’s core guarantee for precisely the reviewers the registry was created to admit.

**Why it survived refutation.** The contradiction is real. §1 assigns exact binding projection to core adapters and requires derivation to discard any mechanism that cannot guarantee the configured provider/model/effort. But for a capability-backed method, `derive_review_mechanism` merely selects an offer by operation and host and returns the adapter tag, capability command, and configured binding; it creates no binding-bearing invocation. `render_review_method` formats author-controlled prose and appends `[shape; model/effort]`, while `parse_review_method` only rejects unknown placeholders and does not require `{command}`, `{provider}`, `{model}`, or `{effort}`. Thus instructions such as `x`, `run {command}`, or prose explicitly directing another seat are accepted. `_resolve_one` nevertheless computes the grade from the configured `ReviewBinding` and records the row as projected whenever the command resolves. Corrections C13–C19 do not resolve the generic defect: their payload checks protect methods using the recognizable `llmOverride={{...}}` form, and their rendered-body checks cover shipped methods and prohibit known foreign model/effort literals, but they do not require an unseen method to project its resolved binding. C19 expressly recognizes that the renderer's suffix is metadata that cannot prove what the body instructs. The unknown-method canaries both use purpose-built `{model}/{effort}` prose, so they prove generic rendering, not generic exact-seat dispatch. The document's `UNKNOWN_UNTIL_RECEIPTS` qualification does not save this: receipts distinguish projected from achieved execution, whereas here the launcher labels a binding `projected` without having projected it into the invocation at all. Consequently a user registry method can be credited as `provider_difference` while the reachable tool receives no binding—or a contradictory one—violating the design's central guarantee on precisely the extension path it introduced.
