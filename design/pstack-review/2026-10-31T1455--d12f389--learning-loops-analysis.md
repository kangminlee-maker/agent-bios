# 학습 루프 세 개의 실제 사용 패턴과 재설계 방향

이 기록은 사용자의 관찰 두 가지에서 출발한다. `learn!`은 거의 쓰지 않고,
`distill!`은 한 달에 한 번 돌리는데 너무 무겁다. pstack의 `correct`는 신경 쓰지
않아도 누적되지만 단편적일 것 같다. 그리고 교정 빈도 하나: 지침이 고도화되면서
사용자가 에이전트를 고치는 턴은 20~30턴에 한 번 정도다.

결정은 담지 않는다. 채택·기각은 `decisions/record-decision.py`로 기록한다.

## 1. 세 루프를 같은 축으로

| 축 | `learn!` | `distill!` | `correct` (pstack) |
| --- | --- | --- | --- |
| 트리거 | 사용자가 세션 중 떠올려 타이핑 | 월 1회, 250세션 nudge | 사용자가 고친 순간, 또는 저장소 이력 |
| 재발 증거의 출처 | 없음. 한 세션 안에서 판정 | 원시 대화록 수백 개 채굴 | 커밋·revert·리뷰 코멘트·우회 주석 |
| 승인 비용 | 후보마다 대화 | 한 번에 수십 건 | PR 리뷰. 기존 절차에 올라탐 |
| 효과까지 지연 | 다음 큐레이션까지 | 한 달 | 즉시 |
| 효과 범위 | 사용자 → 조직 | 조직 지침 전체 | 그 저장소 하나 |
| 산출 형태 | 산문 + 의도 메타데이터 | 지침 편집 | 린트·타입·테스트·게이트 |
| 검증 가능성 | 낮음 | 중간(승인 게이트) | 높음(과거 실수에서 실패하는 검사) |
| 쇠퇴 | 큐레이션 전까지 방치 | 한 달 뒤엔 세션 기억 없음 | CI가 살아 있는 한 유지 |

세 루프는 경쟁 관계가 아니라 증거 출처가 다른 한 파이프라인의 조각이다. 문제는
각 조각이 자기 증거를 가질 수 없는 시점에 판정을 요구한다는 데 있다.

## 2. ledger가 말하는 것

`design/session-distill/ledger.json`(두 윈도, 2026-07-18과 2026-08-25, 227항목)을
센 결과다. 이 숫자는 agent-bios 저장소 작업 세션에서 나온 학습이므로, 일반 작업
저장소에서는 유형 비율이 다를 수 있다.

| 항목 | 수 | 비율 |
| --- | --- | --- |
| 전체 | 227 | |
| placed | 107 | 47% |
| incubating | 115 | 51% |
| 재발 증거 2세션 이상 (전체) | 49 | 22% |
| 재발 증거 2세션 이상 (placed 중) | 41 | 38% |
| `rare_high_cost` (placed 중) | 73 | 68% |
| `rollback` (incubating 중) | 57 | 50% |
| verdict `partial` (기존 지침의 부분 보강) | 160 | 70% |
| verdict `novel` | 55 | 24% |

placed 항목의 착지 층:

| 층 | 수 |
| --- | --- |
| guide | 83 |
| hook | 9 |
| global | 7 |
| enforcement | 3 |
| G(원칙, 층 미정 포함) | 9 |

읽히는 사실 네 가지.

1. **큐레이터가 실제로 채택한 근거는 재발이 아니라 단발 고비용이다.** placed의 38%만
   2세션 이상이고, 68%가 `rare_high_cost`다. `learn!`의 gate 1은 "2세션 재발 또는
   단발 고가치"를 허용하지만, 사용자 쪽에서는 세션 안에서 materiality를 보수적으로
   판정해 버린다. 판정은 큐레이터가 하는 일이고, 사용자 쪽은 기록만 해야 한다.
2. **incubating의 절반이 `rollback` 근거다.** 되돌림은 저장소 이력과 대화록에서
   기계로 뽑을 수 있는 신호다. 교정 턴보다 되돌림이 더 풍부하고 자동화 가능한
   트리거다.
3. **학습의 70%가 기존 가이드의 부분 보강이다.** 지침이 고도화된 상태의 전형이고,
   교정이 줄었다는 관찰과 맞는다. 남은 교정은 지침이 못 잡는 종류일 가능성이 높다.
4. **구조(enforcement, hook)로 간 것은 placed의 11%다.** `correct`가 흡수할 몫은
   1할이다. 단편적일 것이라는 직관은 데이터로 뒷받침된다. 다만 그 1할은 reach가
   전원이고 영구적이라 가치 밀도가 높다.

## 3. 교정이 20~30턴에 한 번이라는 사실의 함의

`cli-multi-model-workflow`의 측정(50요청 이상 세션 1,075개, 400요청 이상도 있음)을
기준으로 하면 세션당 교정은 한두 건이다. 250세션 윈도면 수백 건의 교정 사건이
있는데, 두 윈도에서 ledger에 들어온 항목은 227개다. 큐레이션이 포착한 것은
교정 사건의 일부다.

- **희소할수록 각 교정의 정보 가치는 크다.** 지침이 이미 잡아낸 것은 걸러졌고,
  남은 것이 지침의 진짜 빈틈이다. bar 미달 후보를 capture에서 버리는 정책은 희소한
  신호일수록 더 해롭다.
- **"2세션 재발" bar는 희소할수록 만족 불가능해진다.** 같은 실수가 두 번 나타나려면
  수십 세션이 걸리고, 그 사이 첫 사건은 기록되지 않아 재발을 알 길이 없다.
- **에이전트 제안형 capture의 노이즈 우려는 사라진다.** 20~30턴에 한 번이면 제안
  피로가 없다. 교정 턴에서만 제안하게 묶으면 상한도 필요 없다.
- **남은 교정은 구조로 가기 어려운 종류가 많다.** 판단·선호·맥락 의존(C, G)이거나
  환경 사실(E)이다. `correct`보다 기록 쪽 비중이 크다. 반대로 `correct`의 가치는
  사용자 본인 환경보다 새 저장소·새 팀원에게서 크다. 제품 목적상 팀 공유가 중심이므로
  의미는 있지만 사용자 개인 체감은 작을 것이다.
- **`correct`의 입력은 사용자 교정보다 넓다.** 되돌린 커밋, 리뷰 코멘트, 우회 주석은
  에이전트 교정과 무관하게 쌓인다. 교정 빈도가 낮아도 `correct`는 돌 수 있다.

## 4. `correct`의 단편성, 어디까지 진짜 문제인가

- **구조 층의 단편성은 문제가 아니다.** 저장소마다 린트가 따로 있는 것은 CI가
  원래 그렇다. 위험은 사람이 우회하는 검사가 생기는 것이고, pstack은 "문서·규칙은
  판단 호출에만, 마지막에"로 막는다. AGENTS.md의 "판단을 게이트하면 사람들이
  우회한다"와 같은 말이다.
- **지식 층의 단편성은 진짜 문제다.** 같은 실수 클래스가 저장소마다 다시 발견되고
  팀 환경으로 올라가지 않는다. 제품 목적(공유, 계승)과 어긋난다.
- `correct`는 부산물로 **규칙↔집행자 표**를 남긴다. 이 표는 "이 저장소에서 두 번
  이상 일어난 실수와 그 차단책"의 기계가 읽을 수 있는 목록이다. 여러 저장소의 표를
  모으면 `distill!`이 원시 대화록 대신 읽을 수 있는 이미 압축된 입력이 된다.
- 대화 속 교정(문체, 질문 방식, 판단)은 저장소에 흔적이 없어 `correct`가 못 본다.
  이것이 `learn!`이 맡아야 할 유일한 영역이다.
- 에이전트가 팀 저장소에 린트·CI를 추가하는 것은 무엇이 받아들여지는지를 바꾸는
  권한 행위다. PR 리뷰라는 기존 권한 경로를 반드시 거쳐야 한다.
- pstack의 `correct`도 설계일 뿐 측정은 없다. "두 번이면 클래스"가 과잉 구조화를
  낳는지는 모른다.

## 5. 재설계 방향

"누가 언제 무엇을 보는가"로 다시 배치하면 각 조각이 가벼워진다.

1. **교정 순간이 트리거, 판정은 집계로.** `learn!`을 사용자 의식에서 에이전트 제안으로
   바꾼다. 사용자가 에이전트를 고친 턴에서 에이전트가 후보 한 줄, 유형 추정, 착지
   표면 추정을 제안하고 사용자는 한 단어로 승인한다. bar 미달 후보를 버리지 않고
   기록한다. 재발 판정은 capture가 아니라 집계의 일이다. incubator ledger가 그 자리인데
   지금은 사용자 쪽에서 닿지 않는다.
2. **되돌림을 자동 신호로.** 되돌린 변경(revert 커밋, 사용자가 "그거 되돌려"라고 한 턴,
   되돌린 파일 편집)을 세션 끝에 기계로 수집해 포인터(세션 id, 턴 id, 한 줄)로 남긴다.
   ledger의 incubating 절반이 이 근거이므로 큐레이터 입력의 절반을 채굴 없이 얻는다.
3. **구조로 착지하는 것은 즉시, 저장소 안에서.** `correct` 상당을 들여오되 범위를 작업
   저장소로 한정하고, 산출은 과거 실수 replay로 증명하고, PR로만 들어간다.
   규칙↔집행자 표를 표준 형식으로 남긴다. 흡수 몫이 1할이라는 사실을 기대치로 둔다.
4. **`distill!`은 채굴이 아니라 집계.** 입력을 "지난 윈도 이후의 후보 레코드 + 되돌림
   포인터 + 저장소들의 규칙 표"로 바꾸면 250세션 채굴이 사라진다. 윈도는 짧아져도 된다.
   미러·parity·배포 마감은 채굴과 분리해 릴리스 리듬에 붙인다. PLACEMENT-FRAMEWORK가
   이미 "타입 G는 사건 채굴로 못 뽑는다"고 하므로 무거운 판단은 G에만 남긴다.
5. **승격 1단계를 개인 저장소로.** 승격이 곧바로 canonical 체크아웃 편집이 아니라
   Instructions Studio의 개인 항목으로 먼저 착지하면 윈도마다 게이트 전체를 돌리는
   고정비가 빠진다. 팀 환경 설계가 가는 방향과 같다.
6. **incubating 적체를 분리.** 115개가 윈도마다 다시 판단 대상이 되는 것이 무게의 한
   부분이다. 두 윈도 연속 미승격 항목은 "보류"로 접고, 새 증거가 붙을 때만 다시 연다.

비용과 위험.

- 에이전트 제안형 capture는 제안 품질이 낮으면 승인이 거절로 바뀌고 다시 안 쓰게
  된다. 교정 턴에서만 제안하고, 제안에는 반드시 교정 턴 포인터를 붙인다.
- 낮은 bar로 구조가 쌓이면 저장소마다 검사 부채가 생긴다. 규칙 표에 "이 검사가
  마지막으로 실패를 잡은 날"을 두고 오래 조용한 검사를 지우는 반대 루프가 필요하다.
- 교차 저장소 집계는 저장소 표를 읽을 권한과 경로가 필요하다. 팀 환경 설계
  (repository-first Instructions/knowledge)에 들어갈 질문이다.
- 되돌림 수집기는 사용자 대화록을 읽는다. `learn!`의 단일 세션 경계와 `distill!`의
  preset 경계 사이 어디에 두는지 정해야 한다. 세션 끝 hook이면 `learn!` 쪽이다.

## 6. 남은 미지수

교정 빈도는 알았다. 남은 것은 둘이다.

- **교정의 유형 분포.** 구조로 갈 수 있는 것, 산문·판단, 환경 사실의 비율. ledger는
  agent-bios 작업 기준이라 일반 저장소와 다를 수 있다. 최근 대화록에서 교정 턴을
  뽑아 셋으로 나누면 된다.
- **재발률.** 같은 교정이 다른 세션에서 반복되는 비율. ledger 기준 22%지만 이것은
  큐레이션이 포착한 것만이다. 낮으면 bar 자체가 틀린 것이고, 단발 고가치 통로가
  주 경로가 된다.

이 둘 없이 설계를 바꾸면 또 한 번 안 쓰이는 루프를 만들 위험이 있다. 다만 1절과
2절의 사실만으로도 "capture에서 버리지 않는다"와 "되돌림을 자동 수집한다"는
안전하게 결정할 수 있다.
