이 기록은 두 저장소를 읽고 만든 비교표와 후보 목록이다. 결정은 담지 않는다.

착지하지 않는다. 착지 표면은 `SURFACES.md`의 선택 순서로 골랐다.

### 1.2 작동 방식

1. 사용자가 `/poteto-mode <목표와 완료 조건>`을 보낸다. 안내서는 "how를 쓰지 말고 goal·done check·proof·known facts·constraints만 써라"고 가르친다.
2. 모드가 Principles 색인을 읽고 과제를 playbook에 대응시킨 뒤, 그 단계를 todo에 **그대로** 복사한다. 건너뛰는 단계는 지우지 않고 `skip: <이유>`로 남긴다.
3. 단계가 트리거를 치면 상황 스킬로 라우팅한다(코드가 함수 경계를 넘으면 `architect`, 설계가 다투면 `interrogate`, 숫자를 재면 `benchmark-checklist` 등).
4. 모든 playbook은 `Opening a PR`로 끝난다. 답장은 고정 계약을 따른다(목표 재진술로 시작, 적용한 원칙과 그것이 바꾼 결정을 명시, 모든 주장에 measured/inferred/guess 라벨, 소비자와 유지보수자 관점의 영향).
5. 모델 라우팅은 역할 줄로 한다. 각 스킬은 `pstack-models.mdc`의 자기 역할 줄을 읽고, 없으면 스킬 내 기본값을 쓴다. 판정 자리는 부모와 다른 모델 계열에서 고른다. 슬러그가 거부될 때의 대체 순서가 문장으로 고정돼 있다.
6. 호스트 이식은 어댑터 표로 한다. 생성기가 각 스킬에서 Cursor 고유 이름(`Task`, `AskQuestion`, `readonly`, 모델 슬러그, 경로)을 찾아 어댑터에 대응 행이 없으면 실패한다. 스킬 폴더명과 frontmatter `name`이 다르면 실패한다.
7. 학습 루프는 세 갈래다. `reflect`(세 렌즈 → 합성기 → Accepted/Rejected/Backlog → 사용자 승인 → 스킬 편집), `correct`(반복 실수를 클래스로 묶고 아키텍처 > 타입 > 린트/CI > 테스트 > 문서 순으로 막고, 과거 실수로 검사가 실패함을 증명하고, 규칙↔집행자 표를 저장소 지침 파일에 유지), `automate-me`(대화록을 캐서 개인 `-mode` 스킬 초안).
8. 연속성은 `show-me-your-work`(append-only TSV, run마다 `start` 행, 끝에 대화록 대조 감사, 다른 계열 모델의 교차 검토 → Attention 절), `session-pickup`, `pause-safely`, `recall`, `ketchup`이 맡는다.
9. 검증은 `prove-it-works`를 축으로 `create-verification-skill`(Launch/Doctor/Drive/Evidence/Cleanup + feature map, 넘기기 전 한 번 끝까지 실행), 형식 검증 스킬, `benchmark-checklist`, `blast-radius`, `interrogate`(실행으로 증명된 finding만 생존)가 받친다.
10. 배송은 `babysit`(모드 선언, merge frontier만, 토폴로지 불변, CI 분류 후 재시도), `shipping`(PR마다 비저자 검증자, patch-id로 판정 생존 판단, 바닥부터 연속 검증 구간만 머지), `autopilot-*`, `orchestrate`가 맡는다.
11. 개인화는 `dyl-stack`이 보여준다. 공유 모드 위의 얇은 라우터, 같은 이름의 overlay playbook은 공유본을 먼저 읽고 덧읽기, 충돌 시 개인 게이트 우선.

## 2. agent-bios와의 구조 대응

| 축 | pstack | agent-bios 현재 | 평가 |
| --- | --- | --- | --- |
| 진입·라우팅 | 모드 + playbook 단계 복사 | always 규칙(rule-003~013 Problem Solving) + 가이드 라우터 bullet + `coding-staged-workflow`의 3단계 | agent-bios는 단계의 "종류"만 있고 과제별 단계 목록은 없다 |
| 원칙 | 24 leaf, 답장에 이름과 바꾼 결정 명시 | 원칙이 always bullet과 가이드 본문에 녹아 있음. `domains.json`에 `item_id`·`handles` 존재 | 이름 호출 관례가 없어 사용자가 한 구절로 조향하기 어렵다 |
| 모델 라우팅 | 역할 줄 파일, 예산 사다리, 거부 시 대체 순서 | `launch/agent-launch.toml` tiers·presets·review methods, 영수증, `SpawnGate` 기록 | agent-bios가 구조적으로 강하다(런치 계약, 영수증). 한 손잡이 예산은 없다 |
| 호스트 이식 | 어댑터 표 + 생성 트리 + 이름 검사 | `gates/emit-mirrors.py` 투영 + `check-parity.sh` | agent-bios가 강하다. `claude/skills/`는 투영 대상이 아니므로 호스트 고유 이름 검사는 없다 |
| 학습 루프 | reflect·correct·automate-me, 스킬을 직접 편집 | `learn!`(의도만 기록) → `distill!`(큐레이터 배치), PLACEMENT-FRAMEWORK | agent-bios는 지침 학습에 강하고, 작업 저장소를 고치는 `correct` 상당은 없다 |
| 연속성 | decision TSV + pickup/pause/recall | handoff 계약(CONFIRMED/PROPOSED), 세션 pin, 작성자측 decision record | 사용자측 run 단위 결정 기록은 Decision memory 설계 방향이지 출하물이 아니다 |
| 검증 | prove-it-works + 저장소 로컬 검증 스킬 생성기 | `verification-discipline`("green이 무의미한 경우" 목록이 더 깊다), `review-request`, defect criterion | 규칙은 agent-bios가 깊고, 저장소에 남는 검증 도구를 만드는 절차는 없다 |
| 리뷰 | interrogate, arena 교차 판정 | 독립성 사다리, 영수증, panel/deep review | agent-bios가 강하다. 동급 |
| 배송 | babysit/shipping/autopilot/orchestrate | Default Frame 5~7단계 한 줄씩 | agent-bios 출하물에 PR 생애주기 절차가 거의 없다 |
| 개인화 | automate-me, overlay 플러그인 | env-personal tier, 개인 항목, per-item on/off, repo-charter | "공유 항목을 확장하고 충돌 시 우선"하는 overlay 의미론은 없다 |

## 3. 반영 후보 목록

각 항목은 출처 → 현재 → 제안 → 착지 표면 → 목적 적합성 → 비용/위험 순이다.
우선순위는 4절에 모았다.

### A. 구조

**A1. 과제별 playbook을 가이드 companion tree로.**
- 출처: `poteto-mode/playbooks/*.md`. 단계를 todo에 그대로 복사하고 건너뛴 단계는 `skip: 이유`로 남긴다.
- 현재: `coding-staged-workflow`가 설계→과정 설계→구현의 3단계와 lightweight path를 정의한다. bug fix·refactoring·investigation·session pickup 같은 과제별 단계 목록은 없다.
- 제안: `claude/guides/coding-staged-workflow/playbooks/<kind>.md`를 companion tree로 두고(SURFACES의 Guides는 same-stem companion tree를 허용), 가이드 본문에 "과제 종류가 맞으면 그 단계를 todo에 그대로 복사하고, 건너뛰는 단계는 이유와 함께 남긴다" 한 줄을 추가한다. 후보 종류는 bug-fix, feature, refactoring, investigation, session-pickup, pause-safely 여섯이면 충분하다.
- 목적: worker·model·세션이 바뀌어도 같은 단계로 이어진다(continuity). 팀이 단계 목록을 공유·수정한다(sharing).
- 위험: 가이드 희석. playbook은 절차이므로 always 표면에 둘 수 없고, `relevant` 라우터로만 닿는다. 개수를 제한하고 각 단계가 `verification-discipline`을 가리키게 해 중복을 막는다.

**A2. 규칙 handle을 답장에서 인용하는 관례.**
- 출처: "In your reply, name each principle that shaped a decision and the specific choice it changed. Cite only principles whose leaf you read this session." 안내서 08장은 사용자가 원칙 이름 한 구절로 조향하는 법을 가르친다.
- 현재: `domains.json`에 `item_id`와 일부 가이드의 `handles`가 있다. `SpawnGate: <gate> <tier> spawn|inline — <why>` 한 줄 기록은 같은 발상의 단일 사례다. 답장에서 어떤 규칙이 어떤 결정을 바꿨는지 말하는 관례는 없다.
- 제안: (1) 모든 가이드에 짧은 `handles`를 부여하고 Instructions Studio가 보여준다. (2) `verification-discipline`의 Reporting 절에 "적용한 규칙의 handle과 그것이 바꾼 결정을 한 줄로 적는다. 읽지 않은 규칙은 인용하지 않는다"를 더한다.
- 목적: 사용자가 공유 어휘로 조향한다. `understand!`의 학습 자료와 같은 어휘를 쓴다.
- 위험: 인용이 장식이 되는 것. pstack도 "결정 없는 인용은 적용하지 않은 것"이라고 못박는다. 같은 문장을 넣는다.

**A3. 스킬 트리의 호스트 고유 이름 게이트.**
- 출처: 생성기의 `TERMS` 검사. Cursor 이름이 쓰인 스킬에 어댑터 행이 없으면 실패.
- 현재: `claude/skills/`는 두 호스트가 한 트리를 쓰고 투영되지 않는다. 호스트 도구 이름(`AskUserQuestion`, `Agent`, `TodoWrite`)이 스킬 본문에 들어와도 잡는 게이트가 없다.
- 제안: `gates/check-package.sh`나 lexicon 게이트에 "스킬 본문에 호스트 도구 이름이 나오면 실패, 예외는 이유와 함께 열거" leg를 추가한다. 지금 두 스킬(`understand`, `repo-charter`)은 위반이 없어 보이므로 음성 대조군을 심어 발화를 증명해야 한다.
- 목적: 두 호스트에서 같은 절차가 동작한다(sharing).
- 위험: 낮음. 결정 가능한 검사이므로 blocking 가능.

**A4. 문서 속 모델 이름을 바인딩 권위와 대조.**
- 출처: `check-pstack-docs.mjs`가 README·guide의 수량 주장, 슬래시 명령, 링크, 모델 이름을 트리와 대조한다.
- 현재: `launch/check-prompting-targets.sh`는 런치 설정의 모델 ↔ prompting 가이드 `targets:`만 본다. `cli-multi-model-workflow`와 `coding-staged-workflow`의 Environment Binding 표는 모델명을 산문으로 적고 "8주 지나면 다시 probe"에 의존한다.
- 제안: Binding 표의 날짜가 `agent-launch.toml`의 모델 목록 변경 커밋보다 오래되면 `--diff`식으로 공개(disclose)하는 leg. 차단은 하지 않는다(판단이 섞인다).
- 목적: 공유 기본값이 조용히 썩지 않는다.
- 위험: 낮음. 이미 `ontology/impact.py --diff` 유형과 같다.

**A5. overlay 의미론(공유 항목 확장, 충돌 시 개인 우선)을 Team 설계에 질문으로.**
- 출처: `dyl-stack`. 공유 모드 위의 얇은 라우터, 같은 이름의 overlay playbook은 공유본을 먼저 읽고 덧읽기, "Dylan gates win on conflict".
- 현재: 개인 항목과 per-item on/off는 있다. 한 항목이 다른 항목을 **확장**하고 우선순위를 선언하는 모델은 없다. SSOT §S05는 "로컬 콘텐츠 override는 Team 투표가 필요 없다"고 하지만 확장 관계의 저장 형태는 정하지 않았다.
- 제안: 설계 SSOT에 foreclosure 질문 하나를 올린다. "지금의 store 항목 모델이 `extends: <InstructionsRef>`와 우선순위 선언을 나중에 담을 수 있는가, 아니면 지금 바꿔야 비싸지지 않는가."
- 목적: 제품 목적의 핵심 문장("공유 환경은 재사용 기본값이지 획일 강제가 아니다")을 저장 모델이 지탱하는지 확인한다.
- 위험: 지금은 설계 질문만. 구현 주장은 하지 않는다.

### B. 작동 방식

**B1. 한 손잡이 추론 예산.**
- 출처: `setup-pstack`의 `unlimited/large/medium/small`이 모든 역할의 effort 토큰을 한 번에 올리거나 내린다.
- 현재: presets(balanced/deep-review/fast-batch/solo)가 tier 조합을 고르고 effort는 tier별로 고정이다.
- 제안: preflight에 "예산" 한 축을 두고 tier별 effort를 한 단계씩 같이 움직인다. 런치 계약에 들어가므로 golden이 바뀐다.
- 목적: 환경 선택이 쉬워진다. 비용 절감 경로가 한 질문으로 끝난다.
- 위험: 런치 계약의 보이지 않는 성장. 낮은 우선순위.

**B2. 거부된 모델 id의 결정적 대체 순서.**
- 출처: 모든 스킬이 "도구가 슬러그를 거부하면 → 기본값 → 같은 계열의 가장 가까운 유효 슬러그 → `model` 생략, 그리고 말하라"를 반복한다.
- 현재: rule-054(라이브 artifact로 확인), Rate-limit fallback 행, "family collapse를 기록하라".

**B20. 주석 전용 리뷰어.** `comment-sicko`의 keep-list와 "작성자가 아닌 리뷰어"는 `documentation-hygiene`의 주석 규칙과 리뷰 독립성 사다리가 이미 덮는다. 조치 없음.

**B21. `/sharpen`과 `/in-your-own-words`.** "최고 전문가라면 무엇을 더 하겠는가, 가장 날것의 재료는 무엇인가, 어떤 방법과 도구를 쓰겠는가, 너도 나도 아닌 무엇이 결과가 맞음을 보이겠는가"는 rule-003(목표·범위·모호성·완료 조건)과 falsifiable done-when을 사용자 쪽에서 끌어내는 질문이다. requested 스킬 후보. 낮은 우선순위.

**B22. `/ketchup`의 대기 호출 계약.** 사용자에게 걸린 호출마다 링크·사용자에게 바뀌는 것·근거·위험·추천을 답장만으로 결정 가능하게. Decision Framing(rule-014~017)과 같은 내용을 비동기 감독용 스킬로 포장했다. CURRENT.md의 "실제 작업 CLI/app에서 질문" 설계 항목에 참고 사례로 연결한다. 설계 메모.

**B23. 영어 기술 문서 표준.** `technical-writing`(Diátaxis + Google style + STE + Global English)과 `unslop`의 안정 번호 규칙(다른 스킬이 번호로 인용). agent-bios는 `korean-writing`만 있다. 영어 가이드가 필요하면 후보. 번호로 인용되는 규칙 id는 `item_id`로 이미 있다. 낮은 우선순위.

**B24. hillclimb 루프.** 한 변경·한 측정·keep/revert, harness를 먼저 민감도 증명 후 동결, 시도 횟수 하한, 시도마다 기록 행. A1의 playbook 후보에 포함 가능. 낮은 우선순위.

**B25. Autonomy의 "항상 멈춤" 목록과 세션 override.** rule-055와 `repo-charter`의 human authority stop points가 덮는다. 조치 없음.
