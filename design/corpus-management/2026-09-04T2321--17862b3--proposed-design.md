# User-managed corpus — proposed design

Status: **PROPOSED, pre-implementation.** This document defines the target
product and the implementation process. It does not authorize implementation.

The design is grounded in the current authoring, assembly, install, launcher,
state, and consumption paths at the pinned HEAD. The blind packet used for the
independent design pass is
`2026-09-04T2310--17862b3--blind-design-packet.md`.

An independent GPT FRONTIER draft ran in a fresh context and supplied the
baseline/overlay, stable-id, standalone-manager, and activation-evidence
skeleton adopted here. A Claude Fable 5 OAuth draft was attempted from the same
packet but failed before dispatch (`input_tokens: 0`, authentication rejection),
so it is not counted as a review. Cross-provider design verification remains
open; this proposal must not be called cross-provider-converged.

## Decision in one paragraph

Build a standalone **Corpus Manager** whose canonical model is an immutable
installed baseline plus a copy-on-write personal layer. Every managed corpus
item receives a stable package-local id that survives content edits, renames,
removal, and changes of consumption surface. The manager resolves baseline,
personal packages, overrides, and tombstones into one effective corpus graph,
then the existing Claude and Codex realization paths project that graph under a
single deployment transaction. The launcher deep-links into the manager; one
`corpus` skill and a deterministic `agent-bios corpus` API use the same backend.
Installed-item restore removes the personal override/tombstone and exposes the
current installed baseline. Reset reactivates the last successful install's
defaults while preserving user-authored content for recovery.

This increases the concept surface by one required durable identifier and one
personal overlay layer. It does not add a second corpus model, a second writer,
or a new workspace/profile concept.

## Done when

The feature is done only when all of the following are true on a real npm-only
install, with no Git checkout:

1. The inventory derived from package manifests is non-empty and covers every
   agent-bios-managed instruction carrier on both hosts.
2. Every registered item can be opened as a wiki page, edited, removed, and—if
   installed—restored individually from both the TUI and the always-installed
   management skill.
3. A user can create a personal item, choose a supported consumption surface,
   preview the effective/host diff, and apply it through the same backend.
4. A package update preserves non-conflicting personal intent and refuses an
   unresolved conflict without replacing the last good effective corpus.
5. An interrupted write, failed validation, failed projection, or failed
   activation probe leaves either the complete prior effective corpus or a
   fail-loud recovery record naming every unresolved target; no success is
   reported over a split state.
6. `restore`, `reset`, `rollback`, `undo`, and `uninstall` have the distinct
   behavior defined below and do not delete user data outside their declared
   scope.
7. Current install behavior is byte-equivalent while the feature flag is off.

## Why the current mechanisms are not the answer

- Editing deployed files directly is overwritten by install/update, breaks the
  generated Claude/Codex relationship, and has no stable restoration source.
- Installer backups contain prior bytes, are pruned, and have no reader. They
  are an escape hatch, not an installed baseline.
- Current content-version rollback requires a checkout and Git history, moves
  only part of the realized corpus, and is whole-version rather than per-item.
- `manifest.txt` is a path ownership list. It has no logical item id, origin,
  source hash, consumption surface, or complete projection map, so it cannot
  become the CRUD catalog.
- The current corpus scope is inconsistent: distribution, rollback, and
  benchmark realization enumerate different footprints. Item CRUD must not be
  added until one inventory owns this answer.
- The deferred multi-package composer has reached its activation condition: a
  user-created corpus is the first real second package.

## 1. Concept decisions

| Existing concept | Path | Decision |
| --- | --- | --- |
| `corpus` | extend | The installed and personal instruction items resolved into the effective graph. Source packages and host projections remain distinct views of it. |
| `package` | reuse + extend | Keep unversioned `@scope/name`; add stable item metadata and make the already-specified local multi-package composition real. |
| `domain` | reuse | It remains audience classification, keyed by `(package_id, domain)`. It does not decide load timing. |
| `consumption surface` | reuse + make explicit | It remains the canonical term. The UI exposes outcome labels; the resolver owns the host carrier. Do not add the near-synonym “delivery mode.” |
| `preset` | preserve | Presets keep launch settings. V1 does not make them content owners or add corpus profiles. A later preset may reference a saved corpus selection only if per-launch corpus selection becomes a real requirement. |
| personal area | extend | Add personal packages, targeted overrides, tombstones, and semantic history beside—not inside—the purgeable deploy state. |

One new lasting field is necessary:

```text
CorpusRef = (package_id, item_id)
```

`item_id` is immutable and package-local. Content, label, source path,
consumption surface, audience, and active state may change without changing the
id. Removed ids are never reused. The runtime assigns ids for personal creation;
package authors assign and preserve ids in source manifests. Models may suggest
labels, never ids or paths.

This deliberately amends the older package contract's “no per-item id” choice.
That choice assumed content did not move between carriers. CRUD and per-item
restore invalidate the premise: a mutable anchor or filename cannot identify an
item after the operation the identifier must survive.

## 2. What is a corpus item

A corpus item is a manifest-registered logical instruction unit with:

- `CorpusRef`;
- an origin package and source digest;
- a human label and content bundle;
- one consumption-surface specification;
- separate audience/domain applicability;
- lifecycle state (`active`, `removed`, or `conflict`);
- zero or more generated host realizations.

One logical item may own several source or realization members. A
`when-relevant` guide normally owns its guide body and router metadata as one
item, so remove/restore cannot strand either half. Where an existing router is
independently meaningful, the inventory keeps two items plus an explicit
dependency edge and the transaction operates on the derived dependency closure.

The inventory includes agent-bios-managed:

- global rules;
- guides and their router relationship;
- prose-only skill bodies and descriptions;
- hook-injected instruction text plus its structured binding metadata;
- agent descriptions and bodies plus their structured role metadata;
- personal learnings, through their existing `learning_id` authority rather
  than by parsing the Markdown projection.

All of those are reviewable. Existing registered items are content-editable,
removable, and restorable when they have an installed baseline. Surface changes
are allowed only among the choices the backend returns for that item and target
host set.

The inventory may show related system mechanisms—launch contracts, MCP tool
registration, enforcement defaults, gates, receipt adjudication, capability
withholding, and the incubator ledger—but those are not corpus CRUD targets.
They alter capability or acceptance rather than merely delivering instruction
text. The minimal always-installed `corpus` management skill is also bootstrap
machinery rather than a managed item: allowing the recovery surface to remove
itself would make the required in-session restore path disappear. It is deployed
and verified with the manager CLI, removable only by uninstall, and shown in the
wiki's System view. Project `AGENTS.md` files, manual text outside agent-bios
markers, and files another tool owns in shared guide/skill directories are also
outside the manager's write authority.

### Creation scope

The first release creates personal items on three prose-safe surfaces:

| UI choice | Canonical surface | Required semantic fields | Resolver output |
| --- | --- | --- | --- |
| **Always available** | global bundle | concise rule body, audience | global fragment on both hosts |
| **When relevant** | guide | trigger, summary/router text, guide body | guide plus reachable router |
| **When requested** | skill | skill name, one-sentence invocation description, procedure body | prose-only skill package on both hosts |

Advanced existing items retain two structured editors:

- **On a matching event** → hook injection; edit the injected prose and choose
  from host-supported event/matcher fields. Creating executable hook code is
  excluded.
- **When delegated** → agent description/body; edit prose and choose from
  supported role metadata. Creating new tool authority is excluded.

Moving an item into a control surface, creating an MCP server, adding a gate,
or creating executable hook/skill assets is a development workflow, not an
enum change. The UI says this rather than presenting a choice the runtime cannot
honestly realize.

`removed` is lifecycle state, not a consumption-surface value. Audience/domain
selection is a separate axis too.

## 3. Canonical authorities and storage

The paths below are conceptual; platform adapters resolve the XDG/macOS/Windows
homes. The proposed Unix defaults are explicit so ownership can be reviewed.

```text
~/.local/share/agent-bios/                 # deploy-managed; uninstall may purge
  corpus/
    baselines/<release-digest>/
      packages/<encoded-package-id>/...
      inventory.json
    baseline-current.json
    candidates/<release-digest>/...
    effective/<generation-id>/
      inventory.json
      claude/...
      codex/...
    effective-current.json
    transactions/<transaction-id>/
      journal.json
      undo/...
  corpus-status.json                       # summary projection only
  install-defaults.json                    # last successful clean install choices
  manifest.txt                             # deployment ownership, not item truth

~/.config/agent-bios/corpus/               # user-owned; install never overwrites
  active.json                              # active personal revision and selections
  packages/<scope>/<name>/
    manifest.json
    items/...
  overrides/<target-package>/<item-id>/
    override.json
    content/...
  tombstones/<target-package>/<item-id>.json
  history/<transaction-id>/
    request.json
    plan.json
    before.json
    result.json
    base-content/...
  trash/...
```

Existing personal learning JSONL stays its authority during V1. A catalog
adapter presents it as items and updates its JSONL/Markdown host projections
atomically. Every writer of that authority—`agent-bios learn`, promotion
migration, corpus edit/remove/recover, and reset—must call one learning-store
API and take one learning lock. The manager never publishes a JSONL snapshot
read before that lock. When an operation also changes corpus projections, lock
order is fixed as deployment lock then learning lock; capture takes only the
learning lock, so no reverse acquisition exists. Apply rechecks the learning
revision under the lock before replacing any projection. No forced data
migration is needed merely to make the wiki complete.

Authority assignment:

| Value | Authority |
| --- | --- |
| installed item content and default metadata | immutable package baseline snapshot |
| personal created content | personal package source |
| changes to one installed item | its personal override/tombstone |
| item/package ids, digests, canonical paths, timestamps | runtime |
| effective membership and host paths | generated effective inventory |
| TUI/wiki/skill page | renderer over the same inventory and sources |
| apply/recovery state | transaction journal |
| small launcher status panel | generated `corpus-status.json` projection |

`active.json` records which personal packages/revision and personal-learning
generation are active. It survives install and normal uninstall. Reinstall
reapplies conflict-free personal intent; if it conflicts with the new baseline,
the clean installed baseline becomes usable and the personal revision remains
staged for explicit resolution rather than being discarded.

The installed baseline is copied from the validated package bytes during a
successful install. It is not reconstructed later from a possibly updated npm
path or dirty checkout, and it is not subject to ordinary backup pruning.

An override stores the target `CorpusRef`, base digest, changed-field mask,
replacement values, and the old base content needed to show a later three-way
conflict. Text is stored as complete replacement content, not a positional patch.

The personal package is portable file-backed Markdown/JSON, not SQLite. SQLite
would simplify transactions and search but makes manual inspection, Git backup,
and package export harder. Runtime indexes may be cached, but the cache never
becomes content authority.

## 4. Resolution and update conflicts

The resolver computes:

```text
validated installed package baselines
  + active package/domain selection
  + personal package items
  + exact-target field overrides
  - exact-target tombstones
  = desired corpus graph
```

There is exactly one personal overlay precedence level. This is not a general
N-layer conflict engine. Different packages keep deterministic ordering—core,
then ascending `package_id`, source order within a package—and semantic
contradictions remain a user-review concern.

On package update, compare old base, personal intent, and new base by field:

1. No personal change → take the new base.
2. Tombstone and same stable id → keep removed; restore later reveals the new
   installed version.
3. User and upstream changed disjoint fields/attachments → combine.
4. Both changed the same scalar field or content file → conflict; do not ask an
   LLM or runtime heuristic to choose.
5. Upstream removed an overridden item → conflict with three explicit choices:
   keep it as a new personal item, accept upstream removal, or retain the prior
   effective corpus.
6. A new base makes the selected surface invalid → conflict.

A candidate baseline may be staged and inspected while conflicts exist. It does
not replace the active baseline/effective corpus until the whole desired graph
validates. Non-interactive update leaves the prior effective corpus active,
records `update_pending_conflict`, and exits non-zero rather than mixing versions
silently.

## 5. One transaction path

`install`, `onboard`, package/domain selection, create, edit, surface change,
remove, restore, reset, version rollback, learning capture, and learning
migration must call the appropriate store through one coordinated transaction
boundary. The launcher and skill never write canonical or deployed files
themselves.

Transaction flow:

1. Build a proposal from semantic inputs and compute its expected source/user
   revision.
2. Return a plan containing the semantic diff, generated host diff, warnings,
   validation results, and affected owned targets.
3. On Apply, acquire the common deployment lock and re-read every authoritative
   input; reject a stale plan with no writes.
4. Validate ids, package/domain refs, surface-specific fields, source refs,
   ownership, content limits, and a non-empty inventory.
5. Materialize the candidate personal generation and both host projections in a
   staging area.
6. Write a unique journal and undo snapshot, then mark it `PREPARED`.
7. Publish supporting generation-qualified files first and each host's reader or
   registration surface last. The launcher refuses to start a managed session
   while the journal says `PUBLISHING`.
8. Update the effective inventory, install defaults when applicable, manifest,
   and status only after the host projections are complete.
9. Run structural verification and the applicable activation probes. Mark
   `COMMITTED`, or undo the complete write set and retain the recovery record.

Every individual file replacement is atomic and mode-preserving. The logical
transaction is crash-recovered from its journal. An undo is a new inverse
transaction against the current revision; it never rewinds a pointer across
later work.

Strict one-pointer generation activation would be preferable but is not assumed:
Codex's user-owned `AGENTS.md` marker region and shared host scan directories do
not currently expose a proven generation selector. Implementation must probe
symlink/import/registration behavior. If a carrier cannot switch generations,
the ordered publish + startup barrier + complete undo path is the minimum honest
contract; the product must not claim instantaneous cross-host atomicity.

## 6. TUI: Corpus Studio

`agent-bios corpus` opens the standalone manager. The launcher replaces the
current scattered corpus entries with one **Corpus** deep-link while keeping its
small status summary. Session Distill links back to the same History/Versions
view rather than owning a second package browser.

### Library screen

```text
┌ Corpus tree / filters ─┬ Wiki page ───────────────────────┬ Status/actions ┐
│ Installed              │ Title + effective content        │ origin          │
│ Personal               │ TOC and corpus:// links          │ surface         │
│ Modified               │ backlinks / related items        │ audience/domain │
│ Removed                │ installed vs mine vs effective   │ hosts/evidence  │
│ Conflicts              │ history and realization details  │ Edit · Remove   │
└────────────────────────┴──────────────────────────────────┴─────────────────┘
```

- `Tree` groups by state, package, domain, surface, and item kind.
- Search covers label, content, id, package, domain, and status.
- `MarkdownViewer(open_links=False)` renders the page and intercepts
  `corpus://<package>/<item>` links for internal navigation. External links need
  an explicit open action.
- The default page is **Effective**. Tabs show **Installed**, **My change**,
  **Diff**, **Host realization**, and **History**.
- Status distinguishes `source`, `composed`, `deployed`, `registered/reachable`,
  and `observed loaded/invoked`; it never compresses those into a false `active`.

### Editing

- `TextArea(language="markdown")` provides multiline editing, undo/redo, dirty
  state, and discard confirmation.
- Consumption choices use the outcome labels in §2. Choosing a surface opens
  only that surface's required structured fields.
- Save does not publish. It creates a plan and opens Preview.
- Preview shows baseline → personal → effective changes, affected hosts and
  paths, token/always-loaded impact when known, warnings, and activation probes.
- Apply is a separate confirmation bound to the exact plan revision.
- Installed-item Delete is labeled **Remove from my effective corpus**.
- Restore is labeled **Restore current installed version**.

### Degraded/non-interactive use

- `list`, `search`, and `show` render through stdout/a pager.
- `$VISUAL`/`$EDITOR` edits a runtime-owned temporary draft, followed by the
  same validation and preview. The temp file is never canonical.
- Numbered prompts edit closed surface fields and default Apply to No.
- Non-TTY mutation requires a structured payload and exact plan id/revision.

The Textual screen is a frontend over the manager; corpus lifecycle logic does
not move into the already-large launcher.

## 7. One session skill and one machine contract

Ship one always-available `corpus` management skill. Its short description
covers inspect, create, edit, change surface, remove, restore, and reset.
Separate creator, reviewer, and editor skills would duplicate identity,
navigation, and safety rules while sharing one authority. This bootstrap skill
is product machinery, not an item in the mutable corpus inventory; otherwise
removing it would remove the session route required to restore it. The ordinary
personal skills it manages remain corpus items.

The skill calls the deterministic backend, conceptually:

```text
agent-bios corpus list|search [--json]
agent-bios corpus show <CorpusRef> [--view effective|installed|mine|diff]
agent-bios corpus plan --input -
agent-bios corpus apply <plan-id> --expected-revision <rev>
agent-bios corpus history [<CorpusRef>]
agent-bios corpus activation [<CorpusRef>]
agent-bios corpus export|import-plan ...
agent-bios corpus                         # TUI when interactive
agent-bios reset                          # all agent-bios settings
```

Allowed semantic plan operations are `create`, `update`, `move_surface`,
`remove`, `restore`, `recover_personal`, `reset`, and `resolve_conflict`.
Inputs may contain content, labels, a target ref, an expected digest, an allowed
domain ref, a choice returned by the backend, and surface-specific semantic
fields. They may not contain canonical paths, runtime ids, timestamps, hashes,
host destinations, shell commands, or arbitrary attachment paths.

Runtime owns plan/transaction/generation/receipt ids, item ids for personal
creation, canonical paths, ordering, schema versions, timestamps, digests,
field masks, allowed ref sets, serialization, locking, persistence, projection,
activation status, and recovery.

Unknown fields, runtime-owned fields, unsupported refs, and ineligible surfaces
fail loudly. Model prose becomes content only through a valid plan followed by
Apply. Destructive or authority-expanding plans always expose their consequence
before Apply; the skill cannot treat its own recommendation as user approval.

## 8. Recovery vocabulary

| Operation | Exact meaning |
| --- | --- |
| Remove installed item | Add a tombstone for its `CorpusRef`; keep baseline bytes and semantic history. |
| Remove personal item | Deactivate it in a new personal revision and move its bytes to recoverable history/trash. |
| Restore installed item | Remove all content/surface overrides and the tombstone; reveal the item exactly as it exists in the current active installed baseline. If its domain is unselected, it remains inactive by selection. |
| Recover personal item | Reintroduce a removed personal revision. This is not “restore.” |
| Corpus reset | Archive the active personal revision, deactivate personal packages, clear overrides/tombstones, rotate the active personal-learning projection to an empty generation, restore package/domain selection from `install-defaults.json`, and recompose. Personal package and learning source remain recoverable in history but inactive. |
| `agent-bios reset` | Corpus reset plus removal of agent-bios-owned launcher local settings so packaged defaults become effective. Proposed default: also return connections to the zero-egress install state; secret values are deleted after an explicit warning and are never copied into the recovery archive. |
| Undo | Apply an inverse plan to the current revision. |
| Older-version rollback | Select an older installed package baseline, then resolve the same personal overlay against it. It does not erase personal state or mean “first install.” |
| Uninstall | Remove binaries, deploy-managed state, and proven owned files/regions. Preserve user corpus packages/history and personal learnings; never delete another tool's shared-directory entries. |
| Permanent purge | A separate explicit, target-listed operation. It is never implied by reset, restore, or uninstall. |

If an installed item no longer exists in the active baseline, `restore` refuses
instead of inventing content and offers the distinct choices to recover the last
personal version or roll back the installed baseline.

`install-defaults.json` records the clean package/domain selection and packaged
settings at the end of each successful install, before personal overlays. This
removes today's ambiguity between “no saved selection means every domain” and
“onboarding selected core+infra only.” Reset replays a recorded fact, not a
guessed default.

## 9. Honest activation evidence

Each realization adapter reports the strongest state it can prove:

| Surface | Deployment evidence | Consumption evidence |
| --- | --- | --- |
| global | effective inventory and reader-surface digest agree | a new real host session quotes the exact generation canary |
| guide | registered file digest and router target resolve | a session receipt shows retrieval/read of that guide digest |
| skill | both host copies/registrations match the descriptor digest | a real invocation receipt names the same digest |
| hook | binding and injected-text digest are armed | a matching synthetic event receives the nonce on each supported host |
| agent | descriptor/body digest is registered | a real spawn/dispatch receipt names the same body digest |

Absence of a running session is `activation pending`, not failure. A positive
load mismatch is failure. If a host exposes no receipt, the UI stops at
`deployed` or `registered, activation unverified`.

Before agent CRUD lands, the current Claude `central/agents` discrepancy must be
resolved by a live probe: the assembler copies those files, while the launcher
appears to synthesize agent prompts elsewhere. An unconsumed carrier is not an
editable consumption surface merely because a file exists.

Existing sessions may retain prior context. The manager promises the next
verified session, never retroactive unloading.

## 10. Alternatives and disposition

| Alternative | Benefit | Cost/risk | Disposition |
| --- | --- | --- | --- |
| edit deployed files | smallest first diff | update clobber, host divergence, no baseline restore | reject |
| fork/copy the full baseline | simple mental model, exportable | permanent upstream merge burden and duplicate authority | offer only as export |
| immutable baseline + overlay | update survival, exact restore, small user delta | needs identity, resolver, transaction engine | **default** |
| derived anchor/filename identity | avoids one migration | breaks on the operations this feature adds | reject |
| stable package-local item id | durable links, history, restore | one-time manifest migration | **default** |
| expose every internal surface as one enum | superficially uniform | turns prose edits into false authority promises | reject |
| outcome labels over validated surface variants | honest and understandable | surface-specific forms | **default** |
| put CRUD in launcher | fewer entrypoints | couples lifecycle to a 10k+ line preflight | reject |
| standalone manager + launcher link | one backend, testable, direct CLI entry | one new runtime module/package | **default** |
| external editor/pager only | highly portable | misses requested native wiki/editor | fallback only |
| separate CRUD skills | discoverable verbs | repeated lifecycle/authority contract | reject; one skill |
| destructive reset | exact blank slate | user-data loss and secret duplication risk | reject |
| archive/deactivate + separate purge | reversible and honest | retained history storage | **default** |

## 11. Lifecycle example

Assume installed item `(@agent-bios/core, verify-before-done)` is consumed
**Always available**.

1. **Edit:** the user adds “record the evidence.” The manager stores a content
   override with the installed base digest; both host projections change only
   after Preview → Apply.
2. **Move:** the user chooses **When relevant**. The id stays the same; the
   resolver emits a guide body plus a reachable router and previews the decrease
   in always-loaded text.
3. **Remove:** the manager writes a tombstone. The next effective generation
   omits the router and guide as one logical item; baseline and override remain.
4. **Restore:** the manager deletes the override/tombstone and emits the current
   installed version on its installed surface, even if that version changed
   since step 1.
5. **Reset:** all active personal overlays and learnings are archived/deactivated,
   personal sources remain recoverable, the recorded install selection returns,
   and the agent-bios-managed effective corpus equals the current installed
   baseline. Manual text outside agent-bios ownership is untouched.

## 12. Implementation stages

### Stage 0 — contract and falsifiable fixtures

- Fix the corpus item scope and reset/secret decisions below.
- Add a feature-off switch.
- Derive the current item/footprint population and store golden source snapshots
  for migration tests.
- Verification gate: the population is non-empty and every current managed
  carrier maps exactly once.

### Stage 1 — stable inventory, no behavior change

- Add immutable item ids and a normalized registry adapter over the current
  monolith/file manifest.
- Make distribution, verification, rollback scope, benchmarks, and status read
  the same inventory.
- Keep the current assembler as the only live writer.
- Gate: duplicate/reused id, unmapped source, unknown surface, stale locator, and
  unowned destination controls all fail by name.
- Done when feature-off assembly is byte-identical on both hosts.

### Stage 2 — package composition and read-only Studio

- Parameterize package validation/composition and activate the first personal
  package root.
- Add list/search/show/diff APIs and read-only Textual wiki/fallback output.
- Namespace package guide paths and validate rewritten refs.
- Done when TUI, CLI, and skill-facing JSON return one inventory revision and
  identical content digests from an npm-only install.

### Stage 3 — personal store and dry-run plans

- Add personal packages, overrides, tombstones, history, plan validation,
  conflict calculation, and import/export.
- Keep live apply disabled.
- Controls cover path traversal, symlinks, arbitrary ids/paths, unknown fields,
  runtime-owned fields, invalid domain/surface refs, stale digests, and empty
  inventories.

### Stage 4 — one live transaction engine

- Route install/onboard/select/edit/remove/restore/reset/rollback through the
  common deploy lock and journal.
- Route learning capture/migration/CRUD through one learning-store lock and
  enforce the single deployment→learning lock order for combined operations.
- Add complete undo, install-baseline snapshots, effective inventory, and new
  verify semantics: compare live files to **effective**, while reporting
  customization separately from drift.
- Crash-inject before/after every journal transition and every reader-surface
  switch. Reverting the fix must make the controls fail.
- Done when real npm installs survive edit → remove → restore → reset without a
  checkout and without touching user/foreign bytes.

### Stage 5 — authoring UX and skill

- Add TextArea edit, outcome surface picker, Preview/Apply, history, conflicts,
  and one `corpus` skill using the plan/apply contract.
- Verify short terminals, keyboard-only paths, dirty-exit prompts, numbered
  fallback, `$EDITOR`, non-TTY JSON, i18n, and sanitized Markdown/link handling.

### Stage 6 — advanced existing surfaces and activation

- Add hook/agent structured editors only after their real consumers are proven.
- Run real global, guide, skill, hook, and agent activation probes, with a
  deployed-but-not-consumed negative control for each.
- If the host cannot provide a proof, narrow the status vocabulary; do not invent
  a successful receipt.

### Stage 7 — lifecycle and opt-in release

- Test upstream-only, user-only, disjoint-field, same-field conflict, upstream
  deletion, invalidated surface, concurrent apply, uninstall/reinstall, reset,
  rollback, and recovery from partial failure.
- Run a real packaged installation from an arbitrary directory.
- Update the ontology, lexicon, surfaces, endpoints, README, package payload,
  current implementation map, and generated mirrors only when the behavior
  lands.
- Keep the feature opt-in until current/default output equivalence and both-host
  E2E are green. Changing the default is a separate decision.

Review gates occur after identity/schema, destructive ownership, host activation,
and migration/rollback. Material design defects must be zero under a criterion
that asks whether a required user workflow becomes impossible, ambiguous, or
lossy; missing implementation in this pre-implementation document is not a
finding.

## 13. Redesign triggers

Return to design if any of these occur:

- stable ids cannot be added without changing package identity;
- the normalized inventory misses any currently deployed instruction class;
- feature-off projection differs from current output;
- a consumer cannot be shown to read the carrier the catalog names;
- personal composition requires a general precedence engine rather than one
  exact-target overlay;
- failure recovery cannot restore all affected reader surfaces;
- reset must touch personal/foreign content outside the declared scope;
- two implementation rounds expose new item kinds or ownership boundaries not
  represented here.

## 14. Non-goals

- A remote corpus registry, trust marketplace, signing system, or network fetch.
- Arbitrary third-party executable hooks/scripts/MCP servers.
- Automatic semantic conflict resolution.
- A general N-layer precedence engine.
- Per-launch corpus profiles or preset-owned content in V1.
- Editing product code/gates as if it were corpus prose.
- Changing or unloading already-running sessions.
- Treating the first-ever installation bytes as restore authority.

## 15. Owner decisions before implementation

The architecture has one default, but three behavior boundaries need explicit
owner confirmation:

1. **Scope:** default is all agent-bios-registered instruction items, including
   personal learnings and the prose parts of existing hook/agent items; manual
   entry text, control machinery, and the always-installed management bootstrap
   remain outside CRUD.
2. **Creation:** default V1 creation is global, guide, and prose-only skill.
   Existing hook/agent content can be edited/removed/restored, but new executable
   or authority-bearing mechanisms are not created.
3. **Full reset:** default is to reset connection settings to the zero-egress
   installed state too. Tokens are warned about and deleted without being placed
   in a recovery archive; personal corpus source and learnings are preserved.

Everything else in this document follows from those defaults.

## Design review record

An isolated same-provider/different-model reviewer checked the six user
requirements plus update conflicts, crash recovery, uninstall/reinstall, and
both-host realization under the task-local criterion “a required workflow is
impossible, observably ambiguous, lossy, or inconsistent with a verified
authority.” Missing implementation and explicit non-goals did not count.

The first pass found two material design failures:

1. the existing independent learning writer could append after the manager's
   read and lose that learning when a stale JSONL snapshot published; and
2. treating the management skill as an ordinary removable skill could remove
   the in-session route needed to restore it.

The design was revised to give all learning operations one store/lock and fixed
lock order, and to make the minimal management skill an always-installed
bootstrap outside mutable corpus content. Re-review reported **0 open
`design_failure` findings**. This is independent review evidence, not
cross-provider convergence; the failed Claude dispatch is recorded at the top.

authority instead of forcing migration, and replaced an assumed universal
