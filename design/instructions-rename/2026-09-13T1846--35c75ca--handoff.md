## Compatibility decisions to close before implementation

Record choices for CLI aliases and removal release; environment-variable precedence and conflicting old/new values; old-state readers versus explicit relocation; mixed-version writers; serialized schema evolution; ontology ID redirects; and reserved operation names. Document supported upgrade/downgrade combinations. These choices are still open; this handoff does not silently authorize deleting aliases or relocating user data.

Prefer one new canonical writer with bounded old-format readers/adapters. Never dual-write independent stores. If both old and new roots exist, stop the affected migration and require a deterministic resolution; never choose whichever looks newer. Preserve custom roots, ownership, permissions, symlink protections, user overlays, learning records, active session pins, and exact historical refs. A display rename does not itself require a schema bump; an incompatible serialized contract does.

Retained compatibility literals need named owners, reasons, and retirement conditions. They are migration interfaces, not a second conceptual name. A blanket `corpus` denylist would incorrectly reject those literals and genuine datasets. Scope any new gate to classified current identifiers and include negative controls; do not buy broad directory exemptions.
