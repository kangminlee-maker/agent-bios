# The Desktop route, end to end, on Claude Desktop 2.16120.0

Evidence, not design. It records one run of the implemented route — the bundle
`DesktopBundle` generates and the server in `compose/app_desktop/server.py` — in a
real Claude Desktop, after the qualification
(`2026-09-30T0645--20084c8--desktop-mcpb-qualification.md`) and against the design
(`2026-09-30T0700--20084c8--design.md`). The code was the uncommitted working tree
on top of `20084c8`; the commit that lands it carries this record.

## Method

The user's own agent-bios installation was not touched. A sandbox installation was
made from the working tree into a scratch `HOME`, state root and user root, with
`builder-base` plus one personal item whose body told the model to say a fixed
phrase when asked. `DesktopBundle.build()` wrote the bundle there (11.21 kB,
unsigned; `mcpb validate` 2.1.2 passed its manifest). Its server, run from the
unpacked bundle under `env -i` with a wrong `HOME`, answered preview from the
sandbox roots its configuration names; an earlier build of the same sandbox, before
a fix to how excluded items are listed, returned the body with the phrase and a final
`agent-bios end` line the same way.

The user installed the bundle in Desktop 2.16120.0 and, in **two conversations
using two different models**, sent in turn: a request to load the agent-bios
instructions, a question asking which phrase the instructions said to use, and a
request to turn agent-bios off. No tool name was given.

## Measured

- **Installation.** Desktop installed it as `local.mcpb.agent-bios.agent-bios` and
  logged `Using MCP server command: /opt/homebrew/opt/python@3.14/bin/python3.14`
  — the absolute interpreter the manifest names, not a `PATH` lookup.
- **Content reached both models.** Both conversations answered with the fixed
  phrase from the personal item; the user pasted both answers. One also cited the
  snapshot path under the sandbox directory, which the delivered body itself names.
- **Tool calls.** Six `tools/call` requests, ids 2–7, all through **one server
  process** started at 03:46:20Z: two `use` (03:46:46, 03:46:48), two `status`
  with an end marker (03:46:55, 03:46:56), two `off` (03:47:48, 03:47:49). The models
  chose each tool from the plain-language request.
- **One identity per conversation.** The two `use` calls carried no identity, so
  `AppSessions` minted two, `desktop-c6d0…` and `desktop-44a2…`, one per
  conversation. Each receipt holds exactly one delivery with its own end marker;
  each marker was reported back by its own conversation and recorded as
  `confirmed_at`; each receipt ends with delivery off. Both deliveries share one
  ContentRef (`2c02c274…`) and record working directory `/`.

So one long-lived process served two concurrent conversations, and the minted
identity — the only thing that told them apart — kept their receipts separate.

## Not measured

- Which Desktop client carried the calls. Desktop's log does not name it and the
  receipts do not record it.
- A repeated `use` inside one conversation with its `session_id`, i.e. the repeat
  path in Desktop. The unit tests exercise it; Desktop did not.
- A tool call through the `local-agent-mode` client, Windows, and `roots/list`.
- Whether the text stayed inline. The confirmations prove only that each model
  reported the last line; at about 15 kB the body is far below every boundary seen.

## Got wrong first

Reading the two identities from the receipts and Desktop's log alone, this session
first concluded that one model had called `use` twice and dropped its identity. The
log could not distinguish that from two conversations, because both were served by
one process with consecutive ids; the user supplied the fact that settled it. A
receipt that recorded which conversation it belonged to could have, but Desktop
provides nothing to record.
