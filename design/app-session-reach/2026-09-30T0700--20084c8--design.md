# Reaching a session agent-launch did not start

Target design. Nothing here is implemented; no statement below describes current
runtime behavior. Its evidence is two dated records:
[the Desktop probe](2026-09-29T2010--76b84b4--desktop-mcp-probe.md) against
**Claude Desktop 2.9939.4**, and
[the `.mcpb` qualification](2026-09-30T0645--20084c8--desktop-mcpb-qualification.md)
against **2.16120.0**. Their figures are claims about those builds: compare the
version string and re-probe before treating any constraint here as current. One
of the first record's findings — the 48 KiB inline boundary — did not survive the
update.

This snapshot supersedes `2026-09-29T2015--76b84b4--design.md`. It changes five
things, each forced by the qualification: the end marker proves the end was seen,
not that it arrived inline; the byte ceiling discloses rather than blocks; the
bundle is generated per installation and names its interpreter; `AppSessions`
mints the conversation identity Desktop does not send; and Desktop delivery
resolves with no project scope.

Where this design relies on something the probe did not test, it says so in the
sentence that relies on it.

## The purpose this serves

agent-bios exists so workers can compose, share and inherit team work
environments, and continue the work when a worker, model, session or device
changes. A desktop app is that device change.

An environment reaches a session today by one of two routes: `agent-launch`
projects it at startup, or a Codex app task pulls it explicitly —
`compose/instructions_app.py` `AppBridge` registers a skill at
`~/.agents/skills/agent-bios`, and `AppSessions` returns the selected snapshot on
use (`SURFACES.md:52` lists that as its own delivery surface). Claude Desktop has
neither: no launch to project into, and no registration path of the kind the
Codex app uses. Moving there loses the environment — not because the worker chose
differently, but because no route reaches that host.

## Relation to the Team work-environment SSOT

This initiative is a delivery route, not a redefinition of the environment model.
[`design/knowledge-and-history/CURRENT.md`](../knowledge-and-history/CURRENT.md)
remains the SSOT for what an environment is and how a consumer is asked. Its
§s06 consumer-interaction rule — native forms preferred where qualified, a
verified conversation fallback, otherwise `pending_user` — governs the choice
question below, and this document applies that rule to one host rather than
restating it.

## The goal is not injection

The obvious framing — inject the environment when the session starts — is not
available here and is also not what this repo decided for apps. `SURFACES.md`
separates *activated startup instructions* (`SURFACES.md:190`) from *app task
context* (`SURFACES.md:223`), and the app route was built as explicit in-task
pull: each task begins with delivery off (`SURFACES.md:227`), and the snapshot is
returned only on request.

That framing also answers the second half of the request. **A session already in
progress cannot be pushed to.** This is an argument, not a measurement: MCP gives
a server no way to insert content into a conversation, and the probe found no
mechanism that would. What is achievable is a surface present in every session
and pullable at any turn. The goal is *always present, pulled on request*, and
that wording has to survive into whatever ships, because a claim to have injected
into a running session would be false.

## The carrier: a local MCP server

Measurement leaves one candidate on this host.

| Mechanism | Verdict |
| --- | --- |
| Hook | No hook system exists in Desktop (asserted, not probed). Independently, `SURFACES.md:330` admits only a machine-detectable trigger carrying one to three lines; a work environment is neither. |
| Skill | **No stable root to install into.** Desktop does have skills trees, and the standard `.claude/skills/` path is live inside them — but its local agent mode is bundled Claude Code running against a *per-session* configuration home, not the user's `~/.claude/`, and the managed tree is Anthropic-provisioned (88 of 88 entries). Every location is either managed or created after the session starts. |
| MCP server | The local extension surface confirmed working end to end, by measurement. |

**The MCP server is chosen because it is the route that was measured working.**
The skill row reached its verdict twice. An earlier draft excluded it on the
ground that Desktop had no skills directory — wrong, from a top-level listing that
never descended to the tree two levels down (`D-20260929-a368a7` reopened it on
that correction). Measuring it properly closed it again for a different and
sounder reason: the trees exist and the mechanism works, but agent-bios has
nothing to install into ahead of time, because every root is either
Anthropic-provisioned or created when a session starts (`D-20260929-b275d6`).

What remains untested is whether a skill written into a live session home is
honoured, and whether any pre-session seeding point exists. Neither is a route
agent-bios could ship against today, so neither blocks this design; both are
recorded as the conditions that would reopen it.

`SURFACES.md:317` already carries an *MCP tool surface* entry, but it describes
agent-launch **configuring** servers for a session it launches
(`review_mcp_servers`, `launch/agent-launch.py:10208`). agent-bios becoming a
server is a different surface and needs its own `SURFACES.md` entry with its own
admission bar before this lands. `DEPENDENCIES.md` currently states "App
instructions context delivery does not add an MCP server"; that sentence becomes
false on the day this ships and must change in the same commit.

### Installation route: `.mcpb`, and why not the config file

Two routes exist, and the probe used the one this design rejects.

Registering into `~/Library/Application Support/Claude/claude_desktop_config.json`
works — it is how every measurement was taken, and it is what `Claude Extensions`
shows is not the only shape an extension takes there (eight of its ten entries are
directory-sourced `ant.dir.*`, two are `.mcpb`). It is rejected anyway: that file
is the host's own configuration, and writing it would put agent-bios into the
business of editing a native host config it does not own. That is the same
boundary `SURFACES.md:220` keeps for global `AGENTS.md` and `CLAUDE.md`, and the
same reason private installation preserves native instruction files
(`AGENTS.md:355`). A `.mcpb` bundle is installed by Desktop's own mechanism,
which leaves the write set where it belongs.

**The route is qualified.** A Python-type `.mcpb` bundle installed through
Desktop's own mechanism on 2.16120.0 saw the same two clients, the same
capabilities and the same protocol revision as the configuration-file probe, and
returned the real instruction body intact.

**The bundle is generated per installation and names its interpreter.** Desktop
resolves the manifest's `command` through the user's login-shell `PATH` and ships
no Python of its own. A bundle naming bare `python3` runs on whichever interpreter
comes first there — 3.14 on the measured machine only because Homebrew precedes
`/usr/bin`, whose `python3` is 3.9.6, below the 3.11 agent-bios needs. So the
bundle is not a static file in the npm payload. agent-bios writes it at
installation time, with `mcp_config.command` set to the absolute interpreter that
runs agent-bios itself — the same interpreter the Codex bridge hands its session
commands (`compose/host_platform.py` `python_argv`) — and the private roots in a
configuration member, as `AppBridge` does for its generation. The file is
content-addressed under the private state root; agent-bios reports its path and
the user opens it, so Desktop's own installation dialog is the only step that
writes into Desktop.

A remote MCP server is closed separately: `ENDPOINTS.md` records that a default
install configures no ingestion endpoint (`ENDPOINTS.md:133`), and a delivery
route that required network egress would contradict that default.

## It carries no new authority

The server is a transport at the same layer as
`compose/app_bridge/scripts/bridge.py`. Snapshot selection, ContentRefs, receipts
and their storage stay owned by `compose/instructions_store.py` and
`compose/instructions_app.py` `AppSessions`.

A resident process is what threatens that claim, and it needs a mechanism rather
than an intention. `bridge.py` resolves the confirmed release on every call, so a
package update takes effect on the next call. A long-lived server that resolved
once at startup would keep superseded code answering as though it were current.
**The server must resolve the confirmed release per request, not per process**,
and must hold no state across requests — which also makes the 2026-07-28
migration below a no-op. Concurrent processes are a given, not an edge case: the
probe observed nine server processes for one registration, so store access must
go through the existing transaction locking rather than assume a single writer.

The Codex app skill does not change. It works, and rewriting a working path for
symmetry buys nothing.

## Tool surface

Four tools mirroring the four session operations `AppSessions` declares
(`compose/instructions_app.py:440`): **status**, **preview**, **use**, **off**.
`use` returns the selected snapshot text as tool output under the existing
`returned-as-context` contract (`compose/instructions_app.py:414`), which states
that text was returned through the tool path, not that a native startup injection
or model reading was verified.

**The conversation identity comes from `AppSessions`, because Desktop sends
none.** Every `tools/call` on both measured versions carried only `name` and
`arguments`: no `_meta`, no conversation or task identifier. The Codex app
supplies `CODEX_THREAD_ID`; Desktop has nothing equivalent. So `preview` and
`use`, called without one, return a fresh identifier minted by `AppSessions`, and
the model passes it back on later calls in the same conversation; `status` and
`off` require it. Minting belongs to `AppSessions`, not the server, for the same
reason receipts do (`SURFACES.md` "Owning its deterministic values"). `preview`
writes nothing, so minting there has no side effect. An identifier the model
drops or invents costs at most a second receipt for the same conversation; the
confirmation rule below keeps such a receipt from counting as a delivery.

Those four are not the bridge's whole surface. `bridge.py` dispatches eight
top-level commands — `setup`, `session`, `instructions`, `corpus`, `import`,
`learn`, `bootstrap`, `tui` — and only `session` reaches `AppSessions`. The other
seven are management and setup routes that belong behind the bootstrap procedure,
not in a tool list every turn.

Four is a budget, not a minimum. `SURFACES.md:323` names the failure mode for a
launched session — a registered server the plan never selected "costs tool-list
tokens in every turn of the session, and nothing ever calls it" — and
`SURFACES.md:58` scopes that cost to the one session that registered it. **This
design extends that cost:** a `.mcpb` bundle is installed once and is present in
every Desktop session, so its tool list is paid for by sessions that will never
call it. That extension is this document's inference from the installation model,
not a quotation, and it is the reason the budget is four rather than eight.

## Which environment `use` returns

Neither Desktop client declares `elicitation`, so the server cannot ask through a
native form — the first of the three ranked paths in
[the mechanism review](../knowledge-and-history/2026-09-15T1026--35c75ca--consumption-mechanism-review.md)
(lines 76–78) is unavailable here.

Its second path **is** ordinary conversation, and the review admits it (lines
80–85) on one condition: the connector must be able to confirm the real user
message and response, using the host's own response-event boundary. A model
writing `user_confirmed=true` into a tool argument is not a user's answer (lines
82–84), and a path that cannot distinguish host-autofilled input from real user
input is not accepted as verified (lines 92–94).

**That condition is what an MCP server in Desktop cannot meet, and that is this
document's finding rather than the review's.** The server sees tool calls; it
never observes the user's message or the host's response event, so it cannot
confirm that an answer relayed in a tool argument came from the user. The review
scopes this requirement to decision-record selections specifically (lines
109–111), so it binds the decision question rather than every choice — but the
environment selection is exactly the kind of choice it is about.

**Decision: `use` returns the saved installation selection by default, and an
explicit request naming a selection authorizes that selection for that call.**
This is exactly the contract the Codex app skill already operates
(`compose/app_bridge/SKILL.md`), so both hosts behave alike and no new concept is
introduced. Naming a selection in conversation is an ordinary user instruction,
not a claim of verified consent, and nothing here grants the model authority to
select on the user's behalf.

**No project scope on this route.** Imported instructions can be scoped to a
project root, and the store includes them only when the working directory lies
inside that root (`compose/instructions_store.py` `_selected_items`). Desktop
names no project: the server starts in `/`, and the chat client declares no
`roots`. Desktop delivery therefore resolves with no project context — global
and core items only — and states that in its result, rather than letting `/` or
the user's home stand in for a project by accident. The exclusion is recorded
with its reopening condition: a qualified `roots/list` from the
`local-agent-mode` client, or an explicit project argument the user names.

The review's third path — hold the use and resume when an answer can be obtained
(lines 87–90) — does not arise, because this route collects no new selection. It
would arise the moment a decision question is routed through this server, and
that is a separate design, not an extension of this one.

`user_config` at install time is **not** chosen. It would fix one binding for the
life of the installation, converting a per-task selection into an install-time
constant, which narrows the selection boundary the product exists to preserve.
It is also unmeasured — whether Desktop renders that form was never tested.

## Constraints the measurement imposes, and the mechanism for each

**Body size — the boundary moves between versions.** On 2.9939.4, results above
49,152 bytes were saved to a file that the model read from disk. On 2.16120.0,
50,176 and 65,536 bytes of the same text arrived in the message body, and so did
the real body repeated six times (140,666 bytes). Whether the update or the
installation route moved the boundary is not separated. No fixed byte count is a
property of Desktop.

The body this design sends is **23,434 bytes** for the saved installation
selection on the measured machine (release 0.19.2), under half the smallest
boundary ever observed.

**The end marker proves the model saw the end, not that the text arrived
inline.** On 2.9939.4, file-delivered payloads came back with their END lines
correct too, because the model read the end of the saved file. So the marker
confirms a complete reading, and only the model's own words distinguish body from
file. The mechanism keeps the marker for what it can prove: `use` ends the body
with a marker line carrying a nonce, the receipt records it, and `status` accepts
the marker the model saw. That is `SURFACES.md`'s fourth kind of control, "make it
not count": a delivery whose marker was never reported back is reported as
unconfirmed, and nothing claims it reached the model. The receipt never claims
inline delivery.

**The byte ceiling discloses; it does not block.** A compose-time check against
49,152 bytes — the smallest boundary observed on any version — stays, with its
own negative control, but it reports that the host may save the text to a file
rather than refusing the delivery. On the current version a body that size
arrives inline, and refusing it would withhold text the host would deliver.

**Idempotency.** Desktop retried a failing call four times while reporting two
failures. MCP `tools/call` carries no idempotency key, so a retried `use` and a
genuine second `use` in the same conversation are indistinguishable from the wire
alone. The mechanism: `AppSessions` — not the server — decides duplication, from
the minted conversation identity, the requested selection and the resolved
ContentRef. A repeat of the latest recorded triple returns the text again with
the existing receipt instead of appending a second delivery, because a retry
exists precisely when the first result may not have arrived. A retried `use` that
carried no identity mints a second one and leaves a second receipt; its marker is
never reported back, so it stays unconfirmed and does not count. The owner is
named that way deliberately: a transport that minted its own receipt identity
would be the new authority this design says it is not (`SURFACES.md` "Owning its
deterministic values").

No retry of a *successful* call was observed, so this is a defence against an
observed failure-retry pattern, not a measured duplicate-delivery bug.

**Two clients, different capabilities.** Desktop runs a chat client and a
per-server local-agent-mode client on both measured versions; only the latter
declares `roots`, and **no measurement has exercised `roots/list`**, so nothing
establishes that a root can actually be retrieved. Scope therefore resolves
without roots (above), with roots as an unproven refinement to qualify
separately. No tool call through the `local-agent-mode` client has been measured
either.

**Distance from host limits.** On 2.9939.4 — not re-measured since — the
transport ceiling sat between 16,793,600 and 17,825,792 bytes, an oversized call
could lose the session until Desktop restarted, and failures there reported a
server that was not ours. The design stays far from
that region and must not rely on host error text to explain itself.

## Protocol target

**Implement 2025-11-25.** Desktop 2.9939.4 sent it on all seven handshakes, and
2.16120.0 on all eight in the qualification; neither ever used the 2026-07-28
shape, against probes shown by positive control to detect it.

The current standard is 2026-07-28. Its deltas, from a dated reading of the
specification rather than from this probe (sources listed in the evidence
record's *Asserted* section), are worth recording now:

| Area | 2025-11-25 | 2026-07-28 |
| --- | --- | --- |
| Lifecycle | one `initialize` / `initialized` handshake | no handshake; each request carries `_meta` with protocol version, client info and capabilities, and a server may not infer capabilities from an earlier request |
| Asking the user | server-to-client request | an `input_required` tool result carrying `elicitation/create`, modes `form` and `url` |
| Missing capability | unspecified | `-32021` carrying `requiredCapabilities`; `-32022` for an unsupported version |
| Subscriptions | per-transport mechanisms | one `subscriptions/listen` |
| Batching | — | none |

The lifecycle row is the one that bites, and the per-request resolution rule
above already satisfies it: a server holding nothing across requests has nothing
to migrate.

## What must change with it

Shipping a server makes several current statements false. They are listed here so
the change lands as one commit rather than a trail of stale sentences, and the
gated column says which would stop a commit and which would simply go quiet.

| What | Why it moves | Enforced? |
| --- | --- | --- |
| `DEPENDENCIES.md` — "App instructions context delivery does not add an MCP server", and its neighbour "only a selected capability declaring `mcp-stdio-v1` is registered by the launcher" | both describe a world with no agent-bios server | **No.** Only `gates/check_parity.py` reads the file, for one unrelated string, and `gates/check-package.sh` excludes it by name. This sentence would go stale silently |
| `ENDPOINTS.md:226` — "`compose/instructions_app.py` registers no network service"; `:178` — "no TTY, Textual, MCP/HTTP server or model SDK" | a stdio server is not network egress, but both sentences say more than that | Partly. `gates/check-endpoints.py` anchors wire literals and the zero-egress default, not this prose |
| `SURFACES.md` — a new surface section with its own admission bar | agent-bios becoming a server is not the existing *MCP tool surface* entry | **Yes, blocking.** `gates/check-surfaces.py` fails an **Authority** path that does not resolve, and fails an `install.sh` deploy source no surface claims |
| `package.json` `files[]` | any runtime path the installer reaches | **Yes, blocking**, both directions (`gates/check-package.sh`) |
| `ontology/instances/graph.json` §lexicon, then `LEXICON.md` by regeneration | a new concept needs a term and a declared home | **Yes** (`gates/check-lexicon.py`, `ontology/check-ontology.py`) |

The first two rows are the ones to watch, because nothing would catch them.

**And the one blocking gate has a hole this design would fall straight through.**
`gates/check-surfaces.py` derives its subject set by regex over `install.sh`'s
`deploy_file` / `deploy_glob` / `deploy_tree` call sites
(`gates/check-surfaces.py:115-123`) and fails any extracted source no surface
claims. A server that never passes through a deploy call — **a `.mcpb` bundle
assembled outside that path, which is exactly what this design proposes** — is
invisible to it and to every other gate above. Choosing the packaging that keeps
the write set clean also chooses the packaging the surface gate cannot see, and
that trade has to be paid for deliberately rather than discovered later.

Two ways to pay it, and this repo's own rules prefer the second. Gating the
sentence is possible — whether a tree speaks MCP is decidable from source — and
would need the two properties the repo insists on: a non-empty subject-set
assertion, because "no MCP server found" is satisfied by scanning nothing, and a
`--self-test` that plants a server file and requires failure by name.
`gates/check-endpoints.py` is the nearest template, and its docstring states the
principle that matters here: "Consumption is checked, not just declaration … a
dead constant would anchor a live claim" (`gates/check-endpoints.py:10-14`).

But *Where authority lives* holds that a gate carrying its own copy of a value is
a third restatement, not a guard, and that a one-sided edit should be made
impossible rather than merely detectable. The launcher half of these MCP facts
already has an owner — `review_mcp_servers` and the `mcp-stdio-v1` capability
declarations in `launch/agent-launch.toml`. Giving the app-delivery half a
declared inventory in the same place and **generating** the `DEPENDENCIES.md`
paragraph from it — the pattern `LEXICON.md` and the README purpose block already
use — removes the drift instead of watching for it. That is the version to bring,
with the gate as fallback if no single owner fits.

This work belongs with the server slice, not before it. Until agent-bios ships a
server the sentence is true; the debt is that nothing would say when it stopped
being true.

The `why` field of `D-20260929-7b1589` also repeats the two Desktop observations
that review later corrected; the ledger is append-only and content-bound, so that
record stands as written and `D-20260929-a368a7` carries the correction.

## Open

- `io.modelcontextprotocol/ui` (`text/html;profile=mcp-app`) is the only
  interactive surface either client declares and was never exercised by any
  server on the probed machine. It is the candidate for a chooser equivalent to
  the launcher's terminal interface, is excluded from the first slice, and needs
  its own qualification.
- Whether a skill written into a live per-session config home is honoured, and
  whether Desktop exposes any pre-session seeding point. Neither is shippable
  today; both would reopen the skill route.
- Whether one server process serves both the Codex app and Desktop, or the Codex
  skill keeps its own helper.
- Where the inline boundary now lies on 2.16120.0; 140,666 bytes is the largest
  delivery seen, and nothing became a file.
- Whether the `local-agent-mode` client calls tools the way chat does.

## Alternatives this closes

- **Writing the snapshot into the native global `CLAUDE.md` or `AGENTS.md`.**
  Private installation preserves native instruction files (`AGENTS.md:355`) and
  `SURFACES.md:220` keeps them outside the app bridge's write set. It would also
  impose content on sessions that never selected it.
- **Registering into `claude_desktop_config.json`.** Same boundary, applied to the
  host's own configuration file.
- **A remote MCP server.** `ENDPOINTS.md:133` records that a default install
  configures no ingestion endpoint.
- **Hook-based delivery.** No hook system exists in Desktop, and the surface's
  admission bar excludes bodies of this size regardless.
- **A static bundle naming bare `python3`.** Desktop resolves it through the
  user's `PATH`, which on stock macOS reaches 3.9.6; the generated bundle names
  the interpreter instead.
- **Leaving Desktop conversations without per-conversation receipts.** It would
  remove `off` and duplicate detection for this host; the minted identity keeps
  both.
- **Letting the model invent the conversation identity.** Identifiers are the
  tool's deterministic values, not the model's.
- **Refusing a body over 48 KiB.** The boundary moved between versions; the
  ceiling now discloses.
- **Using the server's working directory as project scope.** It is `/`, an
  accident of the launch, not a project the user named.
- **A Desktop skill mirroring the Codex app registration.** Closed on the second
  attempt and for a different reason than the first: not that no skills directory
  exists — it does — but that every root Desktop uses is Anthropic-provisioned or
  created after a session starts, leaving nothing to install into ahead of time
  (`D-20260929-b275d6`; the first, wrong reason and its correction are
  `D-20260929-7b1589` and `D-20260929-a368a7`).
