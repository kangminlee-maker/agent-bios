# Backlog — one hook body for both hosts

User-approved backlog item (2026-08-19): unify the hook configuration across Claude Code
and Codex. Not scheduled; a design session gates any build. Written during the
criterion-stage build; the probes below are this record's value — they were run against
the live binaries today, and every claim here decays with the next CLI release.

## What was measured (2026-08-19, this machine)

- **Codex hooks exist and are config-parsed**: codex-cli 0.146.0's `config.toml`
  recognizes `hooks` (`expected struct HooksToml` on a planted wrong type — probed with
  a scratch `CODEX_HOME`, no API call). `codex exec` registers
  `--dangerously-bypass-hook-trust`, and a `bypass_hook_trust` boolean exists as a
  config override.
- **The payload vocabulary is Claude's**: the binary (`/opt/homebrew/bin/codex`,
  Mach-O arm64 — note `which codex` resolves to TWO wrapper layers on this machine,
  the agent-launch shell function and `~/.superset/bin/codex`) carries
  `hook_event_name`, `hookEventName`, `hookSpecificOutput`, `stop_hook_active`, an
  `additionalContext` disk-spill threshold (default 2,500 tokens), and handler kinds
  `"type": "command"` / `"type": "prompt"`. It describes itself as an extension:
  "Codex extension: expose the active turn id to internal turn-scoped hooks."
- **The event names are Claude's**: PreToolUse, PostToolUse, SessionStart, SessionEnd,
  Stop, SubagentStop, PreCompact, UserPromptSubmit all appear as strings. Strings are
  not firing: the superset wrapper (dated 2026-08-12) works around "Codex has no
  SessionEnd hook" while the binary carries the SessionEnd string — version drift or
  schema-compat-only, and only a live probe decides which.
- **A live precedent exists on this machine**: the superset wrapper feeds a shared
  script Claude-shaped payloads (`{"hook_event_name":"SessionEnd"}`) around codex via
  `--enable hooks` — its comment says "hooks (formerly codex_hooks) is stable and
  default-enabled in codex".
- **Trust gate**: hooks require persisted hook trust ("hooks are new or changed"
  prompt); "hook stopped execution" exists as a string (blocking semantics plausible);
  plugin scaffolding has `--with-hooks` and a `hooks.json`.

## The design shape this evidence points at

Hook BODIES become one tree serving both hosts — the `claude/skills/` precedent (one
tree, host-specific deploy), not the `codex/` mirror precedent — because the stdin JSON
contract is the same vocabulary. Registration stays host-specific: `install.sh` writes
Claude's `settings.json` hooks block today and would gain a codex leg (config.toml
HooksToml). `compose/domains.json` `hooks[]` already owns hooks by name, so
classification is unchanged. The adapter-split constraint (hooks are core-only, never
in packages) is untouched — one body, still core-owned.

## Prerequisite probes before any build (probe-over-docs; strings prove vocabulary, not behavior)

1. Per-event live firing + payload field diff: register a hook that dumps its stdin to
   a file, run one `codex exec`, compare fields against Claude's payload for the same
   event. PreToolUse parity is the one that matters first (`tooling-gotchas-hook.py`
   is the only shipped hook).
2. Blocking and output semantics: exit-code contract, `additionalContext` injection,
   whether Codex honors the same decision fields (its PermissionRequest hooks
   "fail closed" on reserved fields — a semantics difference to map, not assume).
3. The trust path for unattended installs: how trust is persisted, whether an
   installer can or should pre-trust, and whether the honest path is a documented
   one-time confirmation instead — `bypass_hook_trust` is flagged DANGEROUS and is not
   the default answer.

## Constraints carried from the corpus

Every capability claim above is version-bound (codex-cli 0.146.0, Claude Code 2.1.235);
a build gates on fresh probes, never on this record. Risky/behavior-changing: the codex
registration leg lands default-off with the current Claude-only behavior preserved when
off.
