# The repo layer, and why the SWE mode has nothing in it

Decided in conversation on 2026-08-13, in this order: build for the repo layer,
cover **a new repo and an existing one**, and deliver it as a **skill** — which
means standing up skill packaging, since this repo has never shipped one. An
earlier draft in this same conversation proposed a guide plus a launcher preset;
§3.5 records why that was replaced, because the reasoning is the reusable part.

Nothing here is implemented. Every number is a claim about the tree at `8e7c44e`;
re-derive with §8 before building on it.

## 1. The gap, from code

`agent-bios` deploys the **global** layer and configures the **session** layer.
It has nothing for the **repo** layer.

| Layer | Handled? | Where |
| --- | --- | --- |
| Global | yes | `claude/CLAUDE.md` → `~/.claude/central/bundle.md`, guides, agents, hooks |
| Session | yes | `launch/agent-launch.toml` presets — tiers, review contract, delegation |
| **Repo** | **no** | nothing writes or reasons about a project's own instruction files |

Two confirmations:

- `agent-bios onboard` (`install.sh:966`) is domain-package selection, install,
  and an activation canary. It never looks at a repo.
- Nothing in `install.sh`, `compose/assemble.py`, or `launch/agent-launch.py`
  writes outside `$HOME`.

**This is why the Software Engineer mode is `vanilla` and nothing else.** Exactly
one preset carries `mode = "software-engineer"`, and its own description is "no
launch contract, no tier bindings, standard permissions — exactly what the bare
backend gives you". The other four are `mode = "builder"` and bind session-layer
things (tier fan-out, review methods, delegation). An engineer working in someone
else's repo needs the repo layer, so the mode has nothing to offer. The empty
preset list is the symptom; the missing layer is the cause.

## 2. The research already in this repo

`research/agents-md/` studied 12,749 instruction files and its layer model
already reached this conclusion. `LAYERS.md` §3 carries the five repo-purpose
types and the category mix each needs — reuse that table rather than re-deriving:

| Repo purpose | Categories that must be thick |
| --- | --- |
| Library / framework (accepts outside contribution) | `contribution-protocol` + `completion-gates` + `hard-boundaries` |
| Application / product | `project-invariants` + `pitfall-warnings` + `cochange-duties` |
| CLI / single-author tool | `repo-orientation` + `project-invariants` + `task-procedure` |
| Monorepo / platform | `context-routing` + `task-procedure` |
| Content / docs | `repo-orientation`, minimal |

Four findings from `REPORT.md` that decide content:

- **§5.1** — AGENTS.md leads 12 of 13 categories; CLAUDE.md leads only
  `repo-orientation`. AGENTS.md is a discipline document, CLAUDE.md an explainer.
  This repo's own root is already that shape. So **the output is AGENTS.md as the
  body, CLAUDE.md as a shim** where the host needs one.
- **§5.4** — the built-in `init` scaffold writes a sentence with zero instruction
  content, appearing roughly once per file across the corpus. It produces form
  without content, so **what we add is a procedure that extracts content, never a
  template**. A generator would reproduce the documented failure.
- **§5.3** — `human-authority` is the industry's largest hole at 6.7% adoption,
  lowest of 13. People write prohibitions but not escalation paths. Ask for it.
- **§5.5** — circulated rule packs get pasted wholesale, and a file's name does
  not indicate its target tool. Read what the repo does; do not inherit a pack.

Note the built-in `init` skill cannot be improved in place: it ships inside the
CLI and exists nowhere on disk (checked under `~/.claude` and `~/.codex`).
Overwriting it would mean owning someone else's file, and a CLI update would undo
it. The only available move is to put something better beside it.

## 3. What gets built

### 3.1 A skill

One skill, deployed to both hosts. Format is identical on each — verified
2026-08-13: `SKILL.md` with `name` + `description` frontmatter, prose body, and
free-form subdirectories (`~/.claude/skills/humanize-korean/` uses `references/`,
`~/.codex/skills/onto/` uses `entrypoints/`).

Content, in priority order:

1. Determine the repo's purpose type, then the category mix (§2 table).
2. AGENTS.md is the body; CLAUDE.md is a shim.
3. For an existing repo: **read the invariants and traps out of the code.** This
   is the substantive half and the part no template can do.
4. Ask for `human-authority` explicitly.
5. Ban the zero-content preamble.
6. Directory-scoped files **only for the monorepo/platform type**.

On the last point: a directory-scoped `CLAUDE.md` is injected when a file beside
it is touched — verified in-session on 2026-08-13 by creating one, reading a file
next to it, and watching its content arrive. It fires on contact rather than on
recognition, which is why it survives a compaction that drops the session's early
context. But its value concentrates in the monorepo type (corpus:
`context-routing` 0.62 at 50k+ stars), so it must not be recommended generally.

### 3.2 What the skill must NOT contain

The skill is corpus; its output is not. Keeping that line is the whole safety
argument, so it is a build constraint rather than a note.

| | Owner | Lifecycle |
| --- | --- | --- |
| The procedure (§3.1) | agent-bios | versioned, updated, pruned — ordinary corpus |
| The repo's AGENTS.md it produces | **that repo** — its team, contributors, git history | none of ours |

Consequences, each one a rule for the build:

- **No copyable boilerplate in the skill.** Text meant to be pasted into a repo
  file is exactly the §5.5 failure, and shipping it would make agent-bios a
  producer of the phenomenon its own research documents.
- **No agent-bios marker or version stamp in the output.** A stamp implies the
  file will be updated later, and there is no mechanism that could — corpus
  lifecycle (`versions`, `rollback`, `applied status`, `migrate-learnings.py`
  pruning) cannot reach into someone's project.
- **A produced repo file is never a deploy or prune target.** This is what keeps
  the feature from opening a new authority area.

The global rule this descends from is already in the corpus: *"keep
differently-owned state separate: never colocate deploy-managed and user-owned
data in one overwrite-managed file."*

### 3.3 Skill packaging, which does not exist yet

`agent-bios` has never shipped a skill: nothing skill-related in `package.json`
`files[]`, and no skill handling in `install.sh` or `compose/assemble.py`. The
model to copy is how agents and guides deploy — `deploy_glob "$REPO/codex/agents"
"*.toml" "$CODEX_DIR/agents"` in the installer, `copy_filtered(src_dir, names,
dest, rewrite=...)` in the assembler — but two things genuinely differ:

1. **A skill is a directory, not a flat file.** Every existing deployment target
   is a glob of flat files (`*.md`, `*.toml`) with an explicit `names` list. A
   skill carries `SKILL.md` plus arbitrary subdirectories, so both the installer
   and the assembler need a recursive copy path, and `check-package.sh` needs to
   judge a subtree rather than a filename.
2. **The scan path is shared, and this repo already paid for that once.** Hooks
   moved to `central/hooks/` in v0.9.8 precisely because `~/.claude/hooks` holds
   other tools' files. Skills cannot make that move — the host scans
   `~/.claude/skills/`, and this machine already has 7 there from unrelated
   sources (plus 28 under `~/.codex/skills/`). So ownership must be tracked the
   way the hooks fix ended up doing it: **by manifest name, not by path marker**,
   with uninstall removing only the named entry. The skill's name is therefore a
   collision surface and must be chosen as one.

Open sub-questions for the build: whether a skill needs the guides' path rewrite
(`${CLAUDE_CONFIG_DIR}` ↔ `${CODEX_HOME}`) and therefore an `emit-mirrors.py`
projection, or whether one identical copy serves both hosts; and which
`compose/domains.json` domain it belongs to.

### 3.4 A surface the catalog is missing

`SURFACES.md` declares itself "the current **full** set of delivery surfaces" and
lists 13 (global bundle, guides, hook injection, launch contract, agent body,
agent description, personal learnings, MCP tool surface, incubator ledger, and
four control kinds). **Skills are absent** — from a catalog whose stated job is
completeness, for a surface both hosts support and of which this machine has 35
installed. Add the entry with the rest of this work: what it admits, what it
refuses, how it fails when misused.

The repo layer needs an entry too, and it is a different kind from all 13: those
are surfaces agent-bios *fills*; a repo's AGENTS.md is one it *teaches how to
fill*. That distinction is §3.2 restated as catalog vocabulary.

### 3.5 Detecting the empty repo — deterministically, and without crying wolf

The SWE mode already *declares* the precondition. `launch/agent-launch.py:74-75`
defines the mode as "repo-scoped work under the project's own AGENTS.md/CLAUDE.md",
and **nothing ever checks that those files exist**. The check belongs where the
claim already is.

Split it by what is decidable:

| Question | Decidable? | Owner |
| --- | --- | --- |
| Is cwd a git repo; do AGENTS.md / CLAUDE.md exist? | **yes** — file presence | launcher code, at preflight |
| Does *this* repo need a charter? | no | the model and the user |

So the launcher injects **a fact, once** — "this repo has no instruction file;
the `repo-charter` skill exists" — into the contract, and stops there. It does not
instruct the model to invoke anything. A prose surface cannot control (`SURFACES.md`,
"The one boundary"), and this repo's routing mistakes have all been the same shape:
writing a prohibition where a denial was available, or an instruction where only a
fact was true.

**The false-positive risk outranks the forgetting it prevents.** Absence is often
correct, by this repo's own research: `REPORT.md` §5.2 finds AI-contribution
governance only in high-star infrastructure repos and **absent from personal
repos**, and `LAYERS.md` §3 classes content/docs repos as needing an instruction
file barely or not at all. Add the ordinary case of fixing one line in someone
else's project, where §3.2 says the file is not ours to create. A prompt that fires
on every repo without the file would be wrong most of the time, and a check people
learn to ignore is worse than none.

Two containments follow: fire only in SWE mode, where the precondition is already
declared, and have the skill body itself state that many repos correctly have no
instruction file, so the first question is whether one is warranted.

Scope note: this puts **a new kind of input into the launcher**. `agent-launch.py`
reads configuration today and has never looked at the working directory. Treat it
as its own increment with its own negative control (a repo *with* AGENTS.md must
produce no fact line).

### 3.6 Why a skill, and not the guide-plus-preset this draft started with

Recorded because the reasoning generalizes to the next surface choice.

| Axis | Guide + preset | Skill |
| --- | --- | --- |
| Granularity | session-wide (tiers, review, permissions) | **one task** — writing a charter is something you realize mid-session, not a mode you open the session in |
| Activation | pick in launcher, then type a trigger | **description always registered, body loads on call** — no global budget spent, and no trigger token to invent |
| Reach | SWE-mode sessions only | **any mode** — a builder session edits other repos too |
| Cost | infrastructure already exists | **infrastructure must be built** (§3.3) |

The preset would also have needed a new trigger token (`distill!` is taken); the
skill answers that by being callable by name. The one thing the preset had going
for it was that guides already have four-tree parity, domain classification, and
mirror generation. That is the cost being accepted here, and the reason it is
worth accepting is that skill packaging is reusable and the catalog gap in §3.4
is real regardless.

## 5. Build order and verification points

1. Skill packaging first, with nothing in it but the smallest real skill — a
   subtree that deploys, appears in the manifest by name, and uninstalls cleanly
   without touching the other 7 (claude) and 28 (codex) entries.
2. Write the skill body (English) → self-review against §3.2's constraints.
3. Settle the name and the concept path.
4. Register in `compose/domains.json` → `compose/check-domains.py`.
5. `SURFACES.md`: add the skill surface and the taught-not-filled distinction.
6. Korean side + mirror rule, once §3.3's rewrite question is settled.
7. Full gates: `./gates/check-parity.sh`, `gates/check-package.sh`,
   `gates/check-lexicon.py`.
8. **Negative controls**, all three:
   - remove the skill subtree from `files[]` and confirm `check-package.sh` fails
     by name (this is the leg that does not exist yet — a directory subject);
   - plant a foreign name in the manifest and confirm uninstall leaves it alone;
   - if a mirror rule is added, plant drift and confirm `emit-mirrors.py --check`
     fails by filename.
9. **Dogfood**: run the skill against this repo (purpose type: CLI /
   single-author tool) and compare its skeleton with the current `AGENTS.md`. A
   large divergence means either the skill or `AGENTS.md` is wrong, and finding
   out which is the point.
10. **Separate increment** — the launcher's empty-repo detection (§3.5). Land it
    only after the skill exists, since a fact line naming a skill nobody has is
    worse than silence. Its own negative control: a repo that *does* carry
    AGENTS.md must produce no fact line, and a non-SWE mode must produce none
    either.

Done-when: the skill deploys and uninstalls cleanly on both hosts without
disturbing foreign entries, the full gate suite is green, all applicable negative
controls have been seen to fire, `SURFACES.md` covers skills, and the dogfood
comparison is written down. The launcher increment (step 10) is done when both of
its negative controls have been seen to fire.

## 6. Constraints that outrank convenience

- The skill never writes a marker into a repo file (§3.2).
- Uninstall removes only manifest-named entries; a path marker is not enough, and
  the hooks incident is the precedent (this machine once fired one hook twice).
- The skill body must not name author-side paths — it runs in a packaged user's
  own repo, and `check-package.sh` enforces this.

## 7. Traps paid for on 2026-08-13

- `git ls-files` is what the lexicon gate scans, so a new **untracked** file is
  not scanned and the gate is green about nothing. `git add -N` first.
- `date +%:z` is unsupported on this macOS and emitted a literal `:z` into a
  timestamp. Use Python for the offset.
- A pipeline's `$?` is the last stage's. Run a gate unpiped to read its status.
- Verify "no behaviour change" against the same input — a session still running
  grows between two runs and the comparison is void.
- A corpus statistic can only answer what its collector looked for:
  `research/agents-md/scripts/probe.py` fetches 7 fixed paths, so that corpus
  cannot speak about directory-scoped files at all, and its stated limitations do
  not say so. Fixing that disclosure is separate, unowned work.
