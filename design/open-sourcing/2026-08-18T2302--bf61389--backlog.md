# Backlog — open-sourcing agent-bios: untangle the day1/ai-litmus couplings, and give an org a customization surface

**Status: not started. Needs its own design session.** This record inventories what is
coupled today (verified against the code at `bfcc567`, v0.12.0; revised during its own PR review — never merged under an earlier label, so this label carries the time the whole content was true) and frames the decisions.
It decided ONE thing en route, forced by review evidence: the scope seam (Q4,
D-20260818-71be4e — package+corpus are one already-public distribution; the repo is the
second scope). Everything else is framing, not decision. The standing architecture it extends is
`design/adapter-split/ECOSYSTEM-ARCHITECTURE.md` — whose two master levers (single/org
authorship; prose-only packages) and whose recorded warning (**prose-only does not buy zero
trust; reopening openness needs a trust model**) bind any design here.

## The goal, as stated by the user (2026-08-18)

agent-bios is currently entangled with **ai-litmus** (the day1company AI-usage dashboard —
`ai-litmus.day1co.kr` dashboard / `ai-litmus.dev.day1company.io` ingest, per that repo's
README) and with day1company itself. Open-sourcing requires (1) cleanly separating the areas
that collect data, promote corpus content, and distribute it; and (2) an interface and tools
that let a company adopt and customize it for their own environment.

## Inventory — what is coupled today, by area, with the code that proves it

### 1. Data collection (the learn! sink)

- `learn/collect-learning.py` `transport_config` reads the DASHBOARD-OWNED hook directory
  (token + `ingest-url`/`dashboard-url`) and POSTs to `{base}/api/ingest/learnings` — the
  ai-litmus ingest. Degrades with a notice when the hook is absent (default-off), but the
  endpoint's config home is dashboard-owned: **agent-bios has no config slot of its own for
  a sink**, so a non-day1 org cannot point the sink anywhere without installing the day1
  hook shape.
- The wire schema is `learn/learning.schema.json` (identity-free by design) — the coupling
  is the transport and its config home, not the payload.

### 2. Corpus promotion (the curation loop)

- The curator side lives in the ai-litmus dashboard (admin export `GET
  /api/exports/learnings`, VPN'd, session+CSRF). agent-bios's author-side half —
  `learn/ingest-learnings-export.py` (intake), the distill pipeline, ledger, and
  `learn/build-promotions.py` → `learn/migrate-learnings.py` — consumes that export's
  shape. The adapter-split record already withdrew the third-party curation-loop promise:
  **the curator pipeline is org-DATA-coupled**, and that remains true.
- Even fixtures carry the org: `learn/ingest-learnings-export.py` self-test pins
  `alice@day1company.co.kr` provenance.

### 3. Corpus content (author-personal and org material inside the source)

- `claude/CLAUDE.md` carries the author's `env-personal` bullet (the Korean-response
  preference) — never assembled into a package install, but present in the shipped SOURCE
  monolith and in every clone.
- `README.md`'s Adopting checklist names what an adopter must swap and calls guides'
  `(private)` Environment Binding entries the author's examples — but at this snapshot no
  guide actually carries a `(private)` marker (`git grep -F '(private)' -- claude/guides`
  is empty; corrected per PR review), so the marker is today a README convention without
  in-guide instances, and the design session must define a REAL, greppable marker for
  author-personal bindings before any hygiene gate can key on it. `DEPENDENCIES.md`
  inventories the author's optional capabilities; the checklist is the seed of the org
  interface.

### 4. Distribution

- One npm package under the author's account; `compose/domains.json` is `@agent-bios/core`
  with package-local domains. The multi-package composer (contract v2 §3) is deliberately
  deferred until a real second package exists; `packages/agent-bios/` holds one
  visualization-docs seed. Third-party trust/signing: deferred with the recorded warning
  above.

### 5. Repo-public vs package-public — the seam is the repo, not the package

- The npm payload is already clean (author-side excluded both ways by
  `gates/check-package.sh`). **The GIT REPO is not**: `decisions/decisions.jsonl` and
  `design/` records carry day1-internal narrative (81 `day1` occurrences in the tracked
  tree at this snapshot — `git grep -I -o -i day1 bfcc567 -- | wc -l` — 74 of them under
  `design/` and `decisions/`; an earlier 1,800+ figure counted untracked working files and
  is wrong),
  `research/agents-md/` derives from a 12,749-file GitHub corpus whose licensing terms for
  redistribution were never assessed, and `benchmarks/` + session transcripts references
  name real infrastructure. The two independently decidable scopes are (a) package+corpus —
  one distribution, already world-readable on npm, hygiene-gated (Q4 below) — and (b) the
  git repo, with its own sanitization cost.

## What exists toward the org interface already

Domain selection (`agent-bios onboard`), the user-owned `review-methods.local.toml` merged
at launch and never deployed, the `env-personal` tier that never ships, the audience:author
withholding, and the README swap checklist. What does not exist: an agent-bios-owned sink
config (endpoint + token slot, gitignored env style), an org-owned promotion loop (their
ingest/export/curation equivalent, or a file-drop substitute), org package authoring +
the composer, a trust model, and an org onboarding surface (wizard or config file) that ties
these together.

## The design session's questions (not answered here)

1. **Sink ownership**: give agent-bios its own transport config (org endpoint + token slot)
   with the day1 hook as one provider of it — or keep the sink a wrapper concern (the
   adapter-split's day1-as-npm-wrapper decision may already answer this; re-derive there).
2. **Promotion loop**: what is the minimal org-ownable curation path — a file-drop export
   format replacing the dashboard export, so `build-promotions.py` has one input shape with
   two producers? Does the identity-free schema survive an org whose curation wants identity?
3. **Content hygiene**: mechanize the swap checklist — a gate that fails on author-personal
   content outside declared slots (env-personal bullet, `(private)` bindings), so an org
   fork starts clean by construction.
4. **Which scope opens**: the npm package and the corpus are NOT separable scopes —
   `package.json` `files[]` packs `claude/CLAUDE.md`, the guides, and the codex trees, so
   publishing the package IS distributing the corpus (including the env-personal source
   bullet §3 names). The real split is (a) package+corpus together — which is already
   world-readable on the npm registry today, making the hygiene gate of Q3 the actual
   prerequisite rather than a licensing decision — and (b) the git repo (sanitization of
   decisions/design/research — expensive; assess the research corpus's redistribution
   terms before promising it).
5. **Trust model** for third-party packages — the precondition adapter-split recorded for
   any openness beyond single/org authorship.
6. **Org customization surface**: config file vs wizard vs both; what the org changes
   (endpoints, domains, packages, bindings, language) vs what stays engine.

## Done-when for the design session

A design record under this directory that answers the five open questions (Q4 is resolved
above as an invariant: package+corpus are one scope, the git repo is the other) with
alternatives and costs, names the build order with negative controls per step (the
swap-checklist gate first — it is useful even without open-sourcing, and it is the
prerequisite for the already-public package+corpus scope), and keeps the two scopes
independently decidable; then the user's approval before anything changes.
