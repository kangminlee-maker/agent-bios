# The coverage gate: how the fleet number is reached, and what it says

Roadmap step 3 landed (PR #45): the wrapper carries the transport, and the core
no longer reads the legacy hook directory. Publishing that core to npm is what
actually removes the fallback for everyone, so it waits on one question — has
the fleet moved onto `~/.config/agent-bios/{ingest-url,token}`? This record is
how that question got an answer, and what the answer was.

## There is no route to the production database

Measuring meant querying `raw_ingest_events`. There is no way to reach it from a
laptop, and this is a property of the environment rather than a missing config:

| | |
| --- | --- |
| Cloud SQL `day1-ai-dashboard-prod-pg` | `IPV4_ENABLED=False`, private IP only |
| Cloud VPN tunnels | none |
| Interconnect attachments | none |
| VPC peerings | none |
| `rtr-ai-dashboard-prod` | NAT configs only, no BGP peers |

A cloud router carrying only NAT is an egress path, not an ingress one. No
client VPN reaches `10.174.32.3`, and kpvpn serves the dashboard web tier, which
is a different question. Recorded as D-20260824-d7126a; the one-off Cloud Run
Job alternative was closed with it, because "what is the number now" gets asked
repeatedly until the publish happens.

The answer is a dashboard admin route,
`GET /api/admin/agent-bios-slot-coverage`, read by a logged-in admin. The rule
lives once in `src/services/agent-bios-slot-coverage.service.ts`; the in-VPC CLI
and the route both read it, so the number that informs and the number that gates
cannot drift.

## The number (2026-08-24, 180-day window)

| population | n | migrated | silent | verdict |
| --- | --- | --- | --- | --- |
| all reporting users | 13 | 4 (30.8%) | 9 | — |
| learning senders | **1** | 1 (100%) | 0 | `ok` |

**The gate is green on a denominator of one.** Over six months exactly one
person has sent a learning, and it is the author. So "publishing breaks nobody
today" is true, and "the fleet has migrated" is not: nine of thirteen are on
collectors that predate the slot write (6.7.1, 6.8.1, 6.11.1, 1.3.0, and one
reporting no version at all). Two of those nine were active on the day of
measurement, so the collectors did not self-update to 6.12.0/1.6.0 within a day
of the deploy the way this machine did.

That gap is the real state, and it is invisible in the verdict because the
verdict deliberately measures only the population the publish would break. Both
numbers are reported for exactly that reason.

## What measuring taught, twice

The reading AGREED with the outcome that was wanted, which is when the
instrument gets tested rather than trusted. Two defects came out of that.

**The judgement was on the wrong row.** A user active that morning read as
`silent`, and their most recent row was a Codex poller on 1.3.0 — a version that
has never heard of the field. The slot is one directory per machine and a user
commonly runs two collectors against it, so ranking by recency lets a stale
sibling overwrite an answer the other collector already gave. The fix ranks by
the classification's own precedence (migrated > explicit failure > silence,
recency only inside a rank). It happened not to move today's number — both of
that user's collectors are genuinely old — but it was wrong the moment anyone's
Claude hook migrated while their Codex poller lagged, which is the normal shape
of a rollout.

**The query was 12–24 seconds, and 180 days timed out.** Not cold start — warm
was worse. `EXPLAIN ANALYZE` over 200k synthetic rows located it: evaluating
`payload_json ->> 'agent_bios_slot'` inside the scan detoasts every session
payload in the window, including every row about to be discarded (Seq Scan 31ms
without it, 108ms with it, 258ms with it in the sort key — and real payloads
compress far worse than the synthetic ones). Ranking now runs on cheap columns
and the payload is joined back by primary key for the handful of surviving rows.
180 days went from timeout to 5.8s.

Neither was reachable by reading the code. Both needed the thing to run against
production and then be disbelieved.

## What the controls were worth

- unit: 15 planted defects, each killed by the test that names the rule; suite
  green again after restore
- real Postgres 17: 30 checks over the query's own branches; 13 planted
  SQL/reducer defects, all caught by name
- one mutation **survived** the first pass — the reducer's tie-break. The
  fixture that looked like it covered it used a single `source`, so SQL collapsed
  those rows before the reducer ever saw two of the same rank. A case with two
  sources closed it. A fixture can test something adjacent to what its name says.
- one mutation survives by design and is declared: `->` vs `->>`, proven
  equivalent by probing how the driver deserializes jsonb
- full chain on a real server: no credentials → 401, non-admin → 403, admin →
  200 with the seeded population's verdict, `?days=0` → 400

## Open

- **Whether to publish the core now.** The gate says yes for the population it
  protects; the fleet says 30.8%. This is a judgement about how much the
  non-senders matter, and it belongs to the user.
- **Collector self-update is not reaching everyone.** Two users active on
  2026-08-24 still ran 1.3.0 and an unversioned collector. The dashboard has an
  admin `send-reinstall` action, whose existence suggests this is known. Not
  investigated here.
- `AGENTS.md` still documents the umbrella gate as 10–15 minutes; measured runs
  are ~60. Unchanged from the previous record.
