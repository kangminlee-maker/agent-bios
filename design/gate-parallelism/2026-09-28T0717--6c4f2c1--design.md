# The parity umbrella runs its legs concurrently

The owner chose this on 2026-09-27 (option A of three) after the measurements below. A commit
on this repository took 13 minutes in its hook: 19:46 → 19:59 and 20:02 → 20:15 on 2026-09-27,
each for a change of design records only.

## What was measured (2026-09-27, HEAD 6c4f2c1, 18-core Apple silicon, Python 3.14.7)

The tools and raw outputs are author-side, outside the repository, in
`~/.local/share/agent-bios-workbench/gate-timing/`.

**Serial umbrella.** `gates/check-parity.sh` was run on a snapshot of the index, as
`.githooks/pre-commit` materialises it, under `bash -x` with a time stamp on every top-level
step. It took 909 s; `check-package.sh` took 0.3 s. The stamping adds overhead, which is why this
reads longer than the 13-minute commits. It used one core while the machine's load average was
about 4 of 18. Seven legs took 782 s of the 909:

| Leg | Seconds |
| --- | --- |
| `compose/test_instructions*.py` through `unittest discover` | 250 |
| `gates/workenv/check-workenv.py` | 137 |
| `gates/check-publish.sh --self-test` | 126 |
| `gates/test-install-guides.sh` | 73 |
| `gates/check-endpoints.py --self-test` | 69 |
| `gates/check-package.sh --self-test` | 66 |
| `gates/check_parity.py` | 61 |

Every other leg took under 19 s, and most under 1 s.

**The seven at once.** Each was run on its own snapshot, all started together, with a recorder
that logs every file each Python process opens and every process it starts:
- wall time was 348 s, and all seven passed;
- the repository's refs, stash, `core.worktree` and status were identical before and after;
- no Python `open()` for writing landed outside a temporary directory. Calls through
  `os.open` carry no mode in the audit event, so they were not classified.

A first attempt failed 12 tests. The recorder was the cause, not the concurrency: it shadowed
Homebrew's own `sitecustomize.py`. The rerun with the recorder chaining to it passed.

**The instructions suite split by file.**
- Setup: each of the 25 `compose/test_instructions*.py` ran in its own process, 18 at a time,
  each with its own `TMPDIR`.
- Result: 56 s wall, 523 tests, 25 `OK`, nothing skipped. The serial suite on the same tree also
  ran 523 tests with `OK` and nothing skipped.
- The slowest files were `test_instructions_ui.py` (49 s) and `test_instructions_setup_ui.py`
  (46 s).
- No compose test file lives below `compose/`, so the glob and `discover -s compose` select the
  same set.

## Why not reuse results keyed on what a leg read

A cache keyed on the bytes a leg read would skip a leg whose inputs are unchanged. The recorder
showed it would save little, and could not be trusted where it would:
- **Whole-tree readers.** Four of the seven heavy legs read nearly every tracked file:
  - `check-workenv.py` 3,835 of 3,835;
  - the package self-test 3,835;
  - the endpoint self-test 3,826;
  - the install scenarios 3,821.

  They copy or scan the whole tree, so any change, a design record included, would run them
  again.
- **Invisible inputs.** The publish self-test opened no tracked file from Python. It started
  `git ls-tree` 1,230 times, and what those read is invisible to the recorder. Bash, git, ruff and
  the installed hosts are all outside what a Python audit hook sees, and macOS offers no
  unprivileged way to trace them.
- **Where it would help.** It pays only for the instructions suite (347 files, none under
  `design/`) and `check_parity.py` (142). Splitting the suite by file already brings it under the
  new bound.

A cache that is wrong reports a stale pass. That is the one failure a commit gate must not have,
and here it could not be excluded.

## What the recorder found that this change does not fix

Some legs read the machine, not only the tree. The same commit can therefore get a different
verdict on another machine or on another day:
- **Installed hosts.** The instructions suite starts the installed Codex (`/opt/homebrew/bin/codex`)
  about 20 times: `app-server`, `debug prompt-input` and `--version`. It also runs the installed
  Claude Code (`claude --version`, `claude plugin validate`), `agent-bios` from `PATH`, and `npm`.
- **Real history files.** The instructions suite reads the real `~/.claude/history.jsonl`,
  `~/.codex/history.jsonl` and `~/.local/share/agent-bios/session-distill-state.json`.
- **The real token file.** `check-endpoints.py --self-test` reads the real
  `~/.config/agent-bios/token`, which exists on this machine. Whether the file changes the
  verdict was not tested.
- **Deployed install state.** `test-install-guides.sh` reads the real
  `~/.local/share/agent-bios/selection.json`. `check_parity.py` reads
  `~/.local/share/agent-bios/version.json` and the default launcher venv.

Separating tree checks from machine checks was option B, which the owner did not choose. It stays
open with these findings as its starting evidence. Revisit it when a commit's verdict changes
with no change to the tree, for example after a host self-update.

## The design

- **Unchanged preamble.** Every early refusal happens before any leg starts: the subject guards,
  the leg-guard scan over this file, and the other `exit 1` checks.
- **Leg helpers.** They live in `gates/parallel-legs.sh`, which the umbrella sources. It is
  author-side like the rest of `gates/`, and its `--self-test` is the negative control.
- **One job per original leg.** Each leg that was one guarded block stays one block. It becomes
  one background job, so a self-test still runs before its live run where the umbrella says the
  order matters (`check-workenv.py`), and every block keeps its internal order.
- **One output slot per leg, in textual order.** The job writes stdout and stderr to its slot, and
  the umbrella prints the slots in the order the legs appear in the file. The log reads as the
  serial run did, whatever order the jobs finish in.
- **Failure by name.** A job exits with its own `fail`. For any leg that exits non-zero, the
  umbrella adds `FAIL: leg '<name>' exited <status>` after that leg's output. A leg that dies
  without printing therefore still fails by name. That matters to `install.sh verify`, which
  shows only the `FAIL` lines of this umbrella. Every existing message is unchanged, including
  `PARITY OK`.
- **Concurrency cap.** `PARITY_JOBS` sets it; the default is the online CPU count. A job takes a
  token from a FIFO before it starts and returns it when it exits. `PARITY_JOBS=1` runs the legs
  one at a time in file order, which is the serial umbrella.
- **The instructions suite, split.** `compose/test_instructions*.py` runs one file per job, each
  through the same `unittest discover -s compose`, with a guard that the glob matched at least
  one file.
- **Standard input.** Every job reads standard input from `/dev/null`. A background job in a
  non-interactive shell gets that anyway; the redirection makes it explicit.

## Isolation risks and the answer to each

- **Shared `TMPDIR`.** A test naming a fixed file in the temporary directory would collide with
  its twin in another job. Each job gets its own `TMPDIR` under one directory the umbrella
  creates. The umbrella removes that directory when every leg passes. When a leg fails it keeps
  the directory and names it, because the install scenarios' kept log lives there.
- **Shared `HOME` and the launcher venv.**
  - The recorded heavy legs read the real `HOME` (above). No write-mode `open()` of theirs
    landed outside their temporary directories.
  - Byte-code caches written into the shared snapshot are written atomically by Python, as under
    any parallel test runner.
  - Legs that read the same real files concurrently read the same bytes they would read one
    after another.
- **The venv provisioning order.** Serially, the venv is provisioned only when it is missing,
  after every earlier leg has finished; the legs after it inherit `AGENT_LAUNCH_VENV`.
  - The umbrella keeps that position.
  - When provisioning is needed, it first waits for every running leg and prints their output, so
    no earlier leg sees a half-built venv.
  - Provisioning failure still exits 1 by name, now after printing what ran before it.
  - The export stays where it was, so earlier legs do not inherit it.
- **`git init` under the hook's `GIT_DIR`.** Concurrency does not create this trap and does not
  remove it.
  - Every leg still inherits the hook's `GIT_DIR`, `GIT_WORK_TREE` and snapshot index.
  - The hook's `core.worktree` comparison still runs after both gates.
  - Legs only read the snapshot index. Git's own lock refuses a second concurrent writer rather
    than tearing the index.
- **A self-test before its live run.** Each is one job, and the order inside a job is the order
  in the file.
- **`test-install-guides.sh` reads itself incrementally.** It is one job and nothing edits it
  while it runs. Under the hook the tree is a snapshot in any case. Nothing here makes an edit
  during a run more likely than before.
- **A killed job.** A job killed by a signal that bash cannot trap never returns its token, so the
  run continues with one slot fewer. It hangs only if every token is lost. Stated, not guarded.

## What bounds the run after this change

`check-workenv.py` runs its unit-test files one after another, 137 s serially, after a 5 s
self-test that must precede it. The publish self-test takes 126 s in its 1,230 git calls. Either
could be made faster inside its own gate, which this change does not do. The re-measured wall
times are in the commit that lands this design and in `AGENTS.md` §3.
