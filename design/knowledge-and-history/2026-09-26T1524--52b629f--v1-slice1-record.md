# V1, first slice: the store, the request journal, the local profile and key bindings

V1 is written in five slices. This is the first: the code every later slice writes through. It
is used here, tested, and run against every scenario. It does not complete V1, and no V1 case
can pass on it alone, because every V1 case goes on to a source, a collection or a delivery.

## What was written

| Module | Serves | What it keeps |
| --- | --- | --- |
| `workenv/storage.py` | the B03 binding; the place for given answers | one `state.sqlite` per state root: records by digest, held requests, receipts, heads, profiles, bindings |
| `workenv/journal.py` | the journal layer; `operation.query`, `operation.cancel` | every request read, held and answered once |
| `workenv/access.py` | `access.profile.read`, `access.profile.rename` | the local profile and its access state |
| `workenv/identity.py` | `identity.binding.add`, `identity.binding.revoke` | which key speaks for which principal |

**The store.** Every connection reads back WAL, `synchronous=FULL`, `fullfsync` and
`checkpoint_fullfsync`, and refuses a mismatch by its B03 name. Writes happen only inside a unit
of work, `BEGIN IMMEDIATE` to `COMMIT`, which passes `in_txn_before_commit`. A store written by a
later layout is not opened. There is one database per state root, not one per scope namespace:
a transaction across attached WAL databases is atomic in each file but not across them
(`D-20260926-53cdf6`).

**The journal.** It wraps whatever answers a request, and does the following:

1. It reads the request and its payload in submit mode, and every other carried record in
   stored mode. A record that is no record either way is refused by triples, and nothing is
   written (`D-20260926-5c640f`).
2. It answers from what it holds. The same request again gets the original answer. The same id
   with other bytes is `request_id_conflict`. A request held in review, approved, executing,
   unknown or partial is handed on again (`D-20260926-164aa5`).
3. It applies the operation's row: `payload_not_taken` and `effect_class_mismatch`. It also
   refuses `resubmitted_while_unknown`.
4. It answers queries and cancels itself.
5. It runs everything else inside one unit of work, with what the entry writes and the answer
   it gives.

After the commit, the journal passes `after_commit_before_return` with the answer
(`D-20260926-16cbd7`). The first request from a profile writes that profile, in the same unit.

**Profile and bindings.** First use writes an active state at generation 1. A rename changes
the display name and nothing else. A key bound to another principal is `binding_conflict`.

A principal that has held a binding takes another only with a signature by one of its standing
bindings, over the new binding's bytes, in the `agent-bios/principal_binding` namespace, checked
with `ssh-keygen -Y verify`. This holds even after every binding is revoked
(`D-20260926-312286`).

**Shipping.** The four modules ship in `package.json` `files[]`, each by name, as the contract
modules do (`D-20260926-a920df`). They import only what ships: the journal reads the contract
schemas from the shipped `schemas/` directory. The ontology's derived count of shipped paths, which
`ontology/extract.py` measures, moves from 103 to 107.

## How it was checked

- **Units.** 53 tests in `gates/workenv/units/v1/`: 11 for the store, 23 for the journal, 17
  for profiles and bindings, and 2 for what ships. They use real ed25519 keys and a simulated
  death at each fault point.
- **The package gate.** The first commit attempt was refused: the four modules were neither
  shipped nor declared author-side. Listing them exposed a defect no checkout run could show.
  The journal loaded the schemas through `workenv/contracts/examples.py`, which does not ship,
  so an installed copy would have failed on its first import. The journal now reads the schemas
  itself. `test_shipped.py` holds every shipped `workenv` module's imports to `files[]`, and
  putting the import back fails it by name.
- **Reverts.** 53 reverts, each one rule of the four modules put back as it was before. Each
  made a unit fail. Two survived the first pass: the signer's principal and a revoked principal.
  They led to two tests and to the revoked-principal rule above.
- **The driver, at V1.** Every one of V1's 22 cases answers its slice-1 steps as stated. It then
  blocks by name at the first module not written yet:

  | Cases | Blocked at |
  | --- | --- |
  | 17 | `workenv.sources` |
  | 1 | `workenv.preparation` |
  | 1 | `workenv.delivery` |
  | 1 | `workenv.hosts` |
  | 1 | the driver feature `event_reply_lost` |

  The driver test that stood on the journal's absence now stands on the sources module's.
- **The journal against every scenario.** The four modules served their operations. The
  scripted owner served every other operation, behind the real journal and place. Across the
  162 scenarios, with each case's registry rules:

  | Outcome | Cases |
  | --- | --- |
  | Passed | 85 |
  | Blocked by name, on driver features and conflicting checkouts | 74 |
  | Failed | 3 |

  Under V1's own routing, 21 of 22 pass and one waits on `event_reply_lost`.

  The three failures:
  - **DEL-TEAM and N16-C12-NEG are the harness.** The scripted owner states the digest of a
    binding the real code minted, which it cannot know. Both pass when the double serves the
    binding.
  - **N17-DISCONNECT-NEG waits on settling.** It expects a query to settle a pending carrier
    outcome, which is deferred below.
- **Direct use on this machine.** A script submitted a person's own requests through the
  journal, with real keys, under `team-env-20260920/v1-slice1-use/state`. It read the profile
  and bound a laptop key. It named the profile `노트북`. It was refused a second key without
  proof, then bound it with the first key's signature. It revoked the first key. A query then
  returned the first binding's original result and receipt, and a resubmission returned the
  identical answer. It bound a third key and killed the process after the commit, before the
  answer. A new process's query found the commit, and resubmitting its bytes returned that
  commit with receipt #5.

  `sqlite3` read back `wal`, layout 1, ten held requests and five receipts. The transcript is
  `transcript.txt` beside the state.

## What the full run found in the scenarios

The journal and identity rules are one rule each. Four sets of scenarios stated what no single
rule could give. Each was changed to agree with its contract and with the majority:

| Scenarios | What they stated | Now | Decision |
| --- | --- | --- | --- |
| CAP-08, CAP-13, DEL-TEAM, N04-C03-NEG | the contract example's public key for two principals on one installation, so the second binding is `binding_conflict` | the second principal has its own example key | `D-20260926-24f760` |
| N02-C01-POS, N03-C02-NEG, N05-AVAILABLE-NEG, N24-C03-POS, N24-CLOSURE-NEG | a query of a committed request answered by the result alone, where thirty others and C03 return the result and its receipt | the receipt too | `D-20260926-66c0b0` |
| N05-CONTROL-NEG (two steps), N05-CRASH-NEG | `none` as the provider effect of a conflict and a late cancel over a request that had no provider, where four others state `not_applicable` | `not_applicable` | `D-20260926-d7acb0` |

The specs were edited and `scenarios.py` regenerated them. `--check` passes on all 162. No
V1 case is among them. They move those cases' fixtures before the P01 re-freeze, which freezes
them anyway.

## Open

- **Recovery on `resubmitted_while_unknown`.** CAP-10 states `query_same_request`, while
  TUI-ENTRY-UNKNOWN and TUI-ENTRY-SHARED-UNKNOWN state none. CAP-10's first request is in
  flight rather than held unknown, so the stage that runs requests in flight (V6) decides
  whether these are one rule. The journal states none, as the V1 case does.
- **Deferred** (`D-20260926-e2850f`):
  - `operation.history.read`, to slice 5;
  - settling a pending outcome on a query, and a cancel of a request not held, to V6 and V7;
  - the configure event, to V8;
  - binding a key on verified evidence, to V7.
