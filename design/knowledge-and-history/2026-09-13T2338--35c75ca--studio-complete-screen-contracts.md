# Studio: complete screen and operation contracts

The user has included the operational and advanced areas previously deferred. This record specifies their minimum usable interactions now. Implementation may proceed in stages, but an unavailable backend is not a reason to leave its interaction or failure contract undesigned. These are proposed interfaces, not newly implemented providers. The [governance design](2026-09-13T2336--35c75ca--studio-governance-design.md) owns grants, independent review, authority allocation and exact-change execution; its contract applies to every mutation row below.

The purpose remains selecting, sharing, and continuing a **team** work environment. Completeness means each necessary operation has an identifiable subject, authorized effect, reviewable input, recovery path, and observable outcome. It does not require a separate application or global schema for each operation.

## One shell, seven destinations

Keep the four content areas: **Work environment, Instructions, Domain knowledge, Decision memory**. Add **Review queue, Team/access, Operations** as panels reached from the shared header/utility rail. Search is a scoped command within the shell. A result or operation opens the owning area with a return reference; it does not create another content store.

The header retains selected Team/environment, viewed edition/draft, Team-adopted edition, and actual task edition. A change of browsing scope never switches an active task. Editors use the main panel, preserving their drafts when another panel opens. Short confirmations may use dialogs; multi-step authoring, access changes, conflicts, and deletion use full panels with back navigation.

Every detail view exposes title, role, owner, exact revision or record/frontier, applicable scope, available actions, and relevant qualifications. Technical identifiers are expandable and copyable; they need not occupy every row. Unsupported actions have a named capability explanation. Unknown authorization does not look like a granted right, and restricted metadata is not exposed to explain an unavailable action.

Graph and form modes are editors for provider-owned knowledge representations. They do not establish a universal ontology, execute arbitrary validator code, or replace provider-owned domain package documents. A provider can expose a graph directly or an explicit projection with one canonical authoring owner. A form profile maps to that owner's schema; unsupported semantics remain unsupported rather than being silently coerced into generic fields.

## Shared operation behavior

All mutation screens share the same visible phases: **draft/input → validation and effect preview → authorized submission → confirmed outcome**. A policy may already authorize several phases together. This design does not add a mandatory confirmation click to every routine write.

The preview names the object and the effect: source revision, environment composition, publication, Team adoption, access grant, decision event, or deletion. It includes the base/version token, the actual destination owner, and material consequences. A change to request-defining input invalidates an earlier readiness/effect preview. Back and navigation preserve editable input; discard is explicit.

Submission binds the operation identity to the canonical request and actual principal. **In progress** and **outcome unknown** are different from **failed**. Retry first resolves the same operation. A conditional-write conflict preserves the candidate and offers the provider's supported choices. Cancellation reports whether it stopped pending work, arrived too late, or has an unknown result. Reversal is a new explicit operation, not deletion of its receipt.

Bulk operations show their real atomicity boundary. A client cannot promise all-or-nothing across independent providers. A completion view lists confirmed changes and remaining failed/unknown groups, subject to access. A permission change may require refreshing the result without disclosing newly restricted details.

## Knowledge and memory details that cannot be omitted

Knowledge has four separate signals: domain applicability, local availability, scoped acceptance, and review/source-check evidence. “Reviewed today” is not “true now.” The validation panel lets authors maintain competency questions before having a complete graph. Each question names the decision it changes, necessary scope/evidence, expected answer form, and a counterexample. Nine-lens coverage is available for authoring/review; it is not imposed on every read.

The memory reader establishes qualified current state before search ranking and clipping. Current assessment and historical explanation are explicit view choices. A history view preserves original rationale and may accompany it with later corrections; it must not rewrite what the earlier record stated. Workstreams have stable identities, purposes, memberships, and an editable display name; a renamed lane is not a new workstream. A record can belong to several lanes, and temporal adjacency does not create causality.

Decision deletion is separate from removing a workstream from an environment, filtering it out, correcting an assertion, or withdrawing an actual choice. Retention review must explain the specific operation selected. If a provider cannot supply authorized current-state closure after deletion or access loss, the state view reports that limitation rather than reviving an older assertion.

## Visual and technical closure

The screen label is **agent-bios · Studio**, with the four role-specific area names and three utility panels above. Use the existing prototype's desktop shell as the interaction baseline: left navigation, list/detail content, persistent Team/environment header, and stacked navigation/details at narrow widths. Maintain one typography hierarchy for title, section, body, and metadata; one spacing scale; and semantic tokens for action, caution, error, success, and unresolved state. State is always conveyed by text/icon as well as color. Keyboard focus, form error association, readable contrast, and preserved focus/position on return apply to every screen, including advanced editors.

Exact visual tokens can be supplied by the accompanying design-system/mockup artifact without changing these operation contracts. A framework choice is an implementation binding: its acceptance requirement is keyboard/responsive behavior and faithful provider/request handling. Persistence belongs to the already-designed provider/cache/draft/receipt boundaries. Studio does not gain a private competing source store because a convenient UI framework includes one.

## Coverage audit and implementation acceptance

The previous documents adequately separated browsing, inclusion, publication, adoption, readiness, and actual delivery. Their material gaps were operational: unsupported source-authoring buttons had no complete workflow; advanced model/form/search controls had no subjects or fields; access/deletion/bulk/recovery had no outcome ownership; and child/current-context use had no inspection/remediation screen. The table closes those design gaps with the minimum corresponding contract.

Each row needs one successful and one material failure journey in the expanded prototype or connected UI. Prototype journeys use labeled fixtures and prove interaction logic only. Connected acceptance additionally verifies the owning provider's revision/access conditions, request-bound receipts, real host delivery where claimed, and recovery after the corresponding failure. A panel that is visually present but has neither a supported operation nor an explicit unsupported state does not satisfy coverage.

Implementation can be ordered by provider availability and risk, but the scope is the full table. No row is postponed until an unspecified future need. Additional complexity is admitted only when necessary to realize these workflows or when a new user requirement changes them.
