# Studio prototype QA

## Subject

The source is the literal HTML fragment beside this record, 46,516 bytes.
SHA-256: `60faf42d4e366208bbc74b5d03cdd1f7aa4ae828200fe6b65f48ec98b2fe7e62`.

It was rendered through the visualize skill's wrapper and inspected using
headless Chromium. Browser actions were scoped to the sandboxed iframe.
Assertions checked visible UI state after actual button/select interactions;
they did not assign the internal application state to bypass the flow.

## Completed checks

Eleven grouped interaction assertions passed:

1. Knowledge conditions, exceptions and evidence can be read without creating
   an active task.
2. Current decision, correction from the other workstream, and unresolved
   question remain available together.
3. Both context preview and readiness confirmation leave use status unset.
4. The newcomer journey completes with a virtual task on edition 3.
5. Draft editing and publication leave Team adoption and the existing task on
   edition 3; the draft is cleared by publication.
6. A published edition can be left unadopted and reviewed later. Team adoption
   moves to edition 4 while the existing task stays on edition 3.
7. The maintainer journey starts a new task on edition 4, omits the removed
   checklist pointer, and retains the prior task's edition-3 reference.
8. Team switching retains the earlier task and changes the new preview to the
   selected Team's knowledge and decision scope.
9. A draft survives switching away and back. Discarding it leaves adoption
   unchanged.
10. Shared-source browsing exposes read-only ownership and does not include,
    adopt or activate that source.
11. At a 320px outer viewport, the newcomer flow reaches use and the maintainer
    flow reaches adoption. No horizontal overflow occurs in the inspected
    overview, knowledge, preview, use result, edit, change review, publication
    and adopted-overview screens.

The wrapper has 16px margins on each side, so the 320px viewport actually tested
288px of available fragment width. The desktop viewport was 1,024px wide.

The desktop overview was visually inspected in light and dark appearance.
The dark appearance resolved the product background to `rgb(23, 28, 27)` and
text to `rgb(232, 240, 234)`; it did not retain light surfaces. The mobile
overview was visually inspected, and the remaining mobile screens received
interaction and width checks. Browser page errors: zero.

A presentation-only correction fixed the brand's small-label font declaration,
and keyboard focus restoration was added after rerender. The narrow-screen
journeys and dark overview ran on that final source. Desktop logic checks ran
before those two presentation changes.

## Evidence limits

This validates the finite fixture's UI transitions and basic layout. It does
not validate production authentication, permissions, retrieval, ontology
integrity, temporal correctness, correction closure algorithms, concurrent
writes, offline recovery, source persistence, host integration, actual delivery
or model behavior. Those providers are absent from this prototype.

Keyboard controls are native, with focus retained on surviving controls or
the next primary control after a screen transition. This is not a full
screen-reader or accessibility certification. Optional host-provided design
controls were not exercised by the standalone browser run.

No shipped runtime source changed for this UI design. The full product parity
suite was not rerun for these design/prototype artifacts.
