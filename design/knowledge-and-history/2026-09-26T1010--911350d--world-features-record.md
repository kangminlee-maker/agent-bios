# The driver's world: the clock, faults, the checkout and its edits, and rule contexts

The [09:09 executor record](2026-09-26T0909--6da8ab4--executor-record.md) left V1's step 3b open:
the world features six of V1's cases use, and the rule oracles one of them names. They are in the
tree now, except the lost reply, which waits for the code that launches a host. This is step 3b of
V1; the adapter design's [21:24 record](2026-09-24T2124--0fe13da--conformance-adapter-design.md) is
amended by it.

`cases.features_of` adds `checkout` to every scenario whose records read one: 77 of the 162.

## The checkout a scenario describes

No scenario states its checkout as a world section. Its records state it, and the driver builds
it from them (`D-20260926-353f0e`):

- a file an observation reads from the tree, with its size, git state and digest;
- a member of a repository-authored source, with its path, size and digest;
- the branch, remote and commit a repository binding observed;
- the checkout path a selection or capture names.

A file joined to a member holds the member's bytes; any other holds generated bytes of its stated
size, the same bytes for the same stated content. It is committed unless it is read `modified`, when
HEAD holds other bytes, or `untracked`. The stated checkout path, each literal file digest and each
literal observed commit are stand-ins, replaced everywhere by the directory, the sha256 of the
bytes written and HEAD, as the signing feature replaces a public key. The checkout's git and the
code under test see no `GIT_*` variable from the caller; a planted `GIT_DIR` is the control.

A fact about bytes a file edit writes belongs to the edit, not to the checkout's first state.

### One scenario states a fact it had only implied

CMP-QUALIFIED commits a repository-authored source whose one member is `rules/review.md`, so
derivation puts that file in the checkout. Its start `start_with_an_unavailable_winner` then
expects `role_body_unavailable`: the role's body is no longer there. The scenario edited
`rules/deploy.md` before that start but removed nothing, so the missing file was implied only by the
refusal it expects, and a real implementation would have found the file. Nine other scenarios state
the same path as present; the decision's "seven others" undercounts them. The spec now states the
removal with the vocabulary scenarios already use, a `file_edit` with `absent` before that start:
six lines in `spec.json`, the regenerated `scenario.json`, and `scenarios.py --check` passes for all
162. The owner accepted derivation with stand-ins and no scenario edits; this is the one exception,
and it is reported to the owner rather than decided around them.

## Values learned later

`D-20260926-e6aacc` came from running the fault scenarios. A process killed after it committed, and
observed by a later query, never answers the step that minted the values. Those values, and those
an answer holds only inside a record it names by digest, are pending: each is learned where an
answer first holds it. Until then a digest or size of a record resting on one is learned where an
answer states it, and once the record is known it must be the record that digest named, or the case
fails naming the record, its digest or size, and the value the earlier answer stated. A request resting on a value no answer has returned fails by name, because the
driver cannot build it.

## Rule contexts

`D-20260926-8d841c`: the executor applies each rule a case names to every returned record of the
kind the rule judges, from code in scope. A given answer is the scenario's own and is not judged. A
rule that reads the store gets its context from a resolver in `rules.CONTEXT`, which looks records
up among those the run holds. Only `C01/read_within_selection` has one: it finds the selection by the
digest the observation names. A rule that reads no store is judged with an empty context; a rule
with neither blocks its case. V1 needs only that one rule, for N27-SELECTION-NEG.

## The lost reply

`event_reply_lost` is not written (`D-20260926-421d82`). TUI-ENTRY-UNKNOWN needs it on
`session.routing.activate`, where the host the entrance launches loses its reply. How the driver
reaches that host is a seam of the code V1's slice 4 writes (delivery, hosts and roles); fixing it
now would fix an interface before the code that has to live with it.

## Controls

- **Positive.** Every scenario runs against the scripted owner: 90 of the 162 pass, 72 are blocked
  by name, none fails. The 09:09 figure was 82, with the checkout not yet a feature. The blocked
  reasons are the process, partition, `during` and event features not yet written, and the three
  checkout shapes above.
- **V1.** At V1 the driver runs 22 cases. Against the scripted owner, 21 pass and TUI-ENTRY-UNKNOWN
  is blocked on `event_reply_lost`. Against the code, all 22 are still blocked on
  `workenv.journal:layer_journal`, because no V1 code is written.
- **Negative.** Each required to fail or block by name: a fault point the code never reaches; a
  restart that loses what was committed; a fault on a step the driver gives; a digest learned
  before its record and planted otherwise; a request resting on a value no answer returned; a
  `GIT_*` variable the caller exported, at the checkout's git and at the code under test; a second
  checkout and a path with two contents; an edit reaching outside the checkout; a record breaking
  the rule; a rule no context covers.
- **What each feature does, checked directly.** The call gets its step's instant; the checkout
  holds each file in its stated git state and no stand-in survives; an edit lands before its step
  and not before another; the rule runs on what code in scope wrote, reads the selection the record
  names, and leaves a given answer alone.
- **Reverts.** Each rule of 3a and 3b was reverted in a copy of the tree, one at a time, and every
  control guarding it was required to fail: 50 reverts, 58 revert-and-control pairs, all caught; the
  untouched copy passes.
- **Gates.** `test_executor.py` runs 54 tests, `test_driver.py` 17 and `test_cases.py` 80; ruff,
  the lexicon gate, the ontology gate and the plan gate (33 positive, 442 negative controls) pass.
  The dated evaluator still reads `run-7` as accepted `[P00]`, ready `[P01]`.

`scenarios.py`'s docstring now states the checkout stand-ins, and the fixture fingerprint moves
with it. P01 is re-frozen once V1's cases run, so that move is part of the re-freeze already
planned, not a new one.
