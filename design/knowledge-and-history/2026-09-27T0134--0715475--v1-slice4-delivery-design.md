# V1, fourth slice: delivering a preparation to a host session, whatever the host

The fourth slice delivers a composed preparation to an actual session and records what arrived:
`recipient.link.open`, `recipient.delivery.attempt` and `delivery.observe` (`workenv/delivery.py`),
`session.routing.activate` (`workenv/roles.py`), and the host adapters (`workenv/hosts/`).

The owner chose the defaults on 2026-09-27, with one requirement: the design may not assume
Claude Code. It must work on Codex, and on a host added later, without changing the rules. The
same day, the owner chose how a route's support is decided: by a real probe on the installed
host, not by what the host documents. This record is the design both choices produced. It
describes work in flight; the slice record written when it lands says what was built and
measured.

## The split: one owner, one adapter per host

| Part | Where | Knows | Does not know |
| --- | --- | --- | --- |
| **The owner** | `workenv/delivery.py`, `workenv/roles.py` | links, preparations, which bodies a preparation composed, what was delivered to whom, the rules C04, C07 and C11 state | any host's event names, hook formats, environment variables or session ids |
| **A host adapter** | one module per host under `workenv/hosts/` | which of its host's events reaches which recipient; where the host puts a session's id; the output its host reads | the delivery rules |
| **The probes** | `workenv/hosts/__init__.py` reads them; `capability.probe` makes them | which recipient's delivery a real run showed working on which host name and version | how the host is driven |

The owner asks one question about hosts: does a route reach this recipient on the link's host,
installed here. A host is added by writing its adapter module and listing it; nothing in the
owner changes.

### What an adapter states

Each adapter declares, as data: its host names (the `host.name` a `recipient_link` carries); its
routes, one host event per recipient kind C11 names (`new`, `current`, `child`, `rehydrated`);
where it reads the session id (an event field, or an environment variable for a command the
session runs); and how it writes text so that its host adds it to that session's context.

| Recipient | Claude Code | Codex |
| --- | --- | --- |
| `new` | `SessionStart`, source `startup` | `SessionStart`, source `startup` |
| `rehydrated` | `SessionStart`, source `compact` | `SessionStart`, source `compact` |
| `child` | `SubagentStart` | not declared: what its `SubagentStart` output takes is not shown on the installed version |
| `current` | `UserPromptSubmit` | `UserPromptSubmit` |
| session id | `session_id` in the event; `CLAUDE_CODE_SESSION_ID` in a command | `session_id` in the event; `CODEX_THREAD_ID` in a command |
| output | `hookSpecificOutput.additionalContext` | `hookSpecificOutput.additionalContext`, added as a developer message |

Both hosts take hooks per session without editing a settings file: Claude Code loads a
session-scoped plugin (`--plugin-dir`), and Codex takes hook configuration as per-call `-c`
values. `compose/instructions_session.py` already does both, so a delivery hook can join that
path and leave native files preserved.

### What decides that a route is supported

An adapter's declaration says how it would reach a recipient, never that it does. C12 and the
design SSOT forbid support claimed from a specification or a registered name ("Standard support
or a registered tool is not proof that an installed CLI/app handles the interaction"), and the
frozen cases need it too: N15-C11-POS delivers to a child and a rehydrated session on Claude Code
2.1.278 while DEL-TEAM, on the same host and version, may deliver to neither. No function of the
host's name could pass both.

So a route is supported on a host only where the adapter declares it **and** the latest probe of
that recipient's delivery capability on that host, by name and version, ran for real and worked.
C12 gains four capabilities for this, qualified one at a time like the rest: `new_delivery`,
`current_delivery`, `child_delivery` and `rehydrated_delivery`. A probe against a fixture, one
that did not work, probes of one instant that disagree, or no probe at all leave the route
unsupported. A new host, or a host updated to a new version, is unsupported until a probe runs
on it; nothing is delivered automatically meanwhile, and the bodies stay readable by hand.

A probe of a delivery route is a real run of the installed host through its adapter: the host
fires the adapter's hook, the adapter hands context to the recipient, and the probe observes
that the recipient read it. That is real-evidence work, which the plan gives the real adapter
qualification family (N23). A driver run has no installed host, so a case that delivers states
its probe as a `capability.probe` step, and the driver gives that step (the `qualified_routes`
feature): the stated probe is placed as given state and the code under test reads it as it reads
a probe it kept. Seven cases state such probes: N15-C11-POS, CMP-PINS, DEL-PERSONAL, CMP-UI,
N12-C07-NEG, DEL-TEAM and N15-C11-NEG, each only for the recipients it delivers to.

## What "received" means

The attempt carries no bodies (`recipient.delivery.attempt` returns only the `delivery_attempt`).
Bodies come from an activation, which returns each delivered unit's bytes beside its projection.
An adapter answering a host event takes the bodies, hands them to its host as the event's output,
and records the delivery with an attempt naming exactly those bodies.

`received` states that the adapter reported, in a sealed request, handing exactly those bodies to
its host for that recipient. It does not state that a model read or followed them: C07 keeps
observed use a third fact. The evidence is the sealed request, and `evidence_digest` is its
digest. A child is its own recipient, named by the link and its use id, never by a session id
the owner made up.

## The owner's rules

- **Link.** `recipient.link.open` stores the link the caller states, for the requester alone,
  and mints its id and time.
- **Attempt, refused**, checked in this order:
  - a link not opened here: `recipient_link_unknown`, the attempt answered with `no_channel`;
  - a preparation not composed here: `ref_unavailable`; one composed for another link:
    `recipient_mismatch`;
  - a body the preparation did not compose (or whose bytes are not held): for a rehydrated
    recipient `rehydration_needs_bodies`, seen as `lost`; otherwise `request_mismatch`;
  - a route not supported on the link's host: `child_route_unsupported` for a child,
    `route_unsupported` otherwise, `supported: false` and `no_channel`.
  A refusal answered with its attempt keeps it privately (`private_state_written`); on a link
  held here it is also kept as a delivery requested of that recipient and not seen. Every
  attempt refusal names no recovery.
- **Attempt, answered.** `received` for exactly the bodies named, committed with a receipt.
- **Observe.** One observation per recipient a delivery of the preparation was requested of, in
  the order each was first requested. A recipient anything reached is `delivered` (or
  `activated`), with the evidence and the inventory of the units whose bodies arrived, drawn from
  those deliveries alone. A recipient nothing reached is `not_observed` with
  `delivery_unobserved`, and a child nothing reached is not named. The first observation writes
  it privately; observing again writes nothing.
- **Activate.** `session.routing.activate` activates the requester's session with one preparation.
  It refuses another profile (`request_mismatch`), a preparation not composed here
  (`ref_unavailable`), a session on another host than the preparation's link
  (`recipient_mismatch`), and a preparation whose claims no longer hold in the checkout
  (`working_bytes_moved`); each refusal recovers by a new request. It returns the routing, the
  projection of the preparation's Instructions units for the executor view entered at session
  start, and the bytes of each winning or layered body. A preparation composed for no link is
  activated too, and recorded for nobody.

## The memory usage guide

Every activated routing carries the short usage contract and a pointer to
`guides/memory-use.md` by path and by the digest of the bytes installed. V1 ships that guide
(the owner's option A). It states only what exists in V1; V2 writes the decision-use procedure
and extends it. The `shipped_guide` driver feature holds a case's stated guide digest to the
guide the code under test ships.

## Not in this slice

- **Probing and real delivery.** `capability.probe` for the delivery capabilities, driving each
  installed host through its adapter, and a delivery to a real Claude Code and Codex session on
  this machine, are the next increment of this slice.
- **Questions and resumes** through `recipient.delivery.attempt` are V2.
- **`role.project`**: no V1 case uses it.
- **DEL-PERSONAL**'s second preparation states a body digest an honest owner cannot compose; the
  spec change that keeps the case's intent goes to the P01 re-freeze.
- **The entrances** (`capability.probe` for `read`, `workenv/cli.py`, `workenv/tui.py`,
  `operation.history.read`) are the fifth slice.
