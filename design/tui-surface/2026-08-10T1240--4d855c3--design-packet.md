TUI screens are driven by a MenuScreen class; a parity gate drives the real TUI over a
pty and waits on byte-string screen markers (English text today); another gate pins

# The three features to design (one coherent design, staged)

F1 **Corpus-selection checklist in the TUI**: from the launcher's first screen, the
user selects which corpus domain packages are installed (the domain list comes from
`compose/domains.json`; core+infra always install). Design the full loop: where
selection state lives, who applies it (the launcher cannot deploy), when it takes
effect, how failure (canary fail) is surfaced, and what the read-only status panel
shows about pending vs applied selection.

F2 **TUI language selection: EN / KO / JP** — for the TUI chrome (menus, labels,
descriptions shown in the TUI). The CORPUS stays EN/KO (no JP corpus exists; out of
scope). Design: the string-catalog mechanism, where the language preference persists,
how completeness of each catalog is enforced (a missing key must not crash or silently
fall back invisibly — decide and justify), how the pty-marker parity gates survive
language (they pin English bytes today), and how preset/method DESCRIPTIONS (data in
TOML, English prose) interact with chrome language.

F3 **Guided reviewer registration (writer)**: today "Register another reviewer…" is an
info-only screen naming the user-owned file and its contract — deliberately, because a
form would duplicate the reader's validation and drift. The user now wants a guided
interactive registration flow that WRITES `review-methods.local.toml`. Design it so
validation stays single-sourced in the real reader (no second validator), including:
question sequence, how a candidate entry is proven valid before landing (and what
happens on refusal), editing/removing existing entries or not (justify), and collision
with shipped names.

# Principles to honor (from the repo's own corpus)

- Concept economy: reuse/extend existing concepts (user-owned sibling files, the
  onboard flow, corpus-status.json) before inventing new ones; every new file, key, or
  term must earn its place.
- LLM/capability boundary: deterministic code owns serialization, ids, paths,
  validation; validation single-source = the real parser/reader; never a duplicated
  validator that can drift.
- Differently-owned state stays separate: deploy-managed vs user-owned files never
  share one overwrite-managed file.
- Staged workflow: smallest viable functional change per stage; each stage's
  verification point and gate named.
- Pre-launch, ~1 real user: no backward-compat constraint; clean break + loud failure
  over shims; but never fail-open.
- Every new check ships with a negative control.
