## 1. Architecture decisions per feature

Both renderers should remain thin adapters over shared launcher services. Corpus application, language persistence, catalog lookup, and reviewer registration must not be independently implemented in Textual and numbered-prompt code.

### F1 — Corpus-selection checklist

- **Recommended:** Keep unchecked edits in launcher memory, then have both UIs invoke the existing `agent-bios onboard --domains <ids>` workflow as an argument vector; the installer alone deploys, runs the canary, rolls back on failure, and updates status.
- **Rejected:** Persist desired selection in a new launcher-owned queue file and have the installer discover it later; this creates a second durable authority and ambiguous stale “pending” state.

Flow:

1. Read selectable domain IDs and order directly from `compose/domains.json`. Render `core` and `infra` checked and disabled; pass only selectable IDs to `--domains`.
2. Initialize the checklist from `corpus-status.json.applied_domains`. A missing status means “no verified installation” and no optional domains selected. An invalid or unsupported status schema is a blocking diagnostic, not an empty selection.
3. Until confirmation, changes are labeled “Unsaved selection” and exist only in screen/controller memory.
4. On confirmation, resolve the installed `agent-bios` executable explicitly and run `agent-bios onboard --domains …` without a shell. The launcher streams progress and waits; it neither writes status nor modifies deployed files.
5. The installer atomically records `state=applying`, retaining the previous applied selection and recording the requested selection. It snapshots deploy-managed targets, installs, runs the real activation canary, and prunes only after success.
6. Success means the canary passed, `applied_domains=requested_domains`, and `state=ready`. That is when the selection takes effect.
7. On canary failure, restore the previous snapshot, set `state=failed`, retain the unapplied request and failure phase, and return nonzero. If restoration fails, set `state=degraded`, retain recovery material, and refuse normal launching until repaired.
8. The read-only panel shows:

   - `ready`: Applied selection; no pending line.
   - `applying`: Applied selection plus “Applying” requested selection.
   - `failed`: Applied selection plus “Requested, not applied,” failure phase, and rollback result.
   - `degraded`: Last verified selection plus a prominent “active installation untrusted” diagnostic.
   - Missing status: No verified corpus installation.
   - Invalid status: Status unreadable; do not invent applied state.

An interrupted `applying` attempt remains visibly incomplete. A subsequent installer run must recover or roll back the recorded transaction before accepting another request.

### F2 — EN / KO / JP TUI language

- **Recommended:** Use three release-owned catalogs keyed by stable semantic IDs, with `en` as the canonical key set, one user-owned language preference, and loud catalog recovery instead of per-string fallback.
- **Rejected:** Fall back to English whenever a localized key is absent; it conceals incomplete translations and produces an untestable hybrid interface.

Behavior:

- All launcher-owned menus, buttons, labels, help text, errors, and domain display text use one `tr(key)` service shared by both renderers.
- Domain IDs remain stable data. Display names and help use catalog keys derived from each manifest ID, such as `domain.<id>.label`; the catalog gate requires them for every current domain.
- Absence of `launcher.local.toml` means English. Selecting a language writes `[ui].language` atomically. The value is `en`, `ko`, or `ja`; “JP” is only the display label.
- Add `--ui-language en|ko|ja` as a non-persisting session override. Tests, support sessions, and automation can select deterministic chrome without modifying user preference.
- At build/test time, KO and JA must have exactly the English key set, with no missing or orphan keys. All literal `tr("…")` uses must exist; dynamically constructed keys are allowed only for a gate-checked namespace such as domains.
- At runtime, an invalid preference or incomplete selected catalog opens a small built-in recovery screen naming the file and missing keys. It offers a complete locale or exit; it does not silently select one. As a final safety net, an unexpected lookup renders `⟦missing:key⟧` and records a diagnostic instead of raising `KeyError`.
- Preset and reviewer names/descriptions remain data, not chrome. Their TOML values are shown verbatim in every language, under a localized label explaining that stored descriptions are not translated. No localized-description schema is added.
- Existing English pty markers remain byte-identical when launched with `--ui-language en`. KO/JA receive separate smoke markers; automation does not infer the active language from stored user state.
- Language affects presentation only. It must never enter serialized launch contracts.

### F3 — Guided reviewer registration

- **Recommended:** Ship an add-only wizard that builds candidate TOML, proves the complete shipped-plus-local candidate through the production reader, and atomically appends it only after acceptance.
- **Rejected:** Implement full CRUD with form-side field validation; it duplicates reader rules, increases destructive-write risk, and needlessly rewrites a user-owned file.

Question sequence:

1. Load the current shipped and local definitions through the real reader. If the existing local file is invalid, stop with its actual diagnostics; registration cannot repair it implicitly.
2. Choose either an existing capability or “create capability and method together,” where the current schema supports that distinction.
3. Ask for stable entry names and the stored description.
4. Ask the kind-specific invocation fields in the order exposed by reader-owned schema metadata. The wizard may constrain selection to canonical enumerations, but it must not decide semantic validity.
5. Show the exact TOML block and destination. Values are serialized literally; commands are not executed, shell-expanded, or capability-probed. Secret values are not accepted—only environment-variable names where the contract permits them.
6. After confirmation:

   - Capture the original file bytes, identity/digest, and permissions.
   - Deterministically append the new block to those bytes in a same-directory temporary file.
   - Invoke the production loader with the normal shipped source and that temporary file as the local source. This preserves the real merge-before-validation order and collision behavior.
   - On acceptance, verify the original has not changed, atomically replace it, and re-read the live paths through the same loader.
   - On refusal, delete the temporary file, leave the original byte-for-byte unchanged, display the reader’s structured diagnostics, and let the user revise an answer or cancel.

A collision with a shipped name is therefore refused by the existing reader. The wizard must not shadow, rename automatically, or special-case it.

Editing and removal are intentionally excluded from this release. Add-only append preserves existing comments and formatting and avoids destructive ownership questions. Existing entries remain manually editable/removable in the documented user-owned file; CRUD can be considered later with explicit backup and preservation requirements.

## 2. Data/authority map

| Artifact or key | Owner | Lifecycle and authority |
|---|---|---|
| `compose/domains.json` | Installer | Canonical selectable domain IDs and order. Shipped/deployed with the product; launcher reads it but never copies or edits it. |
| `corpus-status.json.schema_version` | Installer | Increment for the new state contract. Unsupported versions fail loudly. |
| `corpus-status.json.state` | Installer | `ready`, `applying`, `failed`, or `degraded`; written atomically at transaction boundaries. |
| `corpus-status.json.attempt_id` | Installer | Identifies an in-progress or failed installation transaction. |
| `corpus-status.json.applied_domains` | Installer | Last canary-verified optional-domain selection; never launcher-authored. |
| `corpus-status.json.requested_domains` | Installer | Current/latest requested optional-domain selection. Pending state is derived from this, `state`, and `applied_domains`; no separate boolean. |
| `corpus-status.json.error` | Installer | Nullable structured failure phase and safe summary; cleared on successful application. |
| `~/.local/share/agent-bios/install-transactions/<attempt-id>/` | Installer | Snapshot and recovery material for deploy-managed targets. Deleted after success or successful rollback; retained only for `degraded` recovery. |
| `launch/locales/en.toml` | Launcher | Canonical catalog key set and English chrome. Release-owned and overwritten on product deployment. |
| `launch/locales/ko.toml`, `ja.toml` | Launcher | Exact-key translations of the English catalog. Same release lifecycle. |
| `launcher.local.toml` → `[ui].language` | User | New user-owned sibling file. Absent means English; launcher writes atomically after an explicit selection; installer never deploys or overwrites it. |
| `profiles.toml` | Installer | Remains deployment-owned. No language preference is added here. Stored preset/method descriptions remain unchanged. |
| `presets.local.toml` | User | No schema or write-path change. Names and descriptions are rendered verbatim. |
| `review-methods.local.toml` | User | Existing schema and reader remain authoritative. The launcher may append a reader-approved entry atomically; installer never overwrites it. |
| Same-directory reviewer candidate temp file | Launcher | Mode `0600`, validation-only, never authoritative; removed after refusal or atomic commit. No durable draft file is introduced. |
| Shipped reviewer definitions | Installer | Continue to merge before local definitions and before validation. No collision or validation rule moves into the wizard. |

## 3. Gate strategy

| Gate | What it pins | Negative control |
|---|---|---|
| `catalog-contract` | Exact EN/KO/JA key equality, valid language values, all literal translation references, and catalog entries for every domain ID. | Remove one KO key and add one unknown code reference; the gate must fail and runtime recovery must remain non-crashing. |
| Existing `pty-marker` parity gate | Runs the real Textual UI with `--ui-language en`, preserving current English byte markers. The fallback path is exercised with the same state/actions. | Remove one renderer’s action binding or change a pinned English marker; parity must fail. |
| `locale-ui-parity` | EN, KO, and JA can each reach representative first-screen, corpus, error, and registration screens in both renderers; language selection persists identically. | Supply an invalid stored language and an incomplete selected catalog; both paths must show recovery rather than normal menus. |
| `corpus-apply-e2e` | Real installer against isolated deployment roots: manifest order, locked core/infra, status transitions, canary, rollback, and panel projection. Both UIs must invoke the same argv. | Force the real canary to fail; verify nonzero exit, unchanged previous applied selection, restored deploy targets, retained requested selection, and visible failure. Also reject an unknown domain ID. |
| `review-writer-e2e` | Wizard candidate → deterministic TOML → production merged reader → atomic landing → production reread, through both renderers. Original bytes outside the appended block remain unchanged. | Try a shipped-name collision, semantically invalid entry, invalid pre-existing local file, and concurrent file change; every case must refuse without mutation. |
| Existing launch-contract golden | English baseline remains byte-for-byte unchanged; EN/KO/JA and persisted/session language choices produce identical canonical contracts. | Inject a localized chrome value into contract serialization; the golden/invariance check must fail. |

Catalog translation quality is a human review concern; completeness, lookup safety, and contract isolation are deterministic gates.

## 4. Staged implementation plan

1. **Installer transaction and status contract**

   Implement the new status state machine, deployment snapshot/rollback, interruption recovery, and CLI-only `onboard --domains` behavior.

   **Done when:** `corpus-apply-e2e` demonstrates one successful selection and one forced canary failure with restored targets and truthful status.

2. **Localization substrate on existing screens**

   Add catalogs, shared lookup/recovery logic, `launcher.local.toml`, the non-persisting override, and convert all current chrome in both renderers.

   **Done when:** `catalog-contract`, `locale-ui-parity`, the forced-English pty gate, and language-independent contract golden all pass with their negative controls.

3. **Corpus checklist and status projection**

   Add the first-screen checklist, in-memory dirty state, locked core/infra rows, shared installer invocation, progress/failure UI, and applied/requested panel projection.

   **Done when:** a real pty can select and apply domains through Textual and fallback paths, restart into the applied selection, and visibly retain an unapplied request after forced canary failure.

4. **Production-reader candidate seam**

   Refactor the existing reviewer loader to accept an explicit local candidate path and return structured diagnostics without changing merge or validation semantics.

   **Done when:** existing production inputs produce identical accepted models and invalid/collision fixtures produce identical refusals through both the old load entry point and candidate entry point.

5. **Add-only reviewer writer**

   Implement the shared question controller, both presentation adapters, deterministic append serializer, candidate proof, concurrent-change check, atomic replacement, and live reread.

   **Done when:** a guided registration lands and is immediately loadable by the production reader, while every refusal case leaves the original local file byte-for-byte unchanged.

## 5. Risks/open questions the implementer must answer before coding

1. What exact files constitute one deployed corpus transaction, and can the current canary run before final activation? If not, snapshot/restore must precede any TUI integration.
2. Is `compose/domains.json` guaranteed to be installed beside the launcher, and which fields provide stable ID, order, and user-facing meaning?
3. What are the reader’s actual method/capability kinds and required field groups, and can it expose structured diagnostics and prompt metadata without changing acceptance semantics?
4. How are launcher and installer version skew handled around the new status schema? The default should be a schema-version refusal, not a compatibility guess.
5. Who approves KO/JA terminology, and do all translated screens fit both Textual cell-width behavior and the narrow numbered fallback?
