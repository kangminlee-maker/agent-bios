## Seat verdict: concept-economy

[1] PRESERVED — old clause: “reusing existing concepts that clearly cover the behavior” / new text: “**Reuse** | an existing concept already covers this behavior” and “this is the default” — The guide preserves the rule and strengthens reuse into the default; contemplating a new lasting/shared concept matches the router.

[2] PRESERVED — old clause: “Treat lasting or shared names as concept candidates” / new text: “Anything **lasting or shared**” followed by the complete original list — The guide preserves every listed category, while the router’s “anything lasting or shared” covers categories omitted from its examples.

[3] TRIGGER_GAP — old clause: “Before adding or changing a concept” / new text: “Before adding or changing a concept, find the nearest existing one and choose a path **explicitly**”; router: “When adding, renaming, splitting, or exposing anything lasting or shared” — The content survives, but generic changing is absent from the router. Broadening an existing concept’s behavioral meaning without adding, renaming, splitting, or exposing a name would not match it.

[4] PRESERVED — old clause: “Prefer broad, stable concepts with precise properties over narrow near-duplicates” / new text: “Prefer broad, stable concepts with precise properties over narrow near-duplicates” — The rule is verbatim, and creating or splitting a lasting/shared concept matches the router.

[5] PRESERVED — old clause: “runtime behavior, ownership, lifecycle, validation, failure mode, user-visible behavior, audit/replay requirements, authority, persistence, user control, or failure handling” / new text: “runtime behavior · ownership · lifecycle · validation · failure mode · user-visible behavior · audit/replay requirements · authority · persistence · user control · failure handling” — Every trigger is retained, and “splitting” is an explicit router trigger.

[6] TRIGGER_GAP — old clause: “Keep derived values as properties or projections of their source concept when tools/code can derive them from the source authority” / new text: “A value that tools or code can compute from its source is a **property or projection** of that source, not a concept of its own”; router: “When adding, renaming, splitting, or exposing anything lasting or shared” — Changing an already-existing derived field from source-derived to independently written creates a second authority without necessarily adding, renaming, splitting, or exposing anything, so the guide may never load.

[7] PRESERVED — old clause: “Keep internal projections and helper outputs internal unless public exposure is required for user behavior, product contract, or artifact truth” / new text: “Keep internal projections and helper outputs internal unless public exposure is genuinely required by user behavior, a product contract, or artifact truth” — The qualification is preserved and slightly strengthened; proposed exposure matches the router explicitly.

[8] TRIGGER_GAP — old clause: “Distinguish authority from visibility” / new text: “**Authority is not visibility.** These are separate questions”; router: “When adding, renaming, splitting, or exposing anything lasting or shared” — Changing the writer or truth location of an existing internal artifact while leaving all visible surfaces unchanged is governed by the old rule but does not match the router.

[9] PRESERVED — old clause: “Reuse existing enum values, failure kinds, retry/recovery tokens, and result/failure surfaces before introducing new vocabulary” / new text: “Check the existing set first, and prefer an existing value whose meaning genuinely covers the case over a new one” — The guide retains all four vocabulary categories and the reuse-first requirement; introducing a new lasting/shared value matches the router.

[10] WEAKENED — old clause: “Use fallback paths, compatibility shims, and deprecated alias normalization when explicit migration compatibility is required” / new text: “Fallback paths, compatibility shims, and deprecated alias normalization are correct **when explicit migration compatibility is required**” — The imperative obligation “Use” has become the permissive judgment “are correct”; the added removal-condition rule does not restore the requirement to employ compatibility measures when migration compatibility is required.

[11] TRIGGER_GAP — old clause: “Keep comments and active docs aligned with runtime behavior, failure semantics, retry policy, ownership, and authority” / new text: “Keep them aligned with current runtime behavior, failure semantics, retry policy, ownership, and authority”; router: “When adding, renaming, splitting, or exposing anything lasting or shared” — A runtime, failure-semantic, or retry-policy change under unchanged names can make active documentation false without matching any router operation.

[12] PRESERVED — old clause: “name the parent concept, explain the reason for the split, and map aliases or variants back to the canonical concept” / new text: “**Name the parent.**”, “**State the reason.**”, and “**Map the variants back.**” — All three required split deliverables remain, with additional precision, and splitting is expressly routed.

[13] WEAKENED — old clause: “In ontology work, check existing entities and relations first” / new text: “**Ontology work.** Check existing entities and relations before adding either” — The guide restricts the check-first duty to additions; its application to modifying, removing, or relinking existing ontology elements is NOT FOUND. The compact-graph objective otherwise survives through the guide’s reuse and anti-duplication rules.

[14] TRIGGER_GAP — old clause: “In code work, follow existing naming patterns and consolidate variations introduced by the current change” / new text: “Follow the naming patterns already in the file, and consolidate the variations your own change introduced”; router: “anything lasting or shared” — Code work involving transient locals is covered by the unqualified old clause but excluded by the router, so introducing inconsistent local names can bypass the guide. Separately, “existing naming patterns” is narrowed to patterns “already in the file,” losing repository-wide scope.

[15] TRIGGER_GAP — old clause: “Let the repository’s shape mirror its concept graph” / new text: “Let the repository’s shape mirror its concept graph”; router: “When adding, renaming, splitting, or exposing anything lasting or shared” — Auditing or reorganizing an existing repository’s paths and layers while retaining the same canonical names need not match any router verb, even though the full navigability rule applies.

The guide preserves most of the substantive concept-economy doctrine, including the candidate list, four paths, split triggers, vocabulary reuse, exposure boundaries, and repository traceability. The principal defect is routing: six rules remain available only after recognizing operations narrower than the situations those rules originally governed. Two additional clauses lose meaning directly—migration compatibility changes from mandatory to permissive, and ontology checking is narrowed to additions. The worst loss is [11]: a same-name runtime or retry-policy change can bypass the guide entirely and leave active documentation functioning as the “second, false authority” the guide itself warns against.

## Seat verdict: coding-guidelines

[1] TRIGGER_GAP — old clause: “When the user asks to ‘설계’ or design” / new text: “For meaningful development work, read and use … coding-staged-workflow.md”; guide: “When the user asks to ‘설계’ or design, stay in design mode.” — The procedure survives, but a narrow design request—such as designing a small config adjustment—need not be recognized as “meaningful development work,” so the guide may never load.

[2] TRIGGER_GAP — old clause: “Think before coding: state key assumptions and surface ambiguity early.” / new text: “State the assumption before you act on it” and “Where the request admits more than one reading, say which one you took”; router: “For meaningful development work” — The normative content survives, but an ambiguous one-line or otherwise trivial edit can require assumptions without being classified as meaningful development work.

[3] TRIGGER_GAP — old clause: “Build the smallest viable functional path that satisfies the qualitative completion criteria. Minimum limits surface area, configuration, abstractions, optional scope, and implementation spread; it must not reduce required behavior, runtime authority, evidence quality, or verification depth.” / new text: “make the smallest viable functional changes” and “Minimum limits surface area, configuration, abstractions, optional scope, and implementation spread. It must not reduce required behavior, runtime authority, evidence quality, or verification depth”; router: “For meaningful development work” — The rule survives substantially intact, but it also governs narrow config or single-file work that the guide itself assigns to a “lightweight” path and the router may not match.

[4] TRIGGER_GAP — old clause: “Treat viability as real behavior against real inputs, real authority, and the intended runtime path” and “mock-backed paths support verification but do not count as product completion.” / new text: “Use real paths for: product behavior,” “Product completion has real semantic-path evidence,” and “Mock-backed paths can support verification but do not count as product completion”; router: “For mock, fixture, fake, stub, simulated-provider, or test-realization design” — The substance survives, but viability failures need not be recognized as mock design. For example, an agent editing an exported local copy of a connected cloud document instead of using its native authority could miss this guide without ever labeling the approach a mock, fake, or simulation.

[5] TRIGGER_GAP — old clause: “Make surgical changes. Touch only what the request requires, preserve existing style, and avoid casual adjacent refactors.” / new text: “Touch what the request requires, follow the file’s existing style rather than your preferred one, and leave adjacent code alone”; router: “For meaningful development work” — The rule is preserved in the guide, but it remains necessary for trivial text, config, and single-file edits that may not trigger the router.

[6] TRIGGER_GAP — old clause: “Clean up issues introduced by the current change. Mention unrelated dead code separately.” / new text: “Clean up what this change introduced, and only that” and “Debris you found belongs in a sentence: name it so it is visible, and leave it”; router: “For meaningful development work” — Both cleanup and separate-reporting duties survive, but they also apply to small edits that may be treated as non-meaningful and therefore never load the guide.

[7] TRIGGER_GAP — old clause: “Define success criteria before multi-step coding work, then verify against them.” / new text: “Define the success criteria before multi-step work starts, then verify against those criteria”; router: “For meaningful development work” — The clause is preserved verbatim in substance. A routine multi-step change, such as renaming a config key across several files, can still be classified as a “narrow config change” rather than meaningful development work, leaving the rule unloaded.

[8] TRIGGER_GAP — old clause: “For bugs, prefer a reproducing test before the fix when practical.” / new text: “For a bug, reproduce before you fix, when that is practical”; router: “For meaningful development work” — The rule survives at equal strength, but a practical reproduction for a small single-line bug fix can be skipped if the fix is classified as trivial rather than meaningful development work.

[9] TRIGGER_GAP — old clause: “Every changed line should trace back to the user’s request.” / new text: “Touch what the request requires” and “leave adjacent code alone even when it is worse than what you are adding”; router: “For meaningful development work” — The scope constraint survives, but it is equally relevant to trivial edits, which can fall outside the router.

[10] TRIGGER_GAP — old clause: “Fix the root cause at its authority rather than the visible symptom” and “single-source the value and fix the whole class instead of patching instances.” / new text: “Fix the cause at its authority, not the symptom where it shows” and “single-source the value and fix the class”; router: “For meaningful development work” — The complete root-cause rule survives, including both downstream-compensation signals, but a small or obvious single-file bug may be handled through the lightweight path without loading it.

The dominant pattern is not textual deletion: all ten rules survive substantially in the guides. The meaning loss comes from replacing always-loaded domain rules with routers narrower than the rules’ original applicability, especially the subjective “meaningful development work” threshold. The guides explicitly send trivial and narrow work to a lightweight global path, but the supplied new global section does not carry these safeguards there. The single worst effective loss is [4]: real-input, real-authority, and intended-runtime viability can fail without the agent recognizing that it is doing “mock … or test-realization design,” allowing mock-like or authority-bypassing work to be mistaken for product completion.

## Seat verdict: verification-discipline

[1] PRESERVED — old clause: “Use static checks broadly: typecheck, lint, build, format, schema/config validation, graph validation, workbook structure checks, import boundaries, and security checks when available.” / new text: “Run the broad, cheap checks first”; “typecheck, lint, build, format, schema and config validation, graph validation, workbook structure checks, import boundaries, and security checks where they exist.” — The complete check set and availability qualifier survive, while “first” adds sequencing without reducing force. The router’s “choosing verification depth” and “per-domain mix” cover selecting these checks after the globally mandated verification loop.

[2] PRESERVED — old clause: “Add the narrowest reliable runtime or semantic test that proves the changed behavior, meaning, or contract.” / new text: “the unit to add is the narrowest reliable runtime or semantic test that proves it”; “Pick the narrowest reliable mix that proves the changed behavior, meaning, or contract.” — Both the required test unit and what it must prove are retained. The router explicitly covers choosing “the per-domain mix.”

[3] PRESERVED — old clause: “Pick each domain’s verification mix (code, ontology, config/data, spreadsheets, docs) from the Verification Menus in the coding-staged-workflow guide.” / new text: “For choosing verification depth, the per-domain mix”; “its Verification Menus carry the per-domain mixes”; “Code”; “Ontology”; “Config or data”; “Spreadsheets”; “Docs.” — The menus moved to a different guide, but the normative selection rule and every named domain remain. The router directly names “the per-domain mix.”

[4] PRESERVED — old clause: “Let the LLM derive scenarios from the diff, user impact, concept impact, and failure modes; let tools/code execute and verify them.” / new text: “derive them from the diff, the user impact, the concept impact, and the failure modes. Running them is not — tools and code execute the cases and report the evidence.” — The semantic/tooling division is preserved; in an instruction directed to the agent, “semantic work” retains the LLM side of that division. The remaining clauses survive as “Enumerate the space from the artifact that defines it” and “Record the verdict, do not type it,” and the router expressly covers “the case space.”

[5] TRIGGER_GAP — old clause: “Keep E2E stable with deterministic data, resilient selectors, isolated external dependencies, and explicit waits.” / new text: guide: “Keep it deterministic with fixed data, resilient selectors, isolated external dependencies, and explicit waits rather than sleeps”; router: “For choosing verification depth, the per-domain mix, the case space, or what a green result is worth.” — The substantive rule is preserved, but its situation is not named by the router. An agent repairing or authoring an already-selected E2E test’s fixtures, selectors, dependency isolation, or waits could be applying test-maintenance practices—not choosing depth, mix, case space, or interpreting a green result—and therefore never load the guide.

[6] TRIGGER_GAP — old clause: “Make completion criteria falsifiable: prefer signals that fail when the mechanism is wrong (negative or contrast controls), and if no existing gate can judge a criterion, build the executable judge or do not claim the criterion met.” / new text: guide: “Make the criterion falsifiable before you make it green. Prefer a signal that fails when the mechanism is wrong — a negative or contrast control. Where no existing gate can judge a criterion, build the executable judge or do not claim the criterion met”; router: “For choosing verification depth, the per-domain mix, the case space, or what a green result is worth.” — Every substantive clause survives verbatim or nearly verbatim, but defining acceptance or completion criteria before verification begins is not clearly one of the router’s situations. An agent could write non-falsifiable completion criteria without perceiving itself as choosing verification depth, case space, or evaluating a green result.

[7] PRESERVED — old clause: “For non-trivial designs or high-risk changes, run independent adversarial review across distinct lenses, ideally on the design before implementation, and re-verify each finding against real code before acting on it.” / new text: “For non-trivial designs and high-risk changes, run independent adversarial review across distinct lenses — ideally on the design, before implementation”; “Then re-verify each finding against real code before acting on it.” — The reviewer-kind rules also survive: “Same-kind convergence is high confidence but blind-spot-sharing,” “Different-kind divergence is the expected signal,” “Act on the union,” and “An orchestrated workflow’s self-reported all-green is never sufficient on its own.” The routers cover both choosing verification depth and composing the resulting review request.

[8] PRESERVED — old clause: “Proportion verification to cost, risk, and information gain”; “diagnose in code and replay the changed deterministic logic over persisted real artifacts”; “probe at N=1 with inputs precondition-checked”; “reserve full design-review-plus-live verification for first-of-kind or authority-changing work”; “a single-user, own-data tool does not warrant production-grade assurance; prefer delivery.” / new text: “Verification has a cost and an information yield”; “Diagnose in code”; “replay the changed deterministic logic over persisted real artifacts”; “Probe at N=1 with the inputs precondition-checked”; “Reserve the full design-review-plus-live-verification treatment for first-of-kind work and for changes that move authority”; “A single-user tool operating on its owner’s own data does not warrant production-grade assurance”; “Prefer shipping.” — All depth, sequencing, deployment-context, and delivery clauses remain at equal strength. The router directly names “choosing verification depth.”

[9] PRESERVED — old clause: “assert the entity-under-test set has cardinality > 0”; “confirm its inputs satisfy the live branch’s entry guard”; “dump what it actually ran over”; “Checker code itself must assert the expected shape and fail loud”; “a permissive fallback (`a || b`) inside a gate absorbs wrong assumptions and keeps passing.” / new text: “Assert the entity-under-test set has cardinality greater than zero”; “confirm its inputs satisfy the live branch’s entry guard”; “dump what it actually ran over before believing it”; “Checker code must assert the shape it expects and fail loud”; “A `a || b` inside a gate absorbs a wrong assumption and keeps passing.” — Every vacuous-pass, branch-guard, suspicious-run, and checker-fallback clause is retained. The router expressly covers “what a green result is worth,” including results that are “green, empty, or fast.”

Overall, seven bullets are preserved and two suffer trigger gaps rather than textual loss. The guides generally retain the old rules with high fidelity and sometimes add useful precision. The recurring weakness is that maintenance or criteria-definition moments do not necessarily announce themselves as choices about verification depth, mix, case space, or green-result value. The worst gap is [6]: an agent can define unfalsifiable completion criteria—and later claim them satisfied—before recognizing that it should load a verification guide at all.

## Seat verdict: documentation-hygiene

[1] PRESERVED — old clause: “Use comments for non-obvious current behavior, invariants, constraints, or risks that still apply.” / new text: “A comment earns its place by saying something the code cannot say about itself,” followed by “Non-obvious current behavior,” “An invariant,” “A constraint,” and “A risk that still applies.” — The router broadly covers deciding “where a comment … belongs,” and the guide preserves every listed use.

[2] TRIGGER_GAP — old clause: “backward-compatibility notes, deprecated behavior, migration rationale, historical alternatives, change narratives, and handoff logs” / new text: guide: “Isolated paths … carry backward-compatibility notes, deprecated behavior, migration rationale, historical alternatives, change narratives, and handoff logs”; router: “a rejected alternative, a migration rationale, a change narrative, or a handoff log” — The placement rule survives exactly, but the router omits backward-compatibility notes and deprecated behavior and narrows “historical alternatives” to “a rejected alternative.” An agent placing documentation for still-supported legacy behavior could therefore miss the guide entirely.

[3] TRIGGER_GAP — old clause: “Link from active docs or code to isolated notes only when the current task needs that history or the reference helps future maintainers.” / new text: guide: “Link from active material to a historical note only when the current task needs that history, or when the reference genuinely helps a future maintainer”; router: “For where a comment, a rejected alternative, a migration rationale, a change narrative, or a handoff log belongs” — The substantive rule is preserved, but the router says nothing about deciding whether active material should link to history. An agent adding a link from a current architecture document to an old design note could be in the governed situation without matching the router.

[4] PRESERVED — old clause: “Phrase guidelines as desired behavior and preferred patterns.” / new text: “Phrase a rule as the behavior you want, not as the thing you are afraid of,” with positive-pattern examples such as “Pin the interpreter when a bash-specific feature is needed.” — The router expressly covers “how to phrase a rule others will follow,” and the guide retains the positive, preferred-behavior requirement at equal strength.

[5] TRIGGER_GAP — old clause: “Prefer established docs such as `CHANGELOG.md`, `IMPLEMENTATION_MAP.html`, or handoff notes for change history and implementation context.” / new text: guide: “Prefer the established homes over inventing one per change: a changelog for released behavior, a current-state dashboard for architecture and risk, handoff notes for what a session left unfinished”; router: “where … a change narrative, or a handoff log belongs” — The guide preserves the preference and functional destinations, but the router does not cover implementation context generally. Someone deciding where to record current architecture or implementation-map information, without writing a change narrative or handoff log, could fail to load it.

The refactor largely preserved the substantive rules inside the guide, including the comment taxonomy, historical-document placement, positive rule phrasing, and established documentation homes. The dominant failure is router undercoverage: bullets 2, 3, and 5 remain available only after recognizing narrower situations than the old rules governed. Bullets 1 and 4 have sufficiently broad router language and retain their force. The worst loss is bullet 3 because historical-link decisions are wholly absent from the deployed router, making that entire preserved section vulnerable to recognition failure.
