# Are the rules in the right surface, and is each one actually consumed?

Opened from the merge session that landed `ontology-seed`. Nothing here is decided; this
records the question and the evidence that raised it, so a later round starts from a fact
rather than from a feeling that the file is getting long.

## The question, in three parts

**1. Where do this session's new principles go?** One is unplaced:

> **Discriminate before fixing.** When one symptom has two candidate causes, fixing either
> one destroys the evidence for both. And two hypotheses about a failure are not necessarily
> exclusive — a regression and a stale expectation were both true at once.

The nearest existing bullet (`claude/CLAUDE.md:59`, classify a fix by concept surface) is a
different axis, so this is an addition rather than an extension. The always-loaded file is a
token budget, so placing it means naming what it displaces — or deciding it belongs behind a
pointer, or in a gate, or nowhere.

A second candidate is already placed and needs no work: treating reviewer findings as
hypotheses is `claude/CLAUDE.md:33`.

**2. Do the existing `AGENTS.md` items belong where they are?** The file has grown by
absorbing a branch's worth of method. `## Ontology rounds` is 68 lines of how-to-run-a-round
that is needed when you run one, not every session — which is the definition of a guide, not
a global. It stayed in `AGENTS.md` during the merge only because `design/archive/README.md`
assigns durable method there in as many words, and resolving that collision is a decision of
its own rather than a merge resolution.

The general form of the question: for each section, does it work **even when the reader fails
to recognize the situation**? If yes it earns always-loaded placement. If its failure mode is
recognition failure, it belongs behind a pointer.

**3. Is each item routinized where it sits, or is it only prose?** This is the part with
teeth, and the merge session produced three defects that are all the same shape — a rule that
was stated where it could not fire:

| what was stated | where it actually had to hold |
| --- | --- |
| a brace balances, so the file parses | a nested function definition is legal bash; only running the install found it |
| `SURFACES.md` names the hook authority | the named path was untracked, so it resolved only on an already-installed machine |
| the hook judges the index | `git commit` exports a RELATIVE `GIT_INDEX_FILE`; after the hook's `cd` every git-reading gate saw an empty index |

None of these were caught by the layer that stated the rule. Each was caught — or missed —
by whether some mechanism could actually fire on the real input.

## Why this is worth a round rather than an edit

`SURFACES.md` already declares thirteen surfaces with what each admits, refuses, and fails
as; `design/session-distill/PLACEMENT-FRAMEWORK.md` already orders the layers cheapest-first.
The machinery to answer all three parts exists. What has never been done is the sweep: walk
every rule currently in `AGENTS.md` and the deployed global, name the surface it sits in,
and ask whether anything would notice if it were violated.

Expect the honest answer for several of them to be "nothing would notice", and expect that to
be correct for some — the repo deliberately refuses to gate judgment calls, because a gate
people learn to route around is worse than none. The output of the sweep is therefore not
"add a gate for each" but a per-rule disposition: enforced, disclosed, or knowingly prose.

## Entry conditions

Not blocked on anything. Cheap to start, and it wants a quiet session rather than one that
is also landing a merge — the sweep's whole value is in reading each rule against what
actually enforces it, which is slow and easy to fake.
