# 업무용 화면을 설계하고 결과를 전달하는 방법

사람이 근거를 살펴보고, 작업을 구성하고, 판단을 내리거나 기록을 처리하는
화면에 사용한다. 결과물은 사용자가 요청한 단계와 범위에 맞춘다.
고칠 글자가 명확한 단순 수정이라면, 그 글자를 고치고 그에 맞는 확인을 한다.

## 1. 자료가 지금 무엇을 뜻하는지 확인한다

이미 구현된 동작, 받아들여진 요구사항, 제안된 설계 선택, 설명용 예시를 구별한다.
예전 화면을 다시 활용하기 전에 이후의 수정 사항과 결정을 함께 확인한다.
날짜가 더 최근이라는 이유만으로 그 자료가 우선하는 것은 아니다.
중요한 모순이나 아직 모르는 내용은 드러내 두고, 편리한 해석 하나를 말없이 선택하지 않는다.

## 2. 요청한 범위를 지키고 결과물의 단계에 맞게 작업한다

누가 사용하는지, 어떤 결과를 얻어야 하는지, 무엇을 확인하면 이번 결과물이
완성됐다고 할 수 있는지 정한다. 업무에 필요한 기준과 맥락을 받아 쓰는 사람과
그 내용을 작성하거나 관리하는 사람을 구별한다. 각자가 얼마나 자주 방문하는지
지어내거나 모두 같은 곳에서 시작해야 한다고 가정하지 않는다.

전체 설계를 요청받았다면, 화면 뒤에서 일을 처리하는 기능이 아직 없어도
요청받은 동작을 설계에 포함한다. 각 동작의 대상, 입력, 효과, 필요한 선행 조건과
문제가 생겼을 때의 복구 방법을 설명한다. 이를 구현 완료라고 표현하지 않는다.

범위가 정해진 작은 변경이라면, 주변 기능을 늘리기 전에 요청받은 작업 흐름부터
완성한다. 그 흐름을 완성하는 데 꼭 필요하거나 이번 변경 때문에 기존 기능이
잘못 동작하게 됐다면 관련된 부분도 고치고 이유를 밝힌다.
구현이 아직 없다는 이유로 요청받은 설계 내용을 빼지 않는다.

## 3. 사용자가 다음 판단을 내리기 쉽게 구성한다

지금 다루는 업무 범위, 비교할 근거, 현재 상태, 가능한 행동과 그다음 단계를
함께 이해할 수 있게 보여 준다. 프로그램 내부의 기능 묶음이나 처리 단계가
곧바로 메뉴나 버튼이 되어야 하는 것은 아니다.

사용자가 따로 선택할 일이 없다면, 이미 허용된 하나의 요청 아래 여러 준비 단계를
함께 처리할 수 있다. 이때 서로 구별해야 하는 결과는 이해할 수 있게 유지한다.
팀의 시각 체계를 사용해 업무의 중요도에 따라 강조를 배분한다.
글자, 간격, 색, 경계가 정보 사이의 의미 있는 관계를 드러내게 한다.
실제 사용할 화면 크기에서 중요한 업무 내용이 잘 보이는지 확인한다.
장식적인 요약 영역도 업무에 도움이 될 때 공간을 사용하게 한다.

배치를 어떻게 할지가 중요한 미결 사항이라면, 판단에 필요한 만큼만 만든
간단한 시안으로 여러 배치를 비교한다. 각 배치가 업무에 어떤 이점과 부담을 주는지,
어떤 근거가 나오면 선택을 바꿀지 설명한다.

새로운 시각적 방향이나 중요한 배치 결정을 내려야 한다면
`${CODEX_HOME:-$HOME/.codex}/guides/ui-design/visual-direction.md`를 사용한다.
방향이 이미 정해졌거나 범위가 좁은 수정이라면 새로운 레퍼런스 조사나 여러 시안이
반드시 필요한 것은 아니다.

## 4. 조건과 설명이 필요한 정보를 서로 떨어뜨리지 않는다

요약, 수정, 비교, 내보내기를 거쳐도 적용 조건, 예외, 단위, 출처와 버전,
날짜·시간의 의미, 영향을 받는 범위를 보존한다. 서로 독립적인 구분은 따로 유지한다.

근거가 없다는 것은 결과가 비어 있거나 값이 0이라는 뜻이 아니다.
목록이나 관계도에 표시됐다는 사실만으로 실제 본문이 있거나 그 의미가 확인됐다고
볼 수는 없다. 기술적인 설명은 도움이 될 때 펼쳐 볼 수 있게 하되,
판단에 영향을 주는 제한을 숨기지 않는다.

## 5. 각 행동의 권한과 효과를 정확하게 설명한다

변경을 검토할 때는 정확한 대상, 변경의 기준이 된 내용이나 버전,
실제로 바뀌는 내용을 밝힌다. 기준이나 권한이 달라졌다면 다시 확인한다.
이전 승인을 다른 입력에 그대로 적용하지 않는다.

해당 작업에 필요한 경우 선택, 초안 저장, 승인, 실행, 수신자의 실제 사용을 구별한다.
앞 단계가 잘됐다는 사실만으로 다음 단계도 끝났다고 볼 수 없다.
결과가 불확실하면 같은 요청을 계속 식별할 수 있게 유지한다.
실제 결과를 확인한 뒤 다시 시도한다.

화면의 버튼이나 선택 기능은 기존 권한 규칙을 반영해야 한다.
그 화면이 권한 규칙을 새로 만드는 것은 아니다. 정책이 아직 정해지지 않았다면
제안하는 선택지와 이를 결정할 책임 주체를 명시한다.
권한이 있는 것처럼 보이게 하거나 필요한 설계를 통째로 빼지 않는다.

## 6. 화면이나 사람이 바뀌어도 같은 작업을 이어간다

서로 다른 화면이나 도구로 이동해도 초안, 대상, 어느 검토·요청인지 구별하는 정보와
돌아갈 작업 맥락을 보존한다. 같은 결과를 얻는 데 적합한 표현을 사용한다.
배치를 똑같이 만들거나 업무 규칙을 여러 곳에 따로 구현할 필요는 없다.

위치나 관계를 직접 다루는 조작이 꼭 필요하다면, 키보드 조작과 구조화된 목록·표 같은
대체 방법도 제공한다. 내용을 실제로 받을 사람이나 작업을 기준으로 근거를 확인한다.
다른 작업자의 수신 기록만으로 이번 수신자에게도 접근 권한이 있거나 내용이 전달됐다고
판단하지 않는다.

## 7. 이번 결과물에 필요한 확인을 마친 뒤 작업을 끝낸다

설계라면 구체적인 사용 상황과 관련 예외를 따라가며 원자료와 맞는지 확인한다.
제안한 화면 구성이 그 일을 지원하는지도 살펴본다. 실제로 동작하는 기능을 바꿨다면
바뀐 실행 경로와 관련된 실패 상황, 키보드 조작, 복구 동작을 실행해 확인한다.

시각적으로 중요한 변경이라면 대표 내용과 관련 상태를 넣어 영향을 받는 구성을
실제 사용할 크기에서 확인한다. 토큰 변경과 정보 배치 변경을 구별한다.
배치가 바뀌어도 시각적 순서, 읽기 순서, 포커스 이동 순서가 서로 맞는지 확인한다.
시각적 선호는 관찰한 작업 성과와 따로 보고한다.

시뮬레이션 결과, 실제 실행에서 관찰한 결과, 사용자에게서 얻은 근거를 구별한다.
필요한 확인이 끝나면 결과물, 중요한 결정, 사용한 출처·버전 등 자료의 연결 정보와
남은 작업을 팀이 평소 사용하는 문서나 작업 파일에 남긴다.
비공개 정보는 허용된 범위 안에서만 다룬다.

라이브러리나 도구 선택은 요구사항 때문에 그 결정이 필요할 때 한다.
먼저 팀이 현재 지원하고 사용하는 환경을 활용한다.
